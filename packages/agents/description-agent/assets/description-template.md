# Draft v2 — Description Step Help (User-Facing)

## 1. Что делаем на шаге Description
На этом шаге мы собираем понятное описание продукта и его начальную архитектурную картину.

Результат шага — файл:
`Final_Description.md`.

Важно:
- вам не нужно писать техническим языком;
- можно описывать продукт простыми словами;
- агент сам должен перевести это в более точную архитектурную форму.

## 2. Короткий словарь архитектуры
- `Shell` — оболочка продукта.
  Это часть, через которую пользователь запускает, открывает или подключает остальные части системы.
  Shell не равен всему продукту.

- `Самостоятельная часть продукта` — часть системы, которая может жить, запускаться, обновляться или поставляться отдельно.
  Например: shell, отдельное приложение, отдельный runtime, отдельный сервис, отдельный provider.

- `Cluster` — крупный блок системы, состоящий из нескольких модулей, которые работают вместе как одна подсистема.
  У кластера должен быть один явный внешний вход через cluster facade.

- `Module` — отдельный рабочий блок с одной понятной ролью.
  У модуля должен быть один явный внешний вход через module facade.
  Внутри модуль может состоять:
  - либо из одного микрокласса, который одновременно является facade;
  - либо из facade-класса и нескольких внутренних микроклассов.

- `Facade` — внешний класс блока, единая точка входа снаружи.
  Facade может быть у модуля и у кластера.

- `Microclass` — маленький внутренний класс с одной узкой задачей.
  Микроклассы составляют внутреннюю реализацию модуля и не должны подменять его facade.

- `Boundary` — граница между блоками системы.
  Снаружи блок пересекается только через свой facade, а не напрямую через внутренние классы.

## 3. Что важно заполнить в анкете
Перед `Submit questionnaire` желательно, чтобы в анкете были:
1. Проблема и цель продукта.
2. Целевая аудитория.
3. Ключевые сценарии использования.
4. Тип приложения / платформа.
5. Крупные части системы или очевидные самостоятельные контуры.
6. Ограничения и допущения.
7. Что точно не входит в проект.

Если вы не знаете архитектурные термины, это нормально.
Достаточно описать:
- какие крупные части продукта вы уже видите;
- что работает отдельно;
- что запускает или открывает остальное;
- какие блоки точно должны быть разными.

## 4. Что произойдёт после Submit
После нажатия `Submit questionnaire`:
1. Запустится Description Agent.
2. Он создаст и начнёт уточнять `Final_Description.md`.
3. Вы продолжите обсуждение в диалоге этой же стадии.
4. Агент будет задавать только недостающие вопросы.

Следующая цель после этого шага:
- подготовить такой baseline, из которого потом получится понятная пользователю диаграмма модулей, а не набор случайных технических ярлыков.

## 5. Как лучше работать с агентом
- Отвечайте простыми словами, но как можно точнее по смыслу.
- Если часть продукта живёт отдельно, так и пишите.
- Если не уверены, является ли что-то отдельным блоком, опишите это как гипотезу.
- Проверяйте, что в документе не появилось выдуманных деталей.
- Утверждайте финал только когда вас устраивают сценарии, тип продукта и крупные части системы и важные границы между ними.

## 6. Что НЕ нужно делать на этом шаге
- Не нужно проектировать весь код заранее.
- Не нужно придумывать API и внутренние классы.
- Не нужно раскладывать систему по точным файлам и папкам.
- Не нужно закрывать все архитектурные детали сразу.

## 7. Что должно получиться в итоге
На выходе должен появиться `Final_Description.md`, который:
- объясняет, что это за продукт и зачем он нужен;
- делает продукт понятным пользователю;
- фиксирует тип приложения и его shell как факт или разумную гипотезу;
- показывает крупные части системы и важные границы между ними;
- становится базой для следующих шагов и для понятной пользователю диаграммы модулей.
