# Отчёт: варианты интеграции Google Gemini в CodeAI Hub

## 1. Цель
Текущая реализация модуля `@codeai-hub/gemini-module` завязана на управление готовым CLI `gemini` через stdin/stdout. Это приводит к ряду проблем (нестабильный интерактив, невозможность получить `sessionId` до появления локального json-файла, зависимость от эмуляции терминала). В отчёте собраны альтернативные варианты интеграции, основанные на анализе открытого репозитория [google-gemini/gemini-cli](https://github.com/google-gemini/gemini-cli) и официальных библиотек Gemini API.

## 2. Как устроен официальный `@google/gemini-cli`
- Пакет компилируется из монорепозитория и состоит из двух npm-пакетов:
  - `@google/gemini-cli` — оболочка командной строки (Ink UI, команды, управление конфигом).
  - `@google/gemini-cli-core` — ядро, содержащее всю бизнес-логику (работа с API, управление сессиями, файловыми сервисами, телеметрией, tool-runner’ами и т.д.).
- CLI написан на TypeScript, распространяется как ESM, лицензия — Apache 2.0.
- `@google/gemini-cli-core` зависит от `@google/genai` (официальная Gemini API библиотека) и содержит экспортируемые сущности:
  - `Config`, `WorkspaceContext`, `Storage`, `GeminiChat`, `GeminiRequest`, `CoreToolScheduler`, `ChatRecordingService` и т.д. (см. `dist/src/index.js`).
  - Утилиты работы с файловой системой, git, ignore-паттернами, токенами и т.п.
  - Вспомогательные сервисы: `FileDiscoveryService`, `ShellExecutionService`, инструментальные команды (`ls`, `grep`, `read-file`).
- В `optionalDependencies` указаны сборки `node-pty`, из чего следует, что «родное» ядро умеет работать в псевдо-терминале и само управляет интерактивностью.

Вывод: вместо управляющего скрипта поверх бинарного CLI мы можем использовать те же исходные компоненты, которыми оперирует сам CLI, не теряя функциональность.

## 3. Варианты интеграции

### 3.1 Управлять существующим CLI через PTY
**Идея.** Создать псевдо-терминал (`node-pty`) и вести диалог с `gemini` так же, как это делает native UI.

**Плюсы:**
- Минимальные изменения: достаточно заменить `spawn` → `pty.spawn` и добавить парсер управляющих последовательностей.
- Сохраняем текущий сценарий авторизации (OAuth через CLI) и все фичи CLI (индикаторы, инструменты, `/status`).

**Минусы / риски:**
- Нужно корректно обрабатывать TTY-последовательности (Ink отрисовывает экран, нам придётся чистить ANSI, буферизовать JSON и т.д.).
- CLI остаётся внешним процессом: при обновлениях придётся снова адаптироваться к новым escape-последовательностям.
- Не решает стратегического вопроса «как встроить Gemini на уровне Core/UI» — мы по-прежнему оборачиваем готовый CLI над которым нет сильного контроля.

### 3.2 Использовать `@google/gemini-cli-core` как библиотеку
**Идея.** Подключить `@google/gemini-cli-core` как npm-зависимость, создавать `Config`/`GeminiChat` напрямую и управлять сессией из нашего Node-процесса.

**Что потребуется:**
1. Инициализировать `Config` так же, как это делает CLI (см. `dist/src/gemini.js`):
   - Заполнить `Storage` (пути `~/.gemini`, `tmp/<hash>`), `WorkspaceContext`, приложения.
   - Передать сведения о модельных настройках, фичах, тулзах и т.д.
2. Использовать `GeminiChat`/`LoggingContentGenerator` для запуска беседы. Эти классы уже умеют работать и с потоковыми ответами, и с инструментами.
3. При необходимости подключить `ChatRecordingService`, чтобы получать JSON-файлы чатов (мы можем напрямую читать структуру в памяти).
4. Обеспечить авторизацию: CLI хранит OAuth-токены в `~/.gemini/oauth_creds.json`, core использует `google-auth-library` и тот же storage. Значит, мы можем переиспользовать существующую авторизацию без дополнительных шагов.

**Плюсы:**
- Получаем «родную» логику без shell-интерфейса, можно интегрировать с нашим Core без эмуляции TTY.
- Проще тестировать и обновлять: изменения в официальном core мы будем подхватывать через npm.
- Доступны все вспомогательные сервисы (файловые операции, tool runner), можно переиспользовать их там, где нужно.

**Минусы / сложности:**
- Нужно разобраться, какие зависимости обязательны для минимальной работы (config довольно громоздкий, но можно стартовать с `makeFakeConfig` и постепенно расширять).
- Core — ESM; наш модуль сейчас на CommonJS. Потребуется либо перевод на ESM, либо использование динамического импорта.
- Потянем в проект значительный объём кода: стоит продумать механизм обновлений и «чёрные ящики», чтобы не дублировать функциональность.

### 3.3 Форк/инлайнинг частей CLI
**Идея.** Клонировать оригинальный репозиторий, выделить нужные директории (core + часть UI) и встроить в `packages/Gemini_Module`.

**Плюсы:**
- Полный контроль: мы можем модифицировать core под свои требования (убрать лишний UI, адаптировать API).
- Отсутствие внешних зависимостей (кроме `@google/genai`).

**Минусы:**
- Высокие затраты на поддержку: придётся отслеживать upstream-изменения, мержить фиксы безопасности, синхронизировать версии моделей.
- Весь код придётся содержать в проекте (больше строк → больше проверок, документации и т.д.).
- Форк лишает нас возможности получать обновления CLI «с коробки».

### 3.4 Использование официальных библиотек Gemini API (`@google/genai` и др.)
**Идея.** Обойти CLI и работать напрямую с API через официальный JS SDK.

**Особенности:**
- `@google/genai` — та же библиотека, которую использует `@google/gemini-cli-core`. Поддерживает чаты, генерацию кода, мультимодальные запросы.
- Для доступа требуется API-ключ (AI Studio) или сервисный аккаунт. Подписка Google One (consumer) работает через CLI/OAuth и не выдаёт API-ключ — это ключевое ограничение.

**Плюсы:**
- Полный контроль над протоколом, без ограничений CLI.
- Можно строить архитектуру аналогично Claude/Codex: стабильный REST/WebSocket, собственное хранение истории.

**Минусы:**
- Для пользователей с «домашней» подпиской может не быть доступного API-ключа (нужны либо AI Studio креды, либо Vertex AI).
- Придётся самостоятельно реализовать всю обвязку (делта-стриминг, инструменты, файловый контекст).
- Юридически: нужно убедиться, что использование API соответствует условиям подписки пользователя.

## 4. Сравнение вариантов
| Вариант | Усилие внедрения | Поддержка | Важно знать |
|---------|------------------|-----------|-------------|
| **PTY поверх CLI** | Низкое | Среднее: следим за escape‑последовательностями, но CLI остаётся «чёрным ящиком» | Решает локальные баги, но не даёт гибкости; по-прежнему зависим от внешнего процесса. |
| **`@google/gemini-cli-core` как библиотека** | Среднее | Ниже: обновление через npm, единый источник правды | Требуется создать полноценную конфигурацию, но именно так работает официальный CLI. Позволяет внедрить Gemini нативно. |
| **Форк/инлайнинг CLI** | Высокое | Высокое (нужно мержить upstream) | Полный контроль, но тяжёлая поддержка и рост кода. |
| **`@google/genai` напрямую** | Среднее/высокое | Среднее | Отлично, если у пользователя есть API-ключ; не подходит для сценария «consumer OAuth» без доп. шагов. |

## 5. Рекомендации
1. **Основной кандидат:** интеграция через `@google/gemini-cli-core`. Это даст нам доступ к тем же API, что использует официальное приложение, без необходимости управлять TTY. Пошаговый план: изучить `Config`/`GeminiChat`, собрать минимальную конфигурацию (workspace, storage, модель), убедиться, что авторизация через существующий `oauth_creds.json` работает.
2. **Быстрый фикс при необходимости:** временно можно применить `node-pty` для управления существующим CLI, если потребуется экстренно закрыть регрессию. Но рассматриваем это как временный bridge.
3. **Дальнейшая перспектива:** если продукт будет развиваться в сторону «официальной» интеграции, стоит рассмотреть вариант получения API-ключей (AI Studio / Vertex AI) и перехода на `@google/genai` напрямую.

## 6. Следующие шаги
- Прототип: попробовать создать сессию на основе `@google/gemini-cli-core` (минимальный `Config` + `GeminiChat`) в отдельном sandbox-скрипте.
- Определить, какие компоненты CLI core нужны в MVP (чат без инструментов? с инструментами? запись истории?).
- После успешного прототипа — адаптировать `packages/Gemini_Module` под новую архитектуру (заменить текущий `GeminiSessionManager` на работу с core).
- Параллельно изучить юридические моменты использования API в продукте (CLI работает в рамках пользовательского OAuth, API-ключи — другой режим).
