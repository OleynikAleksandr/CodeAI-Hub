# Workflow Tree UI (SolidWorks-подобная визуализация разработки)

**Status:** Draft (v0.1)
**Updated:** 2026-01-14
**Owner:** Oleksandr + Codex

---

## 1. Зачем нужен Workflow Tree
Цель — дать пользователю UI, который **не позволяет хаотично “скакать” по задачам**, как это делает голый Git, а ведёт разработку как SolidWorks:
- сначала определяются артефакты и ограничения,
- затем создаются “детали” (модули),
- затем задаются “сопряжения” (контракты фасадов),
- затем выполняется “Rebuild” (гейты/сборка),
- затем “Simulation” (тесты/прогоны сценариев).

Workflow Tree становится **единой точкой правды** для состояния инициативы (что сделано, что заблокировано, что устарело после изменений).

---

## 2. Ключевая аналогия SolidWorks → CodeAI Workflow
- **Assembly (Сборка)** → **Repo / Workspace** (верхний уровень всегда весь репозиторий)
- **Configuration** → **Initiative** (контекст текущей задачи внутри repo)
- **Subassembly** → **Cluster** (подсистема/домен)
- **Part** → **Module** (единица ответственности)
- **Mates/Constraints** → **Facade Contracts** (интерфейсы и ограничения интеграции)
- **Rebuild** → **Quality Gates + Build**
- **Simulation** → **Tests / сценарии / перф-метрики**

Архитектурное правило, которое “цементирует” модель:
- **Module имеет единственный публичный вход**: `*facade`.
- Внутри Module — **микро‑классы** (≤300 строк) и частные компоненты.

## 3. Предлагаемый UI (как SolidWorks)
### 3.0. Где живёт “полный SolidWorks” (решение для MVP)
Для MVP **полноценный Workflow Tree** (дерево + детали узла + статусы + “жёсткие” гейты) реализуется в **`project-manager` (CEF)**, потому что там доступен широкий холст как в CAD.

`vscode-webview` и `web-client` на этом этапе **замораживаются** (без попыток дублировать Workflow Tree). Позже, когда Workbench в `project-manager` станет основным, мы отдельно определим, какие **не-дублирующие** функции имеет смысл добавить в узкие поверхности (например: быстрый просмотр статусов, действия рядом с кодом, deep-link в `project-manager` на выбранный узел).

### 3.1. Левый сайдбар: 4 вкладки
1) **Structure** — дерево `Initiative → Clusters → Modules → Facade`.
2) **Feature Tree** — линейная цепочка операций (микро‑задача → commit → rebuild → simulation).
3) **Mates** — связи `facade ↔ facade` (список + мини‑граф).
4) **Quality** — статус гейтов/сборок/тестов (по инициативе и по модулям).

### 3.2. Правая панель: Details + Actions
При выборе узла показывать:
- обязательные выходные артефакты,
- текущие блокеры,
- кнопки действий (создать/открыть/запустить проверку/создать сессию агента),
- историю изменений узла (операции Feature Tree).

## 4. Дерево как “изделие” + “контекст задачи”
Иерархия отображения:
```
Repo (Assembly)
└─ Initiatives (Configurations)
   └─ Initiative: <name> (active)
      ├─ Stages (обязательная последовательность)
      │  ├─ Idea  (Sketch)
      │  ├─ Spec  (Drawing)
      │  ├─ Plan  (Feature plan)
      │  └─ Execute (Parts + Mates + Rebuild)
      ├─ Structure
      │  └─ Clusters → Modules → Facades
      ├─ Mates (facade contracts)
      └─ Quality (rebuild/simulation)
```

Важно: **Stages** — это “каркас”, который делает workflow нехаотичным.

## 5. Статусы узлов (как в SolidWorks)
Минимальный набор статусов для любого узла дерева:
- `TODO` — ещё не начато
- `IN_PROGRESS` — выполняется
- `DONE` — выполнено и валидировано
- `BLOCKED` — заблокировано отсутствующими артефактами/ошибками/контрактами
- `OUTDATED` — было `DONE`, но стало невалидным после изменений (аналог “needs rebuild”)
- `ERROR` — последняя проверка/сборка/тест упали
- `SUPPRESSED` — вне текущего скоупа инициативы (аналог suppression в конфигурациях)

Рекомендуемая визуализация:
- `DONE` — зелёная отметка (ok)
- `OUTDATED` — “needs rebuild” (устарело после изменений)
- `BLOCKED` — заблокировано (не выполнены зависимости)
- `ERROR` — ошибка (последний rebuild/simulation упал)
- `IN_PROGRESS` — выполняется
- `SUPPRESSED` — серым (вне скоупа инициативы)

## 6. “Жёсткие” правила (то, чего нет в Git)
Чтобы дерево вело пользователя, вводим **необходи́мые зависимости**:

### 6.1. Stage-gates (последовательность)
- Нельзя считать `Spec` завершённым, если нет `Idea` артефактов.
- Нельзя считать `Plan` завершённым, если не утверждена архитектура/контракты.
- `Execute` допускается только после `Plan`.

### 6.2. Module-gates (целостность модулей)
- Module не может быть `DONE`, пока не:
  - определён `Facade` (контракт наружу),
  - пройдены гейты для затронутого пакета,
  - пройдены минимальные тесты (если есть).

### 6.3. Mate-gates (сопряжения)
- Любая зависимость между модулями должна быть оформлена как `facade ↔ facade`.
- Если контракт меняется, зависимые модули становятся `OUTDATED`.

## 7. Как Workflow Tree связывается с текущим CodeAI Hub
Минимально-инвазивная стратегия (использует уже существующие сущности):
- **Initiatives/Runs/Stages** уже существуют в `.codeai-hub/initiatives/**`.
- Workflow Tree может строиться из:
  - списка инициатив/ранов,
  - файлов артефактов стадий (Idea/Spec/Plan/Execute),
  - результатов гейтов (последние запуски),
  - карты модулей из репозитория (папки `packages/**`, `src/**`).

## 8. Открытые вопросы (для утверждения UX)

2) **Инициатива ↔ Git branch:** хотим 1:1 как “configuration”, или ветка опциональна?
3) **Mates UI:** достаточно списка контрактов или нужен небольшой граф на первом релизе?
4) **Granularity:** на v0.1 фиксируем `Module + Facade` (без классов), классы добавляем позже.
