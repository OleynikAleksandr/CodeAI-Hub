# Workflow Tree UI (SolidWorks-подобная визуализация разработки)

**Status:** Draft (v0.4)
**Updated:** 2026-01-15
**Owner:** Oleksandr + Codex

---

## 1. Зачем нужен Workflow Tree
Цель — дать пользователю UI, который **не позволяет хаотично “скакать” по задачам**, как это делает голый Git, а ведёт разработку как SolidWorks:
- сначала фиксируется описание и ограничения,
- затем формируется структура (кластеры/модули) и связи,
- затем для каждого модуля делаются спецификация/план/исполнение,
- затем выполняется “Rebuild” (гейты/сборка),
- затем “Simulation” (тесты/прогоны сценариев).

Workflow Tree становится **единой точкой правды** для состояния проекта (workspace):
- что сделано,
- что заблокировано,
- что устарело после правок (needs rebuild).

---

## 2. Ключевая аналогия SolidWorks → CodeAI Workflow
- **Assembly (Сборка)** → **Repo / Workspace** (верхний уровень всегда весь репозиторий)
- **Configuration** → **Workspace Fork** (отдельная версия/песочница проекта для изоляции работы и инструкций)
- **Subassembly** → **Cluster** (подсистема/домен)
- **Part** → **Module** (единица ответственности)
- **Mates/Constraints** → **Facade Contracts** (интерфейсы и ограничения интеграции)
- **Rebuild** → **Quality Gates + Build**
- **Simulation** → **Tests / сценарии / перф-метрики**

Архитектурное правило, которое “цементирует” модель:
- **Module имеет единственный публичный вход**: `*facade`.
- Внутри Module — **микро‑классы** (≤300 строк) и строгая декомпозиция.

## 3. Предлагаемый UI (как SolidWorks)

### 3.0. Где живёт “полный SolidWorks” (решение для MVP)
Для MVP **полноценный Workflow Tree** (дерево + детали узла + статусы + “жёсткие” зависимости) реализуется в **`project-manager` (CEF)**, потому что там доступен широкий холст как в CAD.

`vscode-webview` и `web-client` на этом этапе **замораживаются** (без попыток дублировать Workflow Tree). Позже отдельно определим, какие **не-дублирующие** функции имеет смысл добавить в узкие поверхности.

### 3.1. Левый сайдбар: контекст + дерево
В левой панели **дерево всегда относится к одному выбранному workspace** (как в SolidWorks дерево относится к активному файлу/сборке). Чтобы не “съедать” место списком воркспейсов, используем один контекст‑селектор над деревом:
- **Workspace (active)** — кликом открывается полноэкранный dropdown со списком подключённых воркспейсов и действиями `Add Workspace`, `Fork Workspace` (и позже `New Workspace`).

Ниже контекста отображается **реальное дерево разработки** выбранного проекта (workspace).
Ширина сайдбара подстраивается под текст дерева, но ограничена минимальной/максимальной шириной.

### 3.2. Верхняя панель: палитра инструментов (ключевая SolidWorks-метафора)
Идея: этапы workflow — это **инструменты** (как инструменты/фичи в SolidWorks). Инструмент:
- **контекстный** (зависит от выбранного узла),
- **активируется/блокируется** автоматически по зависимостям,
- при первом запуске **создаёт узел шага** в дереве (если его ещё нет),
- при повторном запуске **открывает тот же шаг** для продолжения/редактирования.

Базовые инструменты (MVP):
- Для `Workspace`/`Cluster`: `Описание` → `Диаграммы` → (переход к структуре модулей)
- Для `Module`: `Spec` → `Plan` → `Execute`

Примечание по терминологии:
- Ранее называли первый шаг `Idea` — переименовываем в `Описание` (чтобы совпадало с фактическим действием пользователя).

### 3.3. Центральная панель: содержимое выбранного узла
Центральный холст делим на две области: **Sessions** (слева) и **Artifacts** (справа). Между ними — вертикальный ресайзер с сохранением пропорций. Архитектурно держим возможность расширить раскладку до трёх панелей.
Правило поведения:
- Клик по узлу **шага** (например, `Описание`) открывает **состояние шага**:
  - если шаг ещё не начат — анкета/формы ввода + запуск новой сессии,
  - если шаг уже делался — тот же диалог/сессии с возможностью “Edit / Continue”.
- Клик по узлу **артефакта** открывает текст/визуализацию артефакта.
- Клик по узлу **сессии** открывает полный диалог с агентом (контекст шага, сообщения, вложения, результаты).

Под основной зоной располагается **нижняя панель** для служебной информации и контекста (status bar).

### 3.4. Ожидаемый пользовательский сценарий (MVP)
Цель: пользователь всегда получает понятный “следующий шаг”, как в SolidWorks.

Сценарий для workspace‑проекта (мульти‑модульность):
1) Пользователь добавляет workspace в Project Manager (или выбирает уже добавленный).
2) Система активирует только инструмент `Описание`.
3) Пользователь кликает `Описание` → открывается анкета; часть полей уже предзаполнена данными проекта (workspace).
4) Пользователь дозаполняет анкету и отправляет агенту → создаётся `Session`.
5) В результате сессии агент формирует обязательные артефакты шага `Описание` (см. раздел “Условия разблокировки”).
6) После появления артефактов система активирует инструмент `Диаграммы`.
7) Пользователь кликает `Диаграммы` → агент создаёт `modules-diagram.mmd` и `facades-graph.mmd`.
8) Система сразу материализует в дереве все `Cluster/Module` из диаграммы как Draft‑узлы (`TODO`).
9) При выборе любого `Module` активируется инструмент `Spec`, далее `Plan`. Инструменты строго разблокируются по условиям.

## 4. Дерево: узлы, шаги, артефакты и сессии

### 4.1. Типы узлов (MVP)
- `Workspace` (проект / верхний уровень дерева)
- `Cluster`
- `Module`
- `Step` (шаг: `Описание` | `Диаграммы` | `Spec` | `Plan` | `Execute`)
- `Artifact` (файл/результат шага)
- `Session` (диалог с агентом)

### 4.2. Пример дерева (workspace‑проект с кластерами)
```
Workspace: App
├─ Описание (Step)
│  ├─ Artifact: questionnaire.md
│  │  └─ Session: 001 (create)
│  ├─ Artifact: description.md
│  │  ├─ Session: 001 (create)
│  │  └─ Session: 004 (edit)
│  └─ Artifact: virtual-simulation.md
│     └─ Session: 001 (create)
├─ Диаграммы (Step)
│  ├─ Artifact: modules-diagram.mmd
│  │  └─ Session: 002 (create)
│  └─ Artifact: facades-graph.mmd
│     └─ Session: 002 (create)
├─ Cluster: Auth
│  ├─ Описание (Step)
│  ├─ Диаграммы (Step)
│  └─ Module: auth-token
│     ├─ Spec (Step)
│     ├─ Plan (Step)
│     └─ Execute (Step)
└─ Cluster: Billing
   └─ ...
```

### 4.3. Пример дерева (workspace‑проект без кластеров)
Если кластеры не нужны, модули становятся прямыми дочерними узлами workspace.

Для компактности узлы `Cluster`/`Module` поддерживают сворачивание/разворачивание (внутри — шаги, артефакты и сессии).

### 4.4. Сессии как “полная история” (позиция)
Сессии — **видимые узлы дерева**. Дерево может разрастаться — это нормально: пользователь видит все шаги и историю.

Рекомендованная модель отображения на MVP:
- `Session` отображается как дочерний узел под `Artifact`.
- Один `Session` может быть показан под несколькими `Artifact` как “ссылка” (один и тот же ID), если сессия породила/изменила несколько артефактов.

## 5. Статусы узлов (как в SolidWorks)
Минимальный набор статусов для любого узла дерева:
- `TODO` — ещё не начато
- `IN_PROGRESS` — выполняется
- `DONE` — выполнено и валидировано
- `BLOCKED` — заблокировано отсутствующими артефактами/ошибками/контрактами
- `OUTDATED` — было `DONE`, но стало невалидным после изменений (аналог “needs rebuild”)
- `ERROR` — последняя проверка/сборка/тест упали
- `SUPPRESSED` — вне текущего скоупа проекта (workspace) (аналог suppression в конфигурациях)

### 5.1. Визуальная шкала (MVP)
- `TODO` (“Draft/только создан”) — серый
- `IN_PROGRESS` — оранжевый (тусклый)
- `DONE` — зелёный
- `OUTDATED` — жёлтый “needs rebuild”
- `ERROR` / “требует ревизии” — красный
- `SUPPRESSED` — серый (приглушённый)

## 6. “Жёсткие” правила (то, чего нет в Git)

### 6.1. Активация инструментов (зависимости)
Инструмент активен, только если выполнены его предусловия.

MVP‑правило: **Strict CAD Flow** — никаких перескоков шагов/инструментов. Если предусловия не выполнены, инструмент заблокирован.

Примеры (MVP):
- Для `Workspace/Cluster`:
  - `Диаграммы` активен только если у шага `Описание` есть обязательные артефакты.
- Для `Module`:
  - `Plan` активен только если есть артефакты `Spec`.
  - `Execute` активен только если есть артефакты `Plan`.

### 6.2. Источник правды (anti-chaos rule)
**Источник правды — предыдущие шаги, которые сформировали структуру/сущности.**

Правила:
- Если сущность “появилась” из шага (например, список модулей из `Диаграммы`), то добавлять/удалять/переименовывать её можно **только через этот шаг**.
- Нельзя “создать модуль вручную” в дереве внутри workspace/кластера в обход шага, который сформировал список модулей.

### 6.3. Автоматическая генерация структуры из артефактов
После выполнения шага `Диаграммы` система строит/обновляет ветку `Clusters/Modules` как производную:
- материализует все `Cluster/Module` из диаграммы сразу (статус `TODO` и визуальный режим Draft),
- поддерживает добавление/удаление/переименование только через этот же шаг `Диаграммы` (а не вручную в дереве),
- при несовпадении имён/ID — подсвечивает конфликт и предлагает “Resolve”.

Удаление:
- удалённые из диаграммы `Cluster/Module` удаляются физически только после явных предупреждений (включая список затронутых зависимостей/артефактов),
- после удаления выполняется пересчёт дерева и связей; проблемные узлы помечаются `ERROR`/`BLOCKED` и подсвечиваются красным,
- при наличии проблем, которые система не может разрешить автоматически, создаётся системный артефакт‑отчёт со списком требуемых действий (например: `dependency-problems.md`).

### 6.4. OUTDATED как “needs rebuild”
Редактирование любого узла может повлиять на другие узлы — **не по “глубине дерева”**, а по **графу зависимостей** (как mates/constraints в CAD). Узел, который выглядит “последним” в дереве, может быть ключевой зависимостью для многих других модулей.

Поэтому правило формулируется так:
- Любой `Edit` запускает **impact analysis** (пересчёт влияния изменений).
- `OUTDATED` получают **только реально затронутые** узлы (по зависимостям), остальные остаются `DONE`.

Impact analysis (MVP):
1) **Детерминированный слой**:
   - структурные зависимости (узлы, материализованные из `Диаграммы`),
   - контрактные зависимости (`facade ↔ facade`),
   - инфраструктурные зависимости (build/gates, общие ресурсы — по мере появления).
2) **AI‑слой (опционально, но рекомендуется)**: агент делает первичную оценку последствий и помогает сформировать список требуемых изменений/ревизий.

Результаты анализа:
- затронутые узлы помечаются `OUTDATED` (и блокируют инструменты, пока не пройдут нужные шаги заново),
- при явном конфликте/невозможности связать зависимости — `ERROR`/`BLOCKED`,
- если система не может определить влияние автоматически — создаётся отчёт‑артефакт (например: `impact-report.md`) и узлы остаются `OUTDATED` до ручной ревизии.

Примеры (MVP):
- Изменили `modules-diagram.mmd` → `OUTDATED` получают только реально затронутые `Cluster/Module` (изменённые/удалённые/переименованные) и их зависимые по контрактам.
- Изменили `facade-spec.md` модуля → `OUTDATED` получают модули, которые зависят от этого фасада (incoming зависимости).
- Изменили внутреннюю реализацию модуля без изменения фасада → чаще всего затрагивается только этот модуль (его `Spec/Plan/Execute`).

### 6.5. Условия разблокировки инструментов (MVP, Strict)
Для MVP считаем, что “готовность шага” = наличие **обязательных артефактов** и отсутствие `ERROR` у шага.

`Workspace/Cluster`:
- `Описание` → `DONE`, когда созданы 2 артефакта:
  1) `description.md` (цель, scope/out-of-scope, DoD/критерии успеха)
  2) `virtual-simulation.md` (виртуальная симуляция/прогон сценариев на уровне описания)
  Разблокирует `Диаграммы`.
- `Диаграммы` → `DONE`, когда созданы 2 артефакта:
  1) `modules-diagram.mmd` (кластеры/модули + связи, стабильные ID)
  2) `facades-graph.mmd` (фасады + связи/контракты)
  Разблокирует материализацию `Cluster/Module` узлов (Draft=`TODO`).

`Module`:
- `Spec` → `DONE`, когда созданы 2 артефакта:
  1) `module-spec.md` (границы ответственности, зависимости, требования)
  2) `facade-spec.md` (контракт фасада: вход/выход, ошибки, версии/совместимость)
  Разблокирует `Plan`.
- `Plan` → `DONE`, когда создан `plan.md` (микро‑задачи ≤3 файлов, обязательный пункт `Git Commit` после каждой подзадачи, гейты, таргетные сборки).
  Разблокирует `Execute`.
- `Execute` (оркестрация выполнения) — отдельный “саб‑кластер” по сложности. На MVP фиксируем только входной контракт: **вход = `plan.md`**. Детализацию шагов/инструментов/артефактов `Execute` оформляем отдельным документом, когда дойдём до этапа реализации.

## 7. Как Workflow Tree связывается с текущим CodeAI Hub
Минимально-инвазивная стратегия (использует уже существующие сущности):
- Workflow/сессии/артефакты уже существуют в `.codeai-hub/**` (конкретная структура может меняться, UI не должен “протекать” внутренними сущностями).
- Workflow Tree строится из:
  - списка сессий/шагов,
  - файлов артефактов шагов,
  - результатов гейтов (последние запуски),
  - структуры модулей из репозитория (папки `packages/**`, `src/**`).

## 8. Открытые вопросы (для утверждения UX)
1) **Workspace Fork ↔ Git:** хотим ли делать fork как git clone/новая папка, или как `git worktree`/ветка в текущем checkout?
2) **Валидация артефактов:** достаточно “файл существует и не пустой”, или вводим минимальную схему (frontmatter/JSON) уже в MVP?
3) **Impact analysis:** какие случаи считаем полностью детерминированными (граф/дифф), а где обязательно подключаем AI‑агента?
