# SolidWorks Flow — Node Session Continuity (Architecture)

**Status:** Draft
**Updated:** 2026-02-03
**Owner:** Oleksandr + Codex

---

## 1) Problem

В “SolidWorks‑подобном” Workflow Tree пользователь ожидает **бесконечную** сессию внутри активного узла: он может обсуждать артефакт, делать паузы, закрывать приложение и возвращаться позже, не думая о лимите контекстного окна провайдера.

Однако реальные провайдерные сессии (threads) имеют ограниченное контекстное окно. При исчерпании бюджета система должна **автоматически**:
- завершить текущий provider‑segment;
- открыть новый provider‑segment;
- восстановить контекст работы так, чтобы для пользователя это выглядело как продолжение того же диалога в том же узле.

Критично: переносить “весь диалог” нельзя — это шум и гарантированное сжигание контекстного окна.

---

## 2) Goals

1. **Infinite UX:** пользователь не замечает сегментацию по provider thread.
2. **Node‑aware:** восстановление контекста привязано к текущему узлу дерева и активной роли агента.
3. **Zero core persistence for reports:** Core **не пишет** и **не сохраняет** continuity‑отчёты; этим занимается агент.
4. **Minimal context:** в новый segment попадает только то, что нужно для продолжения процесса, без переписки и без больших вставок.
5. **UI transparency:** во время rollover пользователь видит короткий системный индикатор и не может “потерять” ввод.

---

## 3) Non‑Goals

- Хранить или подсовывать агенту полный лог диалога.
- Делать Core “источником правды” по содержимому отчётов/артефактов.
- Делать единый одинаковый набор инструкций для всех агентов (prompt собирается узлом).

---

## 4) Terms

- **Node (узел):** единица работы в дереве (пример: `Description → Final Description`).
- **Role/Agent:** конкретная роль в узле (пример: `Reviewer`).
- **Provider segment:** один реальный provider thread/sessionId у Claude/Codex/Gemini.
- **Rollover / Handoff:** автоматическое переключение на новый provider segment внутри того же узла.
- **Continuity Report:** короткий отчёт для бесшовного продолжения работы внутри узла.

Важно: **Node bootstrap** (переход на другой узел дерева) ≠ Continuity. При bootstrap поднимается другой агент/роль и используется другой prompt‑шаблон.

---

## 5) Key Decisions

### 5.1 Отчёт пишет и читает агент
- Агент **сам** сохраняет continuity‑отчёт по указанному пути.
- Агент **сам** читает предыдущий отчёт по пути (в новом segment).
- Core только:
  - принимает решение о rollover (по token budget);
  - отправляет агенту инструкцию “как составить отчёт + куда сохранить”;
  - watcher’ом фиксирует появление файла отчёта;
  - после появления файла закрывает старый segment и открывает новый.

### 5.2 Отчёт — единственный “мост” между сегментами
Никакие “скрытые логи” и “полная история чата” в контекст нового сегмента не добавляются.
Если что‑то важно для продолжения процесса, агент обязан зафиксировать это в отчёте.

### 5.3 UI должен защитить пользователя от потери ввода
В момент rollover:
- показать временный баннер/тост “Контекст исчерпан — готовлю продолжение…” + индикатор;
- запретить отправку сообщений (или ставить в очередь до готовности нового segment);
- убрать индикатор сразу после готовности нового segment.

## 6) Flow (Rollover внутри узла)

### 6.1 High‑level шаги
1. **Turn completed:** пользователь видит ответ агента.
2. **Threshold reached:** Core решает, что нужен rollover (по tokenUsage).
3. **Create report:** Core отправляет агенту внутреннюю инструкцию:
   - шаблон отчёта (зависит от типа узла: doc vs code);
   - точный путь для сохранения;
   - ограничения по размеру и запреты (без переписки/без вставок артефактов).
4. **Watcher:** Core ждёт появления финального файла отчёта в целевой папке.
5. **Switch segment:** Core закрывает старый provider segment и создаёт новый.
6. **Resume:** Core стартует новый segment и первым сообщением отправляет:
   - стандартный prompt‑шаблон узла/роли;
   - короткую инструкцию “прочти последний отчёт по пути X и продолжай”.

### 6.2 Надёжность watcher’а
Рекомендуется атомарная запись отчёта агентом:
- запись в `report.tmp.md`;
- затем `rename` → `report.md`.
Core watcher реагирует только на финальное имя `report.md`.

---

## 7) Report Storage Layout (рекомендуемая схема)

Continuity‑отчёты хранятся рядом с артефактами узла и остаются навсегда (пользователь может вернуться к узлу в любой момент).

Рекомендация по путям (пример):
- `<workspaceRoot>/.codeai-hub/<workspaceSlug>/flow/nodes/<nodeId>/continuity/reports/<ISO_TIMESTAMP>-<role>-<provider>.md`

Core:
- не создаёт папки;
- не пишет файлы;
- только watcher’ом ждёт появления файла по заранее объявленному пути.

---

## 8) Failure Modes

1. **Отчёт не появился** (таймаут):
   - UI показывает сообщение “Не удалось подготовить продолжение”; предложить “Повторить” / “Пауза”.
2. **Отчёт слишком большой или не по шаблону**:
   - Core повторно просит агента пересобрать отчёт с более жёсткими лимитами.
3. **Аварийное завершение процесса**:
   - часть контекста может потеряться; система должна быть честной в UI (“сессия прервалась”).

---

## 9) Notes

- Prompt‑шаблоны (bootstrap) должны быть узло‑специфичными и отправляться Core “от лица пользователя” как стартовое сообщение.
- Continuity‑инструкция — короткая и узконаправленная: “составь отчёт” или “прочти отчёт”.
