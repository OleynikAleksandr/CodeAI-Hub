# Virtual Simulation — Workflow Step Contract (SSOT)

**Status:** Active SSOT
**Updated:** 2026-03-01
**Owner:** Oleksandr + Codex

---

## 1) Назначение (зачем нужен шаг)

Шаг **Virtual Simulation** фиксирует *минимальный* сценарный контракт поведения системы.

Он нужен, чтобы:
- не требовать от пользователя «придумать всё заранее»;
- но всё равно иметь 2–4 проверяемых сценария, которые *ведут* архитектуру и реализацию;
- заранее определить «что считаем успехом», «какой сигнал/эффект ожидаем», «как это проверить/наблюдать»;
- узаконить итеративность: документ **живой** и редактируется бесконечно (как другие resume-сессии workflow).

Virtual Simulation **не** является дизайн‑документом UI и **не** требует готового фронтенда.
UI описывается *концептуально*: экран/панель → действие → состояние/сообщение/ошибка.

---

## 2) Позиция в workflow (порядок)

Канонический порядок шагов:

1) `Description` (финал: `Final_Description.md`)
2) `Virtual Simulation` (результат: `virtual-simulation.md`)
3) `Diagram Modules` (результат: `modules-diagram.mmd`)
4) `Diagram Facades` (результат: `facades-graph.mmd`)

На момент выполнения Virtual Simulation диаграмм **ещё нет**.

---

## 3) Входы и выходы (SSOT)

### 3.1 Вход (обязательный)
- `.codeai-hub/<workspaceSlug>/description/Final_Description.md` — источник истины для Virtual Simulation.
- Ожидается, что `Final_Description.md` уже содержит базовые сценарии, ограничения и ключевые термины (это снижает стартовую неопределённость для этого шага).

### 3.2 Вход (опциональный)
- Любые дополнительные документы/заметки, которые пользователь добавляет в диалог с агентом (текстом или файлами).
  - Примеры: требования, гипотезы, списки функций, ограничения, наброски UX, ссылки.

### 3.3 Выход (каноничный артефакт шага)
- `.codeai-hub/<workspaceSlug>/virtual_simulation/virtual-simulation.md`

## 4) UX: ручной запуск + редактирование

### 4.1 Ручной запуск (manual)
Пользователь запускает шаг вручную: кнопка **VIRTUAL SIMULATION** в верхнем тулбаре Project Manager.

Сразу после выбора/запуска шага в правой части (справа от UI сессии) показывается информационный блок **до появления артефакта**.
Этот блок **не блокирует** запуск сессии агента и может висеть долго.

**Текст блока (user-facing):**

> Здесь мы фиксируем 2–4 сценария: действие → реакция UI → что должно произойти в системе → как проверить.
>
> Вы можете править `virtual-simulation.md` вручную в редакторе или через агента (он задаст до 3 уточнений и обновит файл после вашего “ОК”).
>
> Вы также можете прямо в диалоге:
> - задать вопросы;
> - приложить любые заранее подготовленные документы (или вставить текст), чтобы агент учёл их в следующей версии.
>
> Любые изменения пометят следующие шаги как требующие синхронизации.

### 4.2 Два способа редактирования
1) **Вручную (manual edit):** пользователь открывает и редактирует `.codeai-hub/<workspaceSlug>/virtual_simulation/virtual-simulation.md` как обычный Markdown.
2) **Через агента (agent edit):** пользователь пишет в диалог “что изменить/добавить”; агент перечитывает текущий документ и делает upsert **только после явного подтверждения**.

Оба способа считаются равноправными.

---

## 5) Definition of Done (DoD) для шага

Шаг **Virtual Simulation** считается `DONE`, если:
- `virtual-simulation.md` существует по каноничному пути;
- документ соблюдает минимальную структуру (см. шаблон ниже);
- описаны **2–4 сценария**;
- для каждого сценария есть критерии успеха и понятный способ проверки.

Если часть секций не применима (например, нет UI) — это должно быть написано явно (“Не применимо”).

---

## 6) OUTDATED / синхронизация с downstream

Инвариант: артефакты *живые*.

- Изменение `Final_Description.md` **после** того как Virtual Simulation была сделана → Virtual Simulation получает `OUTDATED`.
- Изменение `virtual-simulation.md` → downstream шаги (Diagram Modules/Facades) получают `OUTDATED` (или остаются `BLOCKED`, если ещё не начинались).

Цель: нормализовать цикл «2 шага вперёд, 1 назад».

## 7) Контракт поведения агента (Virtual Simulation Agent)

### 7.1 Вход при старте шага
Агент обязан:
1) Прочитать `Final_Description.md`.
2) Сформулировать до **3** уточняющих вопросов, которые повышают качество сценариев.
3) Дождаться явного подтверждения пользователя («ОК/утверждаю/approve»).
4) Записать `virtual-simulation.md` по целевому пути (relative + absolute), который указан системой.

### 7.2 Бесконечная сессия (resume workflow)
Сессия шага Virtual Simulation **не одноразовая**:
- пользователь может возвращаться к обсуждению и правкам в любой момент;
- агент делает изменения как upsert (перезапись полного файла) после явного подтверждения;
- агент обязан перечитывать актуальную версию `virtual-simulation.md` перед правками.

### 7.3 Важные ограничения
- Агент не должен требовать «готового UI». UI — только концептуально.
- Агент не должен пытаться “дописать весь мир”: на первом проходе достаточно минимального набора сценариев.

> Примечание: файлы в `~/.codeai-hub/templates/...` генерируются/синхронизируются из кода Core (bundled templates). Здесь фиксируется *каноническое содержимое*.

### 8.1 `virtual-simulation-prompt.md` (SSOT текста инструкции)

```md
# System Prompt — Virtual Simulation Agent (file-first)

Ты — **Virtual Simulation Agent** (стадия `virtual_simulation`).

## Цель
Подготовить артефакт стадии: `virtual-simulation.md`.

## Входные данные (SSOT)
- `Final_Description.md` (путь дан в сообщении).
- Дополнительные документы/заметки пользователя (если он их приложил или вставил в диалог).
- Шаблон `virtual-simulation-template.md` (если дан путь и файл доступен для чтения).

## Правила работы
- Никаких JSON.
- Не выдумывай факты: опирайся на `Final_Description.md` и реально прочитанные файлы.
- UI описывай **концептуально** (экран/панель → действие → состояние/сообщение/ошибка). Не делай wireframes.
- Если в сообщении указаны пути к файлам (relative/absolute) — **прочитай их напрямую** средствами среды (доступ к файловой системе).

## Процесс
1) Прочитай `Final_Description.md`.
2) Задай до **3** уточняющих вопросов (если это повысит качество сценариев).
3) Дождись явного подтверждения («ОК/утверждаю/approve»).
4) Запиши `virtual-simulation.md` по целевому пути (relative + absolute), который указан в сообщении.

## Бесконечная сессия
- Пользователь может возвращаться к правкам в любой момент.
- Перед каждой правкой перечитывай текущий `virtual-simulation.md`.
- Любые изменения выполняй только после явного подтверждения.

## Ожидаемое содержание
- Следуй шаблону, если он доступен.
- Сценарии должны быть практичными: предусловия → шаги → ожидаемые результаты → критерии успеха.
- Обязательно добавь: UI ↔ Core события, логи/телеметрию, риски, must-pass проверки.
```

## 9) Примечания к реализации (для следующего этапа, не часть SSOT)

- При ручном запуске шага PM должен запускать бесконечную сессию агента и параллельно показывать информационный блок до появления `virtual-simulation.md`.
- В инструкциях, которые Core отправляет агенту, должен быть указан путь к `Final_Description.md` (relative + absolute) и целевой путь `virtual-simulation.md`.
- Минимальная валидация артефакта должна быть детерминированной (например, заголовок `# Virtual Simulation:` + базовые секции), чтобы UI мог показывать `ERROR` и предлагать «Исправить с агентом».
