# Virtual Simulation — Workflow Step Contract (SSOT)

**Status:** Active SSOT
**Updated:** 2026-03-19
**Owner:** Oleksandr + Codex

---

## 1) Назначение (зачем нужен шаг)

Шаг **Virtual Simulation** фиксирует *минимальный* сценарный контракт поведения системы.

Он нужен, чтобы:
- не требовать от пользователя «придумать всё заранее»;
- но всё равно иметь достаточное количество проверяемых сценариев, которые *ведут* архитектуру и реализацию;
- заранее определить «что считаем успехом», «какой сигнал/эффект ожидаем», «как это проверить/наблюдать»;
- узаконить итеративность: документ **живой** и редактируется бесконечно (как другие resume-сессии workflow).

Virtual Simulation **не** является дизайн‑документом UI и **не** требует готового фронтенда.
UI описывается *концептуально*: экран/панель → действие → состояние/сообщение/ошибка.

---

## 2) Позиция в workflow (порядок)

Канонический порядок шагов:

1) `Description` (финал: `Final_Description.md`)
2) `Virtual Simulation` (результат: `virtual-simulation.md`)
3) `Diagram Modules` (результат: `product-parts.index.md` + `product-parts/<part-id>.md` + diagram sidecar)

На момент выполнения Virtual Simulation диаграмм **ещё нет**.

---

## 3) Входы и выходы (SSOT)

### 3.1 Вход (обязательный)
- `.codeai-hub/<workspaceSlug>/description/Final_Description.md` — источник истины для Virtual Simulation.
- Ожидается, что `Final_Description.md` уже содержит базовые сценарии, ограничения и ключевые термины.

### 3.2 Вход (опциональный)
- Любые дополнительные документы/заметки, которые пользователь добавляет в диалог с агентом (текстом или файлами).

### 3.3 Выход (каноничный артефакт шага)
- `.codeai-hub/<workspaceSlug>/virtual_simulation/virtual-simulation.md`

---

## 4) UX: ручной запуск + редактирование

### 4.1 Ручной запуск (manual)
Пользователь запускает шаг вручную: кнопка **VIRTUAL SIMULATION** в верхнем тулбаре Project Manager.

Сразу после запуска в правой части (справа от UI сессии) показывается информационный блок **до появления артефакта**.
Этот блок **не блокирует** запуск сессии агента и может висеть долго.

**Текст блока (user-facing):**

> Здесь мы фиксируем ключевые сценарии: действие → реакция UI → что должно произойти в системе → как проверить.
>
> Вы можете править `virtual-simulation.md` вручную в редакторе или через агента (он задаст до 3 уточнений и обновит файл после вашего “ОК”).
>
> Вы также можете прямо в диалоге:
> - задать вопросы;
> - приложить любые заранее подготовленные документы (или вставить текст), чтобы агент учёл их в следующей версии.
>
> Любые изменения пометят следующие шаги как требующие синхронизации.

### 4.2 Два способа редактирования
1) **Вручную (manual edit):** пользователь открывает и редактирует `.codeai-hub/<workspaceSlug>/virtual_simulation/virtual-simulation.md` как обычный Markdown.
2) **Через агента (agent edit):** пользователь пишет в диалог “что изменить/добавить”; агент перечитывает текущий документ и делает upsert **только после явного подтверждения**.

Оба способа считаются равноправными.

---

## 5) Definition of Done (DoD) для шага

Шаг **Virtual Simulation** считается `DONE`, если:
- `virtual-simulation.md` существует по каноничному пути;
- документ соблюдает минимальные инварианты качества (см. раздел 8.2);
- описаны ключевые сценарии в количестве, достаточном для покрытия продукта;
- для каждого сценария есть критерии успеха и понятный способ проверки.

Если часть секций не применима (например, нет UI) — это должно быть написано явно (“Не применимо”).

---

## 6) OUTDATED / синхронизация с downstream

Инвариант: артефакты *живые*.

- Изменение `Final_Description.md` **после** того как Virtual Simulation была сделана → Virtual Simulation получает `OUTDATED`.
- Изменение `virtual-simulation.md` → downstream шаг (Diagram Modules) получает `OUTDATED` (или остаётся `BLOCKED`, если ещё не начинался).

Цель: нормализовать цикл «2 шага вперёд, 1 назад».

---

## 7) Контракт поведения агента (Virtual Simulation Agent)

### 7.1 Вход при старте шага
Агент обязан:
1) Прочитать `Final_Description.md`.
2) Сформулировать до **3** уточняющих вопросов, которые повышают качество сценариев.
3) Дождаться явного подтверждения пользователя (`ОК`/`утверждаю`/`approve`).
4) Записать `virtual-simulation.md` по целевому пути (relative + absolute), который указан системой.

### 7.2 Бесконечная сессия (resume workflow)
Сессия шага Virtual Simulation **не одноразовая**:
- пользователь может возвращаться к обсуждению и правкам в любой момент;
- агент делает изменения как upsert (перезапись полного файла) после явного подтверждения;
- агент обязан перечитывать актуальную версию `virtual-simulation.md` перед правками.

### 7.3 Важные ограничения
- Агент не должен требовать «готового UI». UI — только концептуально.
- Агент не должен пытаться “дописать весь мир”: на первом проходе достаточно минимального набора сценариев.

## 8) Bundled prompt contract (`~/.codeai-hub/templates/virtual_simulation/`)

> Примечание: файлы в `~/.codeai-hub/templates/...` генерируются/синхронизируются из кода Core. Для шага `Virtual Simulation` используется **prompt-only** модель: отдельный artifact template не поставляется и не отправляется агенту.

### 8.1 `virtual-simulation-prompt.md` (SSOT текста инструкции)

```md
# Virtual Simulation Agent Instructions

## 1) Контекст: зачем workflow и что такое шаг Virtual Simulation
CodeAI Hub превращает идею в цепочку артефактов, которые последовательно уточняются и используются следующими агентами.

Шаг `Virtual Simulation` идёт сразу после `Description` и нужен, чтобы перевести продуктовое описание в рабочие сценарии поведения системы: кто и зачем действует, что делает, что должно произойти, и по каким признакам это считается успешным.

Важно: `virtual-simulation.md` не является «документом ради документа». Он должен, вместе с `Final_Description.md`, дать достаточно точный и непротиворечивый вход для двух следующих шагов:
- `Diagram Modules` (выделение модулей, зон ответственности, зависимостей).

## 2) Среда работы агента, роль и артефакт
Ты — Virtual Simulation Agent стадии `virtual_simulation`.

Ты работаешь в runtime-сессии Project Manager и имеешь доступ к файловой системе workspace. Если в сообщении указаны пути к файлам (relative/absolute), ты обязан читать их напрямую.

Вход:
- `.codeai-hub/<workspaceSlug>/description/Final_Description.md` (обязательный SSOT-вход);
- дополнительные материалы пользователя (если они реально прочитаны);
- текущая версия `.codeai-hub/<workspaceSlug>/virtual_simulation/virtual-simulation.md` (если файл уже существует).

Выход (SSOT):
- `.codeai-hub/<workspaceSlug>/virtual_simulation/virtual-simulation.md`

Критическое правило: отдельный markdown-template для этого шага не используется. Ты формируешь структуру документа самостоятельно, исходя из содержания `Final_Description.md` и цели шага.

## 3) Процесс работы (file-first)
Повторяй цикл:
1. Прочитай `Final_Description.md` и выдели сценарии/ограничения, которые критичны для проектирования.
2. Сформируй или обнови `virtual-simulation.md` в файле.
3. В чате дай короткий отчёт, что изменилось и какие 1–3 уточнения действительно влияют на качество следующего шага.
4. Вопросы задавай только если они повышают качество артефакта; максимум 3 вопроса за итерацию.
5. Перед каждой новой правкой перечитывай актуальную версию `virtual-simulation.md`.

Не публикуй полный текст `virtual-simulation.md` в чат, если пользователь явно не попросил.

## 4) Что должен дать артефакт для следующих шагов
`virtual-simulation.md` должен быть достаточным, чтобы следующий агент смог:
- выделить кандидатов в модули без выдумывания бизнес-логики;
- понять границы ответственности и ключевые точки взаимодействия;
- зафиксировать, где нужны фасады и какие типы контрактов между ними ожидаются (команда, событие, запрос-ответ, асинхронный процесс);
- проследить связь: сценарий -> системная реакция -> ожидаемый проверяемый результат.

Минимальные инварианты качества:
- в документе есть заголовок вида `# Virtual Simulation: ...`;
- описаны ключевые сценарии в количестве, достаточном для покрытия продукта;
- каждый сценарий содержит: актор/цель, последовательность действий, ожидаемый результат, критерий успеха;
- зафиксированы ограничения и допущения, которые влияют на архитектурные решения;
- отмечены открытые вопросы, если они не блокируют переход дальше.

## 5) Ограничения
- Язык: русский.
- Никаких JSON-ответов.
- Не выдумывай факты: если данных нет, зафиксируй допущение или задай уточнение.
- Не прыгай в детальную реализацию классов/методов: это не шаг спецификаций.
- Не превращай шаг в UML/mermaid-диаграммы: цель шага — сценарный артефакт, пригодный для построения диаграмм на следующих этапах.

## 6) Критерий готовности шага
Шаг считается готовым, когда пользователь явно подтвердил (`ОК` / `утверждаю` / `approve`), а `virtual-simulation.md`:
- содержит связный сценарный baseline без внутренних противоречий;
- покрывает продуктовую суть из `Final_Description.md` без потери ключевых ограничений;
- даёт следующему агенту достаточную основу для построения staged product-part артефактов без переписывания контекста с нуля.
```

### 8.2 Минимальные инварианты артефакта (без жёсткого template)

`virtual-simulation.md` валиден для workflow, если:
- есть заголовок `# Virtual Simulation: ...`;
- присутствует хотя бы один сценарий (`## Сценарий N` / `## Scenario N`), а общее количество достаточно для покрытия продукта;
- сценарии дают downstream-полезный материал (актор/цель -> действия -> ожидаемые результаты -> критерии успеха);
- сохранены ограничения/допущения, влияющие на архитектуру.

Отдельный файл `virtual-simulation-template.md` в runtime **не используется**.

---

## 9) Примечания к реализации (для следующего этапа, не часть SSOT)

- При ручном запуске шага PM должен запускать бесконечную сессию агента и параллельно показывать информационный блок до появления `virtual-simulation.md`.
- В инструкциях, которые Core отправляет агенту, должен быть указан путь к `Final_Description.md` (relative + absolute) и целевой путь `virtual-simulation.md`.
- Минимальная валидация артефакта должна быть детерминированной (заголовок `# Virtual Simulation:` + хотя бы один сценарий), чтобы UI мог показывать `ERROR` и предлагать «Исправить с агентом».
