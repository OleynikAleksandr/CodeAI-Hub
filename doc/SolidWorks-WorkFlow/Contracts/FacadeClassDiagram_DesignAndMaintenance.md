**Status:** Active (process)
**Updated:** 2026-03-19 (release 1.1.749)
**Owner:** Oleksandr + Codex
**Validated for:** 1.1.749
**Validated on:** 2026-03-19


## Реальный пример: спиннер загрузки UI Сессии (v1.1.622)

**Симптом:** после `Submit questionnaire` (Description pre-submit -> runtime) в зоне UI Сессии слева 8–10 секунд ничего не происходит — висит карточка `Create your first session…`, из‑за чего кажется, что PM завис.

**Ключевое наблюдение (не гадать):** эту карточку рисует `EmptyState` **только** когда `SessionView` видит `sessions.length === 0`. Значит спиннер/статус ожидания обязан жить **в том же месте**, а не «где-то рядом» и не в другом контуре.

**Почему прошлые попытки не работали:** pending‑сигнал привязывался к событию/моменту типа `session:created` (или другому «раннему» факту), который может происходить **до** того, как список `sessions` реально гидратится/становится видимым в UI. В итоге условие `sessions.length === 0` продолжало быть истинным, а UI оставался на старой карточке.

**Правильный фикc (SSOT для состояния EmptyState):**
1. Добавить в `SessionView` отдельный флаг `emptyStatePending` и прокинуть его в `EmptyState pending={...}`.
2. В `EmptyState` отрисовывать **спиннер + "Creating session…"** когда `pending=true`, иначе — прежнюю карточку.
3. Источник `emptyStatePending` брать из того же workflow‑события, которое начинается по `Send` анкеты (PM‑контур), и держать его истинным пока `sessions.length === 0` (или пока не выбран/открыт диалог).

**Где реализовано (точки для навигации):**
- UI: `src/client/ui/src/session/session-view.tsx` (prop `emptyStatePending`)
- UI: `src/client/ui/src/session/empty-state.tsx` (ветка `pending`)
- UI: `media/session-view.css` (стили `.session-spinner`)
- PM: `src/client/project-manager/components/sessions/project-manager-session-view.tsx` (prop drilling)
- PM: `src/client/project-manager/components/sessions/project-manager-runtime-session-view.tsx` (`emptyStatePending`)
- PM: `src/client/project-manager/components/sessions/project-manager-dialog-session-view.tsx` (`emptyStatePending`)

**Проверка/DoD:**
- В момент `Send` анкеты слева **сразу** появляется спиннер (на месте карточки), и исчезает, когда UI Сессии гидратился.
- Фикс подтверждён пользователем в релизе `1.1.622`.

**Вывод для всех будущих фиксов:** сначала находим **реального владельца UI‑состояния** (какой компонент/фасад рисует симптом и по какому условию), затем добавляем/меняем сигнал **ровно в этом контракте**. Любые «pending события» вне этого контракта почти гарантированно дадут «релиз в пустоту».


**Цель:** сделать цепочки взаимодействий в системе _наблюдаемыми_ и _проверяемыми_ так, чтобы поиск причины бага не превращался в угадайку и серию «релизов в пустоту».

Эта диаграмма — один из ключевых артефактов этапа проектирования и должна работать как «быстрый источник правды» по тому:
- какие **модули** существуют,
- где их **границы**,
- какие **фасады** являются единственными точками входа,
- какие **взаимодействия** между фасадами допустимы и реально происходят.

Для текущего diagram workflow это означает:
- semantic SSOT шага `Diagram Modules` хранится в staged Markdown артефактах (`product-parts.index.md` + `product-parts/<part-id>.md`);
- визуальная композиция хранится отдельно в `module-map.flow.json`;
- Project Manager рендерит диаграмму из Markdown DSL через React Flow;
- visible runtime surface больше не использует Mermaid как source-of-truth, не показывает inline semantic editors и не держит bottom-right minimap.

## 1) Что именно мы считаем «фасадом»

**Facade-класс/файл** — единственная публичная точка входа в модуль (в терминах проекта: «закрытый модуль» + «фасад как API»). Внешний код не должен импортировать/использовать внутренние классы модуля напрямую.

Практическое правило идентификации фасадов в репозитории:
- файлы `*facade.ts` (или `*-facade.ts`) — фасады по соглашению;
- допускаются фасады без `facade` в имени, но тогда их нужно явно задекларировать в реестре фасадов (см. раздел 4.2).

**Внутренние классы** — любые реализации внутри модуля, не предназначенные для прямого использования извне.

## 2) Какие диаграммы нужны (минимальный набор)

### 2.1 Facade Dependency Graph (обязательная)
Глобальная диаграмма зависимостей фасадов.

**Узлы:** фасады (по одному узлу на фасад).

**Рёбра:** направленные зависимости фасад → фасад с обязательной типизацией:
- `import` — статическая зависимость через импорт;
- `event` — взаимодействие через event bus / custom events / stream events;
- `http` / `ws` — сетевой вызов;
- `fs` — взаимодействие через файлы/каталоги как контракт;
- `proc` — запуск процессов/CLI.

**Правило:** каждое ребро в диаграмме должно быть либо:
- автоматически выведено из кода (предпочтительно), либо
- явно аннотировано вручную (и объяснено — зачем оно существует).

### 2.2 Facade Interaction Map по шагам Workflow (желательно)
Для каждого шага дерева разработки (например, `Description`, `Virtual Simulation`, `Diagram Modules`) нужен короткий сценарный граф/схема:
- «кто инициирует действие» → «какой фасад принимает» → «какие фасады/контуры участвуют» → «какой артефакт/событие является сигналом завершения».

Это не заменяет глобальный граф, а прикладывается как «быстрый трейс» для конкретного шага.

Для runtime-шага `Diagram Modules` такой trace должен ссылаться на канонические staged Markdown артефакты (`product-parts.index.md`, `product-parts/<part-id>.md`), а не на legacy Mermaid-файлы.

## 3) Инварианты, которые диаграмма должна обеспечивать

1) **Никаких скрытых входов в модуль.** Если внешний код обращается к внутренностям — это либо баг архитектуры, либо модуль не закрыт.

2) **Единая точка ответственности.** Если UI/PM/Core/Launcher показывают статус, должны быть явно описаны:
- где находится source-of-truth,
- как он доставляется,
- какой сигнал считается «готово/не готово».

3) **Наблюдаемость до фикса.** Перед любым исправлением «простого UI поведения» обязателен ответ на вопросы:
- какой контур рисует UI (какой бандл/рантайм),
- какой сигнал должен изменить состояние,
- где именно этот сигнал появляется (код + лог).

Диаграмма должна позволять отвечать на это за минуты, а не за дни.

## 4) Как строить диаграмму так, чтобы она была поддерживаемой

### 4.1 Принцип «автомат + ручные аннотации»
Диаграмма деградирует, если её поддерживать только вручную.

Рекомендуемый подход:
- **автоматическая часть** строится из кода (статические зависимости + известные паттерны событий/транспорта),
- **ручная часть** добавляет смысл: тип ребра, причина, контрактные файлы, ограничения.

### 4.2 Реестр фасадов (обязателен, если есть исключения)
Если фасады не всегда следуют `*facade.ts`, нужен единый реестр фасадов:
- список фасадов (путь файла, экспортируемый символ, модульная область),
- краткая ответственность,
- статус (stable/experimental/deprecated).

Реестр нужен, чтобы генератор диаграмм был детерминированным.

### 4.3 Типизация рёбер (не «красивость», а диагностика)
Когда ребро помечено типом (`ws`, `fs`, `event`), ты автоматически понимаешь:
- где искать логи,
- где ставить correlation-id,
- где мог потеряться сигнал.

Это ключ к тому, чтобы не «гадать» при исправлениях.

## 5) Алгоритм постоянного обновления (обязательный рабочий цикл)

### 5.1 Когда обновлять
Диаграмма обновляется **в каждом PR**, если изменилось хоть что-то из списка:
- добавлен/переименован фасад;
- изменены публичные методы фасада;
- добавлены/удалены зависимости фасад → фасад;
- изменён транспорт (например, `ws` → `http`, `event` → `snapshot`);
- изменён контракт по файлам/артефактам (`.codeai-hub/...`, jsonl, continuity каталоги).

### 5.2 Что является “definition of done”
PR считается завершённым только если:
- обновлён граф фасадов;
- в PR описано, какие ребра изменились и почему;
- добавлены/обновлены логи по ключевым переходам (если менялся транспорт/статус);
- обновлена документация шага workflow (Interaction Map), если менялся пользовательский сценарий.

### 5.3 Минимальные проверки (gates)
Добавляем отдельные «гейты» качества для диаграмм (сначала как процесс, потом как скрипт):
- запрет на новые ребра без типизации;
- запрет на фасады без ответственности/модуля;
- детект «неправильных импортов» (внешний импорт внутренних классов).

## 6) Как использовать диаграмму для предотвращения тупиков

### 6.1 Протокол расследования бага (без кода)
Перед тем как писать фиксы:
1) По диаграмме определить цепочку фасадов для сценария.
2) Зафиксировать ожидаемый сигнал изменения состояния (событие/файл/snapshot).
3) Найти в логах место появления/потери сигнала.
4) Только после этого менять код в **одной** точке ответственности.

### 6.2 Пример вопросов, на которые диаграмма должна отвечать
- Где именно рождается «pending» для UI ожидания?
- Какой фасад обязан перевести UI из `pending` в `ready`?
- Через какой транспорт идёт сигнал?
- Где логируется этот переход и какой correlation-id у события?

Если на любой из этих вопросов нет ответа за 2–5 минут — диаграммы недостаточно, и её нужно улучшать.

---

## 7) Формат диаграмм (актуальная рекомендация)

- Для runtime workflow шага `Diagram Modules` канонический формат — staged Markdown артефакты:
  - `product-parts.index.md` + `product-parts/<part-id>.md` как semantic SSOT;
  - `module-map.flow.json` как manual-layout/view sidecar;
  - React Flow rendering в PM как user-facing surface.
- `Mermaid` допустим только для explanatory documentation, временных investigation notes или одноразовых design sketches вне runtime workflow.
- Если в документации используется `Mermaid`, он не должен рассматриваться как source-of-truth для PM rendering, watcher gating или agent merge path.

---

## 8) Что делать прямо сейчас (в контексте текущих проблем)

Даже на этапе `Description` уже стоит:
- начать вести реестр фасадов/контуров для PM/Core/Launcher;
- описать Interaction Map для `Send анкеты → создание сессии → появление UI`;
- стандартизовать logging + correlation-id для переходов статуса (pending/created/bound/running/done).

Это снизит вероятность повторения ситуации, когда простое UI-ожидание не удаётся реализовать несколькими релизами из-за отсутствия наблюдаемости и явной карты взаимодействий.
