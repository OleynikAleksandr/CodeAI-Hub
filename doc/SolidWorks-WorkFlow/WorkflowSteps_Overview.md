## 0) Философия Workflow

Главный принцип: **от простого к сложному**.

Никто в начале пути не может подробно описать будущее приложение. То, что в зрелом проекте выглядит как пакет из десятков архитектурных документов — результат месяцев итеративной работы. Попытка заставить пользователя «продумать всё заранее» на первом шаге — тупик.

Поэтому каждый шаг Workflow добавляет ровно один слой понимания:

- **Шаг 1 (Description):** ЧТО делаем, для кого, зачем. Скелет идеи.
- **Шаг 2 (Virtual Simulation):** КАК пользователь взаимодействует с будущим приложением. Сценарии простым языком.
- **Шаг 3 (Diagram Modules):** Из ЧЕГО состоит система — кластеры, модули, ответственности, связи.
- **Шаг 4 (Diagram Facades):** КАК модули общаются — фасады, контракты, типы взаимодействий.
- **Шаг 5 (Module Specifications):** ДЕТАЛИ каждого модуля — классы, state, storage, auth, error handling.
- **Шаг 6 (TODO Plan + Implementation):** РЕАЛИЗАЦИЯ — микрозадачи, код, коммиты.

Чем дальше по workflow, тем больше ведёт агент и тем меньше от пользователя требуется техническая экспертиза. На первых шагах пользователь — автор идеи. На последних — рецензент и заказчик, а агент — исполнитель.

### Архитектурная рекомендация

Workflow декларирует и настоятельно рекомендует **кластерно-модульную архитектуру**: микроклассы, классы-фасады как единственные точки входа в модуль. Это позволяет в каждый момент времени работать с очень небольшим фрагментом приложения и упрощает все задачи — от проектирования до отладки.

### Feedback Loop (сквозной принцип)

На каждом шаге возможен возврат назад. Это не баг, а легализованный итеративный процесс:

- Virtual Simulation показала, что модуль лишний → возврат в Description.
- Diagram Facades обнажила невозможный контракт → пересмотр Diagram Modules.
- Спецификация модуля выявила, что нужен ещё один модуль → обновление Diagram Modules.

Механика `OUTDATED` propagation обеспечивает видимость: при изменении артефакта upstream все downstream-шаги получают статус `OUTDATED`, и пользователь видит, что требуется синхронизация.

Перспектива: агент-оркестратор, который при изменении на любом шаге предлагает план обновления всех затронутых downstream-артефактов и выполняет его после одобрения пользователя.

## Шаг 1 — Description

**Главная цель:** зафиксировать идею в структурированном виде — достаточном, чтобы агент мог задать умные вопросы и помочь её оформить.

### Подшаг 1.1 — Questionnaire (анкета)

**Кто ведёт:** пользователь.

Пользователь заполняет анкету — краткий скелет идеи. Анкета намеренно облегчённая: она не требует технической экспертизы и не заставляет «продумать всё заранее». Задача — зафиксировать суть: какая проблема, для кого, какое решение, примерный стек, примерные модули (если пользователь уже видит их).

Принцип: лучше написать мало, но честно, чем много и фантазийно.

**Вход:**
- Пустой шаблон `questionnaire-template.md`.
- Опционально: существующие документы, наброски, ссылки (указываются в секции «Документы для чтения»).

**Выход:**
- `questionnaire.md` — зафиксированная анкета (артефакт шага).

### Подшаг 1.2 — Description Agent (единая сессия) → Final Description

**Кто ведёт:** Description Agent (в бесконечном диалоге с пользователем).

Агент читает заполненную анкету, задаёт уточняющие вопросы и итеративно собирает итоговое описание. Никаких искусственных лимитов: ни на количество вопросов агента, ни на количество замечаний пользователя. Диалог продолжается столько, сколько нужно, пока пользователь не скажет «утверждаю».

На этом этапе уже желательно обсудить **примерный состав модулей и кластеров**, но без жёсткой фиксации — это первое приближение, которое будет уточняться на следующих шагах.

**Вход:**
- `questionnaire.md` — заполненная анкета.
- (опционально) документы из `pre_read_documents`, если они указаны пользователем.

**Выход:**
- `Final_Description.md` — отполированный, утверждённый пользователем документ описания.

**Тип сессии:** бесконечная (resume). Пользователь может вернуться к обсуждению и правкам в любой момент.

### Артефакты шага

- `.codeai-hub/<workspaceSlug>/description/questionnaire.md`
- `.codeai-hub/<workspaceSlug>/description/Final_Description.md`
- Legacy (compat only): `.codeai-hub/<workspaceSlug>/description/description.md` может встречаться в старых workspace, но не является SSOT.

### Граница отложенного reviewer-модуля

Standalone/manual Reviewer не входит в базовый шаг 1 текущего workflow.
Если такой модуль будет возвращён, он должен жить как отдельная архитектурная надстройка поверх `Final_Description.md`, а не как обязательная внутренняя фаза шага Description.

## Шаг 2 — Virtual Simulation

**Главная цель:** описать 2–4 ключевых сценария взаимодействия пользователя с будущим приложением — что он делает, что видит, что ожидает получить.

### Проблема, которую решает двухфазный подход

Если агент Virtual Simulation ведёт интервью и сыпет техническими терминами (events, state machine, error handling), пользователь-не-программист теряется. А формат интервью плох ещё и тем, что пользователь отвечает на вопрос, агент фиксирует ответ, а через два вопроса пользователь вспоминает, что ответил неправильно.

Решение: дать пользователю сначала описать сценарии **своими словами**, а потом агент переведёт это в структурированный формат.

### Подшаг 2.1 — User Scenarios Draft (пользователь)

**Кто ведёт:** пользователь.

Пользователь получает мини-анкету (или пояснение-шаблон), где **простым языком** объясняется, что нужно сделать: «Опишите 2–3 ситуации: что вы делаете в приложении и что ожидаете увидеть. Пишите как рассказываете другу — без технических терминов».

Описание взаимодействия — это, по сути, интерфейс, который пользователь видит у приложения. Его понимание, как им управлять, последовательные действия и ожидаемые отклики. Как можно более человеческим языком.

Пусть это не будут описаны абсолютно все сценарии и шаги. Пусть это будет только несколько — агент уже поймёт направление, поймёт, чего ждёт пользователь, как он хотел бы пользоваться приложением и какие отклики хотел бы получать.

**Вход:**
- `Final_Description.md`.
- Мини-анкета / шаблон с пояснениями (что ожидается на этом этапе).

**Выход:**
- Черновик сценариев (в поле ввода или как файл).

### Подшаг 2.2 — Agent Refinement (агент)

**Кто ведёт:** Virtual Simulation Agent (в бесконечном диалоге с пользователем).

Агент читает `Final_Description.md` + черновик пользователя. На основе этого **сам** строит полноценный `virtual-simulation.md` со структурой (предусловия, шаги, ожидаемые результаты, контрольные точки). При необходимости задаёт уточнения и дорабатывает документ после подтверждения пользователя.

Принципиально: пользователь **не должен** формулировать «триггеры и события» или «state transitions» — он просто рассказывает историю использования, а агент переводит это в структуру. Документ пишется двуязычно: user-facing часть человеческим языком + техническая часть для последующих этапов.

**Вход:**
- `Final_Description.md`.
- Черновик сценариев от пользователя.

**Выход:**
- `virtual-simulation.md` — структурированный артефакт шага.

**Тип сессии:** бесконечная (resume). Пользователь может возвращаться к правкам в любой момент.

### Артефакты шага

- `.codeai-hub/<workspaceSlug>/virtual_simulation/virtual-simulation.md`

## Шаг 3 — Diagram Modules

**Главная цель:** зафиксировать структуру системы — из каких кластеров и модулей она состоит, какова ответственность каждого, и какие простые связи между ними.

### Почему этот шаг критически важен

Workflow декларирует кластерно-модульную архитектуру с микроклассами и фасадами. Diagram Modules — это первая точка, где эта архитектура материализуется. К этому шагу пользователь и агенты со всех дальнейших этапов будут часто возвращаться, когда понадобится новый модуль или перестройка существующих.

### Подход: Agent-First

После двух предыдущих этапов у агента достаточно материала (`Final_Description.md` + `virtual-simulation.md`), чтобы **самому предложить** первый вариант диаграммы модулей. Анкета и начальный ввод от пользователя здесь не нужны.

**Кто ведёт:** Diagram Modules Agent.

Ядро отправляет агенту инструкцию с шаблоном и путями ко всем предыдущим артефактам. Агент читает всё, строит диаграмму модулей (Mermaid), показывает пользователю с пояснениями. Пользователь выступает **рецензентом**: обсуждает, корректирует, утверждает.

**Вход:**
- `Final_Description.md`.
- `virtual-simulation.md`.
- Инструкция от ядра с шаблоном.

**Выход:**
- `modules-diagram.mmd` — диаграмма кластеров/модулей с ответственностями и связями.

**Тип сессии:** бесконечная (resume). Диаграмма — живой документ. При изменениях upstream (description, virtual simulation) шаг получает статус `OUTDATED`.

### Артефакты шага

- `.codeai-hub/<workspaceSlug>/diagram_modules/modules-diagram.mmd`

## Шаг 4 — Diagram Facades

**Главная цель:** углубиться в контракты — показать фасады каждого модуля, их публичные API, типы взаимодействий (event, import, ws, fs, proc) и построить граф зависимостей фасадов.

### Подход: Agent-First (полностью)

Пользователь-не-программист (в том числе так называемый «вайб-кодер») может не знать, что такое «контракт» и «фасад» — это приходит с опытом. Заставлять его формулировать контракты на входе бессмысленно. Этим полностью занимается агент.

**Кто ведёт:** Diagram Facades Agent.

Агент читает все предыдущие артефакты (включая `modules-diagram.mmd`) и строит **два артефакта**:

1. `facades-graph.mmd` — диаграмма зависимостей фасадов с типизированными рёбрами.
2. `facades-description.md` — пояснения человеческим языком: что такое каждый фасад, зачем он нужен, как общается с другими, какие контракты действуют.

Пользователь может задавать вопросы, просить упростить, объединить модули, перестроить контракты. Агент ведёт диалог и обновляет оба артефакта после подтверждения.

**Вход:**
- `Final_Description.md`.
- `virtual-simulation.md`.
- `modules-diagram.mmd`.
- Инструкция от ядра с шаблоном.

**Выход:**
- `facades-graph.mmd` — диаграмма фасадов.
- `facades-description.md` — пояснения к каждому контракту и фасаду.

**Тип сессии:** бесконечная (resume). К этому шагу часто возвращаются при рефакторинге модулей и их контрактов.

### Артефакты шага

- `.codeai-hub/<workspaceSlug>/diagram_facades/facades-graph.mmd`
- `.codeai-hub/<workspaceSlug>/diagram_facades/facades-description.md`

## Шаг 5 — Module Specifications (будущий)

**Главная цель:** для каждого модуля/кластера составить детальную спецификацию — внутренняя структура, классы, state management, хранение, auth, error handling, observability.

### Почему детали появляются только здесь

Вопросы, которые может быть соблазнительно задать на первом шаге (анкете) — механизм аутентификации, стратегия хранения, error handling, observability, recovery — **живут именно здесь**. На этапе идеи пользователь не знает ответов. После четырёх предыдущих шагов контекст достаточен для обоснованных решений.

### Подход: Agent-First

Агент, прочитавший всю цепочку артефактов, уже лучше пользователя понимает техническую сторону и разбирается в формулировках. По сути, хорошая спецификация — это уже практически код. Если она правильно написана, то код напишет любая модель.

**Кто ведёт:** Spec Agent (в диалоге с пользователем).

Агент ведёт диалог: предлагает структуру спецификации, задаёт точечные вопросы пользователю («вы хотите хранить данные локально или в облаке?», «аутентификация нужна?»). Пользователь участвует как эксперт по требованиям, а агент — как технический архитектор.

Ядро должно дать агенту хорошую инструкцию в начале сессии с контекстом всех предыдущих артефактов.

**Вход:**
- `Final_Description.md`.
- `virtual-simulation.md`.
- `modules-diagram.mmd`.
- `facades-graph.mmd` + `facades-description.md`.
- Инструкция от ядра.

**Выход:**
- `<moduleSlug>-spec.md` для каждого модуля — детальная спецификация.

**Организация:** каждый модуль специфицируется отдельно (отдельная сессия агента). Можно параллельно. Изменения в спецификации одного модуля могут повлиять на спецификации зависимых — OUTDATED propagation.

**Тип сессии:** бесконечная (resume) для каждого модуля.

### Артефакты шага

- `.codeai-hub/<workspaceSlug>/specifications/<moduleSlug>-spec.md` (по одному на модуль)

## Шаг 6 — TODO Plan + Implementation (будущий)

**Главная цель:** превратить спецификацию в последовательность микрозадач, которые можно выполнять и коммитить.

### Подход: Agent-First (проверен месяцами практики)

Этот шаг полностью принадлежит агенту. Он читает спецификацию модуля и генерирует пофазный, построимный план с микрозадачами. Формат проверен на практике:

- **Фазы** → **Стримы** → **Микрозадачи** (каждая затрагивает ≤ 3 файлов).
- Каждая подзадача оформляется парой: (1) реализация/изменения, (2) Git Commit.
- Статусы: `TODO` → `IN_PROGRESS` → `DONE`.
- Real-time обновление `todo-plan.md` после каждого коммита.
- Документация обновляется синхронно с кодом (в том же коммите).

### Подшаг 6.1 — Plan Generation (агент)

**Кто ведёт:** Planning Agent.

Агент читает спецификацию модуля и нарезает работу на фазы/стримы/микрозадачи. Пользователь утверждает план.

**Вход:**
- `<moduleSlug>-spec.md` — спецификация модуля.
- Общая архитектура (диаграммы, контракты).

**Выход:**
- `todo-plan.md` — план с микрозадачами.

### Подшаг 6.2 — Implementation (агент + пользователь)

**Кто ведёт:** Development Agent (под контролем пользователя).

Агент выполняет микрозадачи последовательно: реализация → гейты качества → коммит → обновление плана. Пользователь контролирует процесс и принимает результаты.

**Вход:**
- `todo-plan.md` + спецификация + существующий код.

**Выход:**
- Рабочий код + обновлённый `todo-plan.md` + обновлённая документация.

### Артефакты шага

- `doc/TODO/todo-plan.md`
- Код в `packages/` и `src/`
- Обновлённая документация в `doc/`

## Сквозные механизмы

### OUTDATED Propagation

При изменении артефакта на любом шаге все downstream-шаги получают статус `OUTDATED`:

- Изменение `Final_Description.md` → Virtual Simulation = `OUTDATED`.
- Изменение `virtual-simulation.md` → Diagram Modules = `OUTDATED`.
- Изменение `modules-diagram.mmd` → Diagram Facades = `OUTDATED`.
- Изменение `facades-graph.mmd` → Specifications = `OUTDATED`.
- Изменение спецификации → TODO Plan = `OUTDATED`.

### Feedback Loop (текущее и перспектива)

**Текущий механизм:** все сессии бесконечные (resume). Пользователь может вернуться на любой шаг и внести изменения. Статус `OUTDATED` на downstream-шагах виден в UI.

**Промежуточный шаг (перспектива):** при изменении артефакта ядро показывает **impact report** — какие downstream-артефакты затронуты и что в них нужно обновить. Пользователь решает, какие обновления запустить.

**Целевой механизм (перспектива):** агент-оркестратор, который при изменении на любом шаге предлагает план обновления всех затронутых downstream-артефактов и выполняет его после одобрения пользователя. Например: «Вы добавили модуль Z в Diagram Modules. Я могу: (1) обновить facades-graph, (2) создать спецификацию для Z, (3) обновить todo-plan. Утвердить?»

### Адаптивные шаблоны (перспектива)

Сейчас все шаблоны артефактов и инструкции для агентов статические и не зависят от конкретного проекта. В перспективе — отдельный агент (или препроцессор), который на основе уже созданных артефактов **корректирует шаблоны и инструкции** для следующего шага, делая их более релевантными конкретному приложению.

Например: после `Final_Description.md` (описан CLI-инструмент без UI) шаблон Virtual Simulation автоматически убирает секции про UI-потоки и фокусируется на CLI-сценариях.

Архитектурно стоит заложить место для этого: шаблоны проходят через препроцессор, который может быть тривиальным (копия файла) сейчас и умным (агент-адаптер) в будущем.
