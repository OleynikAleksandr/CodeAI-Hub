# System Architecture (SSOT) — SolidWorks-WorkFlow

**Scope:** каноническое описание системы CodeAI Hub целиком (уровень System).

**Status note (2026-05-15, updated 2026-06-06):** the previous managed workflow orchestration baseline for Diagram Modules, Application Skeleton, and Quality Gates Baseline remains removed. The replacement Managed Workflow Orchestration cluster now owns the active managed lifecycle for all three technical trunk stages: `Diagram Modules` Product Part Type A subturns and user review, `Application Skeleton` draft/review/materialization, and `Quality Gates Baseline` draft/review/integration/formal verification/persistent return. Core owns stage plans, validation, commit boundaries, continuation prompts, user-review phase transitions, and downstream unlock state; Project Manager and future clients are projections only.

## 0) Session role

Этот документ читается в начале сессии как базовый SSOT знакомства с системой:

- он объясняет глобальные инварианты;
- он показывает карту подсистем;
- он не является каталогом всех документов, которые нужно читать дальше.

Если после обсуждения новой задачи нужно выбрать дополнительные документы по конкретному scope, агент обязан использовать `doc/SolidWorks-WorkFlow/Docs_Index.md` и читать только релевантные документы, а не весь каталог подряд.

## 1) Компоненты системы (верхний уровень)

- **Core Orchestrator** (Node.js сервис): бизнес‑логика, turn lifecycle, routing, continuity.
- **Managed Workflow Orchestration** (Core Runtime cluster): replacement cluster for Core-owned lifecycle decisions of managed technical Documentation Tree stages (`Diagram Modules`, `Application Skeleton`, `Quality Gates Baseline`) and future managed steps through one facade/registry/state-machine contract.
- **Core Supervisor**: управление runtime, запуск/перезапуск и version attach.
- **Project Manager (CEF UI bundle)**: Workflow Tree + Sessions/Artifacts + stage/session routing UX + единственный живой Settings UI; PM также владеет runtime bootstrap authority для пользовательского запуска Core.
- **UI bundles**: `project-manager`, `vscode-webview` (extension-side settings surface = compat-only notice, не живой product UI).
- **VS Code extension shell**: distribution/install/bootstrap-components shell; не владеет runtime startup/attach и не является живым Settings owner.
- **CEF Launcher**: локальный клиент для Project Manager.
- **Providers**: Claude/Codex/Gemini/Kimi модули (CLI/SDK/Wire контуры), Local Models и OpenRouter Core providers.
- **Shared runtime translation module**: `doc/SolidWorks-WorkFlow/Modules/Shared_RuntimeTranslation_Module.md` (package: `packages/translation/`; engine-neutral facade with engine-aware safe chunk planning and per-chunk fallback assembly for live overlays today and localization adapters tomorrow).
- **Localization module**: `doc/SolidWorks-WorkFlow/Modules/Localization.md` (package: `packages/localization/`; owns bundled English source catalogs, glossary protection, localized bundle persistence, runtime payload contracts, and UI lookup primitives).
- **Gemini bundled runtime dependency**: installed Gemini provider bundles vendor `@codeai-hub/translation` into their own runtime root so the provider can resolve the shared translation package outside the workspace `node_modules` tree.

## 3) Глобальные инварианты (must-not-break)

0. **Clients are replaceable projections, not workflow authority**: Project Manager, future mobile/Wi-Fi clients, VS Code surfaces, and any other UI client are display/input/transport layers only. They may submit raw user intent and render Core-owned snapshots, but they must never own workflow truth: stage phase, active microtask, expected commit, prompt/template/source-artifact selection, artifact validity, gating, localization target, Core/system messages, managed state, or commit lifecycle. Core must continue every workflow step while all clients are closed until the next explicit user gate; any dependency on an open Project Manager for managed workflow progress is an architectural defect. New clients must attach to Core APIs and consume the same Core-owned state instead of inheriting Project Manager logic.
   - **Prompt template inline rule:** any text material required to produce a workflow artifact must be embedded in the first provider prompt as text: artifact templates, field references, schema fragments, examples, authoring rules, repair contracts, and validator-facing diagnostics. Paths may be included only as output targets/provenance/debug metadata. A workflow agent must not be expected to discover required format by reading template files, parser source, Project Manager code, or docs not embedded by Core.
   - **Artifact contract authority:** artifact schemas, parsers, validators, graph/read-model materializers, and repair diagnostics belong to Core or a provider-neutral shared contract module under Core authority. UI clients may render Core-owned parse results and pass raw user repair intent back to Core, but they must not own a separate backend parser/validator truth. If Project Manager currently contains a parser needed by the product contract, that parser is mislocated until moved to Core/shared contract or until PM consumes Core parse output only.
   - **Managed repair authority:** every artifact repair attempt, including a button click from any client, must become a Core-managed transition. Core chooses the failing artifact, creates or advances the active microtask plus paired Git Commit line, dispatches provider-visible repair instructions, validates through the canonical artifact contract, and commits accepted or safe rejected attempts with real hashes. Client-built repair prompts sent directly to provider sessions are forbidden for managed steps.
   - **Managed review acceptance button:** Core-authored system messages with tag `managed-workflow-user-review` may render an inline `Подтверждаю` button in Project Manager/shared Session UI. The user is not expected to type `подтверждаю`; the button is the normal UI command surface and submits a Core-owned review action scoped to the current review message id. It is not ordinary provider-visible text, must be idempotent for the active gate, and must reject stale/already-closed gates without starting duplicate provider turns. `Description` and `Virtual Simulation` remain provider-direct preliminary steps: they must not receive a Core completion/review handoff at session start, and their startup/provider prompts must be dispatched to the provider even if the prompt text mentions `подтверждаю` as an instruction. After every provider turn completion on these preliminary steps, while the step is not accepted, Core must append a user review gate that lets the user answer the agent's questions, ask more questions, request edits, or press `Подтверждаю`. If the user answers or requests edits, that text is routed to the provider; when the provider finishes the revision turn, Core appends the same review gate again. Only the explicit button acceptance or an equivalent short acceptance command sent while that gate is open may be consumed by Core. For managed technical review stages, provider `turn_completed` must not unlock input until Core has persisted messages, completed managed arbitration/cleanup, and opened the next Core gate or settled the transition. After a valid review acceptance, Project Manager may activate the next step card for navigation convenience, but Core remains the source of completion/phase truth.
   - Канон: `AGENTS.md`, `doc/SolidWorks-WorkFlow/Clusters/ManagedWorkflowOrchestration.md`, `doc/SolidWorks-WorkFlow/System/WorkflowSteps_Overview.md`.
1. **Snapshot-first lock contract**: состояние input определяется только snapshot‑сигналами (`turnState`, continuity lock flags и т.п.). Reopened workflow dialog обязан иметь runtime session в `workspace:snapshot` после первого `dialog:list`: Core materialize-ит stub runtime session для каждой continuity entry (`registerSessionWithId` + `registerRestoredBinding` + `notifySessionCreated` с `turnState: "idle"`, `continuityLockActive: false`, `bindingStatus: "ready"`) без запуска provider adapter turn; PM не имеет права держать fallback-ветку для "runtime session отсутствует в snapshot". **Stale-binding auto-recovery (1.2.42):** `providerSessionStatus: "ready"` выставленный materializer-ом означает только "журналированная запись в ядре есть", но НЕ означает "provider-модуль уже держит активное досье на сессию". Первый user message после Core restart попадёт в `adapter.sendMessage` с `providerSessionId`, которого модульный state (Claude SDK Manager in-memory Map / Codex app-server handshakedThreadIds Set / Gemini session map) не знает. Каждый provider adapter обязан бросать typed stale-binding error с `code` (`CLAUDE_SESSION_STALE_BINDING` / `CODEX_SESSION_STALE_BINDING` / `GEMINI_SESSION_STALE_BINDING`) и `providerSessionId`; `SessionRequestHandlerMessageDispatch.dispatchUserMessage` распознаёт code и выполняет one-shot `invalidateProviderBinding` + `ensureSessionReadyForSend` + resend. Generic `Error` на этом пути недопустим — он приводит к silent drop (classifier помечает `retryable`, но retry не запускается). **Post-rebind usage_limits refresh (1.2.43):** retry-ветка после успешного `ensureSessionReadyForSend + resend` обязана одноразово триггерить `adapter.refreshUsageLimits` для свеже-hydrated session через `triggerPostRebindUsageLimitsRefresh`. PM отправляет `binding_ready` usage_limits refresh ровно один раз на логическую session, и тот первый refresh гонится против paper-binding до hydration — без повторного trigger'а usage_limits виджет остаётся пустым у Claude и Codex после Core restart. Gemini не страдает потому что делает proactive refresh внутри `startManagedSession`, остальные провайдеры полагаются на Core-триггер. **Codex PATH augmentation (1.2.43):** `CodexAppServerProcess.startInternal` расширяет inherited `process.env.PATH` curated-списком user-level install locations (`~/.npm-global/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` на POSIX; `%APPDATA%\npm` на Windows) — без hardcoded absolute paths, PATH lookup остаётся primary mechanism. Это убирает `spawn codex ENOENT` при recovery re-spawn на macOS, где VS Code extension host inherit'ит GUI env без shell PATH extensions. **Single-probe usage_limits warmup (1.2.44):** `binding_ready` triggers для каждого reopened dialog ранее дёргали `adapter.refreshUsageLimits` каждый раз, что приводило к lost payload'ам на первом (до hydration) refresh и лишнему трафику на остальных. Теперь `SessionRequestHandler` держит account-wide `UsageLimitsWarmupTracker: Set<providerId>`: первый успешный `binding_ready` probe per provider per Core process запускает dispatch и помечает provider как warmed, все последующие `binding_ready` для того же провайдера делают только cached replay. Empty probe без payload не имеет права warming-ить provider и не должен suppress-ить следующий `binding_ready`. Другие lifecycle triggers (`turn_completed`, `reconnect`, `manual`, `provider_session_rebound`, `dialog_opened`, `session_opened`) не дедуплицируются — они отражают реальные state changes. Кэш уже account-scoped (`providerScopeKey = {providerId}:global` с `070139b9e`), поэтому один успешный probe наполняет payload для всех sessions провайдера одновременно. **Pre-turn reopened-dialog usage refresh (1.2.45/1.2.47):** PM держит provider-scoped usage cache и seed-ит из него новые dialog/runtime snapshots даже если source `sessionId` ещё не materialize-ился локально; при фактическом `dialog_opened` Core обязан сначала replay-ить cached usage snapshot, а затем запускать cheap provider refresh даже если cached payload уже есть. `adapter.refreshUsageLimits` на этом пути обязан быть awaitable и завершаться только после фактического provider read/broadcast, иначе Core lifecycle incorrectly concludes before payload exists. Поздний provider-scoped `usage_limits` payload обязан применяться ко всем matching provider-family snapshots даже если исходный `payload.sessionId` уже исчез локально из-за placeholder→restored runtime swap. Это обеспечивает last-known limits immediately + fresh limits before the next user turn without eager `resumeSession` / provider hydration.

Для Claude этого уже недостаточно как общей формулы: CodeAI Hub-managed turns также обязаны идти в full SDK isolation mode без filesystem `CLAUDE.md` / settings discovery, иначе parent-chain от `cwd` может затащить personal memory из real home.

7. **Provider dialog segment preservation**: если provider runtime фактически отдает несколько assistant-replies внутри одного пользовательского turn-а, provider normalization layer не имеет права схлопывать их в один post-factum blob; допустим только fallback aggregate-path, когда streamed segment boundaries не были отданы вообще.
   - Gemini extension (1.2.9): provider-side quirks, которые лепят thought-like content в обычный `content`-поток без сопровождающих `ptype: "thought"` events, обязаны быть распознаны и вынесены в thinking overlay, а не прокинуты в финальный assistant bubble. Это покрывает два случая: (a) inline `[Thought: true]` / `[Thought: false]` разделитель внутри одного content stream между thought-like английским summary и финальным target-language ответом; (b) pre-tool английский progress-text на старте сессии, когда target `messagesForTheUserLanguage` в Cyrillic-family (`ru`/`uk`/`bg`/`sr`/`mk`/`be`/`ky`/`kk`/`mn`/`tg`/`ab`) и snapshot не содержит ни одного U+0400..U+052F символа. Литеральный `[Thought: ...]` token никогда не попадает в dialog.
   - Gemini extension (1.2.12): на `thinkingLevel=high` с большими Description Agent промптами Gemini 3.1 Pro Preview иногда эмитит свой internal meta-prompt (`sthought`, `CRITICAL INSTRUCTION`, `Related tools:`, `Plan:`, `Drafting the content`) через `Content` events вместо `Thought` events. `GeminiAssistantEventNormalizer.handleFinishedEvent` проверяет финальный assistantSegment через `hasMisroutedThinkingPrefix` (после 1.2.9 marker-splitter и pre-tool heuristic) и маршрутизирует весь segment через `emitInlineThoughtAsThinking` если сработал префикс. Это UI-correctness patch до upstream-fix от Google; список префиксов в `MISROUTED_THINKING_PREFIXES` — это allowlist, расширяется консервативно по наблюдениям retest'ов.

8. **Workspace-scoped stream replay**: stateful session signals (`token_usage`, `usage_limits`), которые могут прийти до attach/rebind workspace scope, обязаны иметь replay-safe transport path после websocket connect и после смены scope; single-shot delivery для таких сигналов недопустим.

9. **Provider-order-safe continuity arbitration**: Core обязан одинаково корректно обрабатывать оба event order-а (`token_usage -> turn_completed` и `turn_completed -> token_usage`); trailing usage может завершать уже начатую post-turn arbitration, а cached usage обязан быть turn-scoped и очищаться после решения.
   - Explicit unavailable fallback (1.2.16): если eligible flow-node session завершилась `turn_completed`, но provider знает, что trailing usage snapshot для этого turn-а уже не появится, provider обязан эмитить explicit `postTurnTokenUsageUnavailable: true`. Только этот explicit signal разрешает Core завершить pending post-turn arbitration как `no_rollover`; просто отсутствие usage не может молча unlock-нуть session.

Transient errors (`transient_turn_failure`) не должны удалять binding, деградировать whole provider или молча дропать user message. Retry budget ограничен (1 transient + 1 auto-resume), pending user intent имеет TTL=60s.

14. **Effective model identity SSOT**: `modelId` в transport/runtime/UI контракте означает полную effective model identity, а не только base model; reasoning/thinking являются частью identity. `~/.codeai-hub/settings/settings.json` остаётся global defaults/seed path для bootstrap and new workspace seeding only. Once a workspace is active, Project Manager/workflow settings resolve to `.codeai-hub/<workspaceSlug>/runtime/settings/settings.json` inside that workspace capsule; that file is live workspace truth but is rollback-ignored/preserved across workflow Clear/Undo. After a logical session is created next-turn identity belongs to `Session.modelBinding`, and committed session/applied-config artifacts are the reproducibility proof instead of rolling back live settings. Launcher/Core bootstrap and extension-side compat storage are not allowed to fall back to `~/.codeai-hub/settings/claude.json`; when the global seed or workspace settings file is missing, Core must materialize a fresh normalized `settings.json` instead of resurrecting any legacy filename.
   - Core settings snapshot reads use a path-scoped short TTL cache (`packages/core/src/config/json-file-snapshot-cache.ts`) before provider/default/translation settings normalization. Cache keys are resolved file paths, malformed JSON/non-object roots resolve to `null`/existing defaults, and the cache must not merge snapshots across different settings paths. Settings save/reset/default materialization paths invalidate the canonical settings path immediately after write.
   - Broadcast contract (1.2.13): **любой** `session:model:update` event, отправляемый клиенту, обязан нести effective modelId (т.е. с суффиксом `thinking:X` / `reasoning:X` где применимо), а НЕ raw base id от provider SDK. Это распространяется и на `broadcastRuntimeModelUpdate` в `session-provider-event-router.ts` (путь через SDK `model_info` events), и на dispatch-path из `session-request-handler-message-dispatch.ts`. Raw `data.model` от SDK должен обогащаться через `SessionRequestHandlerAppliedTurnConfig.resolveEffectiveModelId(providerId, targetModelId)` до broadcast'а. Без этого UI label в session status panel мерцает между двумя формами (`(thinking high)` vs `(high)`) в зависимости от того, какой update прилетел последним.
   - Client-side fallback contract (1.2.15): клиентский `ModelInfo` builder в `src/client/ui/src/session/model-info-builder.ts` при fallback-пути к `settings` (initial render до первого `session:model:update`) обязан обернуть raw level из `thinkingLevelByModel` / `reasoningByModel` в тот же provider-specific prefix, который эмитит `parseEffectiveModelId` на effective id (`thinking ${level}` для Gemini, `reasoning ${level}` для Codex). Claude ветка сохраняет отдельную convention (`"thinking off"` для disabled, raw effort для enabled). Без этой consistency UI показывает label в двух разных формах за время первого рендера (начальный fallback → Core broadcast).
   - Session-scoped binding contract (SMB-001): persisted Settings больше не являются live owner для уже созданной logical session. Settings или explicit create selection только seed-ят `session.modelBinding` при `session:create`; после этого existing turns читают frozen binding identity из `Session`, serialization и `session:created`. Единственный нормальный mutation path для bound identity — explicit `switch_model`, который обновляет `session.modelBinding` и emits `session:model:update`. PM/shared UI seed-ят initial snapshots из `session.modelBinding` (`ModelInfo.source = "binding"`), а `useSettingsModelsSync()` не имеет права переписывать binding/runtime-owned snapshots при изменении Settings.
   - Provider launch/start-card settings truth (1.2.545): workflow start cards and Development Tree start/fix cards are Settings writers only. They must persist provider/model/reasoning choices through scoped Settings before session creation; Core then resolves the new session binding from Settings. Launch-card payloads must not carry one-shot model/reasoning truth. Native GLM connection settings (`apiKey`, `baseUrl`) remain global user-space settings, while GLM model/reasoning defaults remain workspace-scoped.
   - Kimi binary thinking toggle (1.2.544/1.2.545): native Kimi has no effort levels and no Wire per-turn thinking field. `providers.kimi.thinkingEnabled` is a spawn-time binary flag (`--thinking` / `--no-thinking`), and `providers.kimi.thinkingDisplaySyncEnabled` is UI-only visibility. Settings save/reset and launch-card writes must reconcile active Kimi adapters only on a real value change; `reconfigureThinking` keeps the adapter initialized after restart so the next stop/rebind turn can proceed without provider deactivation.
   - Claude Status Panel switch (1.2.119): `session:claude:model-switch` follows the same binding-owned mutation rule as Codex. ## 5) Workflow Boundary (Description, 2026-03-01)

- Шаг `description` зафиксирован как single-agent file-first flow:
  - pre-submit: `questionnaire.md` + user Help,
  - post-submit: единая resume-сессия,
  - SSOT-артефакт: `Final_Description.md`.
- `Final_Description.md` должен формироваться сразу после чтения анкеты (первичный черновик), чтобы пользователь обсуждал уже существующий документ.
- Первый prompt шага `Description` должен включать полный текст текущей анкеты `questionnaire.md` как authoritative inline source с path/provenance; агент не должен тратить отдельный turn на чтение анкеты целиком перед созданием первого draft.
- `Final_Description.md` должен содержать не только описание идеи, но и базу для следующего шага `virtual_simulation`:
  - ключевые сценарии в количестве, достаточном для покрытия продукта (актор/цель → действие → ожидаемый результат → критерий успеха),
  - ограничения/допущения,
  - ключевые сущности/термины.
- Product-visible contract шага не использует `description.md`, manual restart или встроенный reviewer; internal compat для legacy draft допустим только как non-SSOT fallback.
- Legacy naming `Idea` / `Idea Collector` больше не участвует в PM bootstrap, user-facing copy, release packaging или stage semantics текущего workflow. ## 6.4) Diagram Workflow Stabilization Boundary (Phase 5, 2026-03-16; updated Phase 57, 2026-03-24)

- Shared diagram editor UX обязан сохранять визуальную непрерывность:
  - background refresh не должен очищать уже загруженный graph перед следующим успешным parse/load;

Дополнительно (релиз `1.2.40`, уточнено в `1.2.41`, compact retest 2026-05-17): диаграмма авто-подгоняется по ширине Artifacts panel через `ResizeObserver` + natural `scrollWidth` композиции — effective scale = `autoFitScale × userZoom`, где `autoFitScale = min(1, containerWidth / naturalWidth)` с нижним порогом `0.12`. Manual Cmd/Ctrl+scroll — overlay поверх auto-fit базы; Cmd/Ctrl+0 сбрасывает только user overlay, не auto-fit. Inner composition обязана оставаться в естественном grid sizing режиме — без intrinsic-sizing keyword'ов (`width: max-content` и т.п.) на самом grid-container'е: `scrollWidth` на нормально-сайзнутом grid уже равен `max(clientWidth, rightmost-child.right)` и поднимается выше container width ровно тогда, когда реальные cluster/module card constraints (`minWidth: 220`, `minmax(240px, 1fr)` в ProductPart header) выталкивают content за track. Попытка форсировать `width: max-content` на composition-container'е разрешает prose (purpose text, long titles) и `1fr` column tracks развернуться в unwrappable single lines, что раздувает natural width в тысячи пикселей и schleppt auto-fit в floor независимо от user zoom. Начиная с row-aware auto-layout scope `2026-05-17`, automatic layout считает фактические горизонтальные module-card slots в каждом Product Part row, а не количество кластеров: default auto-placement не должен превышать три горизонтальных module cards суммарно across adjacent clusters and standalone modules. Product Part `columns: auto` candidates проверяются после resolved cluster `moduleColumns`, поэтому кандидат, который визуально дал бы Cluster(2) + Cluster(1) + standalone Module в одной строке, отклоняется как four-card row и переносит standalone Module на следующую строку. Это правило применяется к `moduleColumns: auto` внутри cluster даже когда пользователь явно выбрал Product Part `columns`; explicit cluster `moduleColumns` остаётся user-authored override. Product Part `targetAspectRatio` работает только при `columns: auto`: resolver выбирает среди допустимых row-budget candidates `1..5`, поэтому `square` может уйти в более вертикальную 1-column композицию, а `wide` выбирает более широкую композицию в пределах того же row-budget. Cluster/module spacing is compact by contract: Product Part body tracks size to occupied content, Cluster cards align to start, internal module tracks use the real module-card width bounds (`220..260px`) with fixed small gaps, and free viewport width must not be distributed as empty space between module cards. Cluster boundary width is computed from the resolved module grid width, so long titles or purpose text wrap inside the compact cluster width instead of creating excess right-side padding.

If any planned Product Part brief is missing or not accepted, Core keeps the lead order-plan task blocked and dispatches no provider prompt. When the final brief is accepted, Core sends the lead `DevelopmentOrderPlan` prompt to the lead Product Part session, not to the secondary session that happened to open the barrier.
  - Lead Product Part `DevelopmentOrderPlan.draft.json` uses the Core-readable `codeai-development-order-plan-v2` contract. The lead prompt embeds the full accepted brief markdown for every planned Product Part inline; file paths are provenance only and the agent must not be required to discover or read brief files. The lead agent proposes waves, dependencies, locked nodes, and required accepted briefs, but it does not directly start downstream agents. Core validates the JSON against the materialized Development Tree, persists `.codeai-hub/<workspaceSlug>/workflow/managed/development-tree-product-parts/<partId>.unlock-state.json`, and leaves the accepted order plan markdown/JSON/Product Part ledger/managed state in main. It does not start `cluster` / `standalone_module` sessions from Product Part documentation closeout.
  - Development Tree node prompts resolve chat/artifact prose languages from global localization settings, including `~/.codeai-hub/settings/settings.json`; they are not workspace-local language preferences. Downstream Product Part and Cluster prompts must include the resolved runtime language contract inline while keeping canonical file names, ids, JSON keys, method/event names, structural headings, and status tokens in English.
  - Future Cluster Contract work runs only after a verified-main downstream start, not from Product Part documentation closeout. The cluster sub-agent must receive inline Product Part/order-plan/skeleton/quality-gates context from main and produce the cluster facade boundary artifacts in its own downstream worktree. User/lead review acceptance writes a boundary-accepted checkpoint in the main workspace but does not copy draft cluster documents into main, does not perform a mainline merge, and does not mark the cluster node `merged`; the cluster worktree remains the active downstream execution tree for future facade/module code work.
  - Project Manager reads Product Part coordination only from Core's `developmentTree` snapshot. Cluster/module nodes may carry `coordination.status` (`locked`, `waiting`, `unlocked`, `boundary_accepted`, `worktree_active`, `code_ready`, `merged`) plus worktree/evidence refs; clients render this graph but do not infer phase state, start waves, or mutate Git.
  - `Implementation Foundation` and full branch-level implementation waves remain future/deferred scopes after user review of the generated Product Part / Cluster / Module drafts.
  - Facades are not a separate trunk step; cluster/module facade contracts are draft artifacts produced with the matching node specification.
- Diagram workflow user surface не может подменять диаграмму raw Markdown source по умолчанию. При reopen/resume `Diagram Modules` Project Manager обязан возвращать пользователя в `Artifacts` (visual diagram), а `Source` оставлять вторичным debug view.
- Пока canonical artifact ещё не создан, `Artifacts` panel для workflow stage обязан показывать тот же help-content, что и вкладка `Help`; отдельный pending-intro prose вне help SSOT не допускается.
- Ordinary dialog reopen/recovery contract обязан сохранять identity continuity между PM, Core continuity и provider runtime. Если runtime по любой причине создает fresh provider session вместо обычного resume, новый binding должен быть immediately normalized в continuity/index до следующего outbound user turn, а PM не имеет права бесконечно повторять `createSession(old providerSessionId)` для того же continuity entry.
- `Diagram Modules` не навязывает пользователю inline semantic editors или bottom-right minimap. Product UX обязан опираться на:
  - AI-generated semantic structure в canonical `.md`;
  - nested ownership containers для `Diagram Modules`, где `Product Part` = top-level CSS Grid контейнер, `Cluster` = nested CSS Grid контейнер, `Module` = child card внутри cluster или напрямую внутри owning product part;
  - right-click context menu для decalarative layout params (columns, aspect ratio, module columns), результат которых сохраняется в `module-map.flow.json` v2 `layoutParams`;
  - agent-driven semantic updates when new semantic content is needed.
- Diagram canvas interaction model (начиная с релиза `1.1.922`, Sidecar v2):
  - **Right-click context menu** на ProductPart: `columns` (`auto` | 2..5), `targetAspectRatio` (`landscape` | `wide` | `square`); на Cluster: `moduleColumns` (`auto` | 1..3). Выбранные значения мутируют in-memory nodes, сразу уходят в sidecar v2 через `onNodesChange`, и переживают reload через `applyFlowSidecarLayoutParams` на read-path;
  - **Zoom**: CSS `transform: scale(...)` по Cmd/Ctrl+scroll (range 25–200%, шаг 1%); reset — Cmd/Ctrl+0 или clickable badge в bottom-left при scale ≠ 100%;
  - **Без drag-based node movement**: CSS Grid сам раскладывает card'ы согласно layout params. Нет collision avoidance/containerConstraints/resizeContainersToFit — всё это реализует браузер.
- Detachable diagram window:
  - кнопка `Detach` в artifact header (слева от `Artifacts` toggle) открывает popup-sized CSS Grid view в отдельном CEF popup через `window.open()`;
  - detached окно использует тот же sidecar файл (`module-map.flow.json`), что и основной PM — layout params v2 синхронизированы;
  - `BroadcastChannel("pm:diagram:sidecar-sync")` уведомляет второе окно о перезагрузке sidecar после layout write;
  - detached окно является отдельной projection surface и обязано само активировать `workflow-state-store` для своего workspace: изменения Core-owned workflow snapshot / Diagram Modules progress / generated Product Part ids должны вызывать reload projection без закрытия и повторного Detach;
  - semantic artifact refresh не должен зависеть от sidecar write channel: `module-map.flow.json` синхронизирует только user-authored layout params, а появление новых `product-parts/<part-id>.md` приходит через workflow-state/read-model polling;
  - detached popup не является owner-window приложения: его закрытие не должно завершать main PM window и не должно reuse-ить autosaved frame главного PM окна;
  - реализация: `detached-diagram-view.tsx`, `detach-diagram-button.tsx`, `stage-artifact-header-toggle.tsx` (`extraActions` slot).

## 6.5) Diagram Modules Ownership Hierarchy Boundary (Phase 6, 2026-03-21; updated 2026-04-09 post React Flow removal and Sidecar v2)

- `Diagram Modules` больше не ограничивается semantic baseline вида `cluster + standalone module`.
- Канонический semantic runtime contract для module stage теперь включает `ProductPartEntity[]`, `ClusterEntity[]`, `ModuleEntity[]` и `ModuleRelation[]`.
- `Product Part` является верхним ownership layer для user-facing diagram:
  - имеет `title`, `purpose`, ordered `clusterIds`, ordered `standaloneModuleIds`;
  - не может быть пустым;
  - не может использоваться как relation endpoint.
- `Cluster` обязан принадлежать ровно одному `Product Part`, а `Module` обязан принадлежать ровно одному `Product Part` и максимум одному `Cluster`.
- Visual shell projection для `Diagram Modules` обязана использовать nested CSS Grid container model:
  - `Product Part` = top-level CSS Grid контейнер, положение которого задаётся декларативными layout params (`columns`, `targetAspectRatio`);
  - `Cluster` = nested CSS Grid контейнер внутри owning product part, чья внутренняя раскладка задаётся per-cluster `moduleColumns`;
  - `Module` = child card внутри cluster или напрямую внутри product part, если модуль standalone;
  - контейнеры не владеют pixel-level constraints (`parentId`, `extent: "parent"`, `containerConstraints`, collision avoidance) — layout driven целиком браузерным CSS Grid движком, а не JS measure/place pass (см. §6.2, §6.4).
- First-open composition для ownership-aware `Diagram Modules` обязан оставаться readable без user drag:
  - top-level `Product Part` containers раскладываются как независимые lane sections и не могут overlap друг с другом;
  - standalone modules внутри `Product Part` компактизируются через тот же owning-grid, а не через отдельный auto-layout pass;
  - ownership-free external modules/boundaries (например выбранный AI provider) визуализируются вне product-part container, а не как внутренние элементы его ownership layer.
- Начиная с managed technical trunk baseline (`2026-05-16`), `Diagram Modules` фиксируется как главный user-feedback checkpoint, но больше не является последним шагом ствола:
  - пользователь именно здесь впервые видит архитектуру в наглядной форме и должен иметь возможность активно её корректировать;
  - после `Diagram Modules` workflow переходит к `Application Skeleton`, затем к `Quality Gates Baseline`;
  - production implementation, code-ready branch execution and downstream merge разрешены только после committed skeleton materialization и verified Quality Gates command/hook evidence;
  - facade specs are produced later by user-started Development Tree Product Part / Cluster / Module node sessions, not by the trunk `Diagram Modules` step.
- Начиная с product-part decomposition baseline (`2026-03-23`), `Diagram Modules` больше не должен упираться в giant single-turn generation:
  - сначала runtime materialize-ит `product-parts.index.md`;
  - затем отдельные `Product Part` materialize-ятся по одному;
  - visual shell обязана progressively регенерировать CSS Grid composition по мере появления новых part artifacts;
  - relation lines и cross-part wiring исключаются из первого обязательного baseline slice.
- First-open layout contract для `Diagram Modules` теперь полностью декларативен:
  - runtime отдаёт visual shell только semantic tree (`Product Part -> Cluster -> Module`) и optional layout params из sidecar v2;
  - CSS Grid контейнеры раскладывают child cards нативно — runtime не выполняет JS-based measure/place pass, runtime не владеет header budget'ами и не вычисляет child positions вручную;
  - defaults layout params выбираются projection layer'ом (`columns: auto`, `targetAspectRatio: landscape`, `moduleColumns: auto`), пока пользователь не override-ит их через right-click context menu.
- User-facing hierarchy contract для ownership containers:
  - `Product Part` и `Cluster` обязаны показывать короткий purpose/description surface, а не только title и counters;
  - standalone modules компактизируются через owning product part CSS Grid column track, а не через отдельную band-logic;
  - outer frame `Product Part` замыкается по реально занятому CSS Grid содержимому — без пустой декоративной вертикали.
- `module-map.flow.json` остаётся non-semantic layout sidecar:
  - хранит placeholder positions, viewport и (в формате v2) опциональную секцию `layoutParams` с declarative CSS Grid overrides (`columns`/`targetAspectRatio` на ProductPart, `moduleColumns` на Cluster);
  - не переносит ownership semantics и не дублирует содержимое канонического `.md`;
  - применяется только если `Revision` sidecar совпадает с текущим semantic artifact; если нет, visual shell стартует с projection defaults и игнорирует sidecar (см. §6.2).
- Runtime orchestration contract для `Diagram Modules` is owned by the active Managed Workflow Orchestration cluster:
  - visual shell renders semantic artifacts as read-only projection state;
  - Product Part follow-up, repair prompts, task movement, and next-step release must come from Core stage-plan validation and commit boundaries;
  - sidebar label remains `Module Graph` (Source mode убран — визуальная композиция является основным артефактом).

## 7) Codex Response Mode Boundary (2026-03-13)

- `Settings -> General` теперь владеет persisted policy `general.responsePolicy`; эта настройка не смешивается с `Core Controls`.
- В Project Manager-owned settings surface `Core Controls` снова видимы как recovery block рядом с persisted response policy: General tab допускает `Restart Core`, но не превращается в полный runtime lifecycle console.
- Baseline default для workflow-сценариев: `hybrid`.
- `strict` оставляет editable schema/instruction contract для узких machine-readable turn-ов.
- `debug_raw` нужен для исследования новых моделей без baseline default schema pressure на обычные turn-ы.
- Provider-home native artifacts and optional native request capture are diagnostic artifacts; dialog/history остаётся нормализованным display-слоем. Always-on provider SDK/raw JSONL mirrors under `~/.codeai-hub/logs/{claude,codex,gemini}` are not part of the runtime contract.
