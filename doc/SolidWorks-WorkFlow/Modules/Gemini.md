# Gemini Provider Module — Module (SSOT)

## Назначение
Провайдерный модуль Gemini для Core: запуск CLI/SDK, one-shot turns, базовая интеграция с workflow.

## Где живёт код
- `packages/Gemini_Module/`
- Usage-limits facade for Gemini lives in Core: `packages/core/src/provider-usage-limits/providers/gemini/gemini-usage-limits-facade.ts` (shared cluster, see `packages/core/src/provider-usage-limits/`).

## Messaging cluster
- `packages/Gemini_Module/src/messaging/message-processor.ts` — thin façade: `createAccumulator`, `handleEvent`, `finalize`.
- `packages/Gemini_Module/src/messaging/gemini-stream-event-router.ts` — dispatch по Gemini stream event types и error normalization.
- `packages/Gemini_Module/src/messaging/gemini-assistant-event-normalizer.ts` — assistant chunks, source-first thinking messages и flush по `finished` boundaries.
- `packages/Gemini_Module/src/messaging/thought-translator-service.ts` — compatibility re-export старого имени поверх adapter class.
- `packages/Gemini_Module/src/messaging/gemini-system-event-normalizer.ts` — tool/system/warning events без смешивания с assistant сегментами.

## Runtime cluster
- `packages/Gemini_Module/src/runtime/cli-bridge.ts` — runtime bridge loader and compatibility entrypoint; root/core resolution now delegates to `cli-bridge-root-resolver.ts`.
- `packages/Gemini_Module/src/runtime/cli-bridge-module-loader.ts` — module loading and compatibility validation helper shared by `cli-bridge.ts` and `gemini-installer.ts`.
- `packages/Gemini_Module/src/runtime/cli-bridge-root-resolver.ts` — CLI/Core package root candidate scanning and version resolution helper.
- Gemini runtime bridge must support both the legacy `dist/src/config/*` CLI layout and the modern bundle-only global `@google/gemini-cli@0.36.x` layout; safe compatibility settings loading reads `~/.gemini/settings.json` plus `<workspace>/.gemini/settings.json` directly instead of importing bundle chunks with runtime side effects.
- Installed Gemini provider bundles are self-contained at runtime: `scripts/build-gemini-module.sh` vendors `@codeai-hub/translation` into the provider install root so `dist/index.js` can resolve the shared package outside the workspace tree.

## Installer cluster
- `packages/Gemini_Module/src/installer/gemini-installer.ts` — bridge/install orchestrator facade for package preparation and recovery.
- `packages/Gemini_Module/src/installer/gemini-package-manager.ts` — package install/update/recovery helper owned by the installer boundary.

## Инварианты
- Lifecycle обязателен: `turn_started` → `turn_completed|turn_failed`.
- Любые auth/quota ошибки не должны оставлять UI в stuck working.
- Provider event order не симметричен другим модулям: `Gemini` может эмитить `token_usage` раньше `turn_completed`, поэтому usage не считается признаком завершения turn-а.
- Для flow/document continuity `token_usage` используется только как вход в post-turn arbitration; Core не имеет права запускать rollover до фактического `turn_completed`.
- Если provider отдал несколько assistant segments в одном turn-е, модуль обязан флашить их по реальным `finished` boundaries и не дублировать финальным aggregate block, когда segmented history уже была сохранена.
- Gemini thoughts сначала emit-ятся в source form и сохраняются в canonical history без ожидания перевода; если translation overlay позже готов, UI получает `localizedContent` patch и обновляет уже существующее сообщение по тому же `messageId`.
- Переведённые Gemini thoughts не должны выглядеть как отдельный provider role в UI: текущий продуктовый контракт хранит visible path как `assistant` + `tag: "thinking"`; `thinkingDisplaySyncEnabled` — это только presentation toggle (`Thinking in dialog`), поэтому source history и overlay persistence продолжаются даже когда Session UI скрывает видимую плашку.
- Видимость решается на emission time и фиксируется на persisted `SessionMessage` через `visibilityAtEmission`. Hidden Gemini thinking не попадает в Core-owned translation queue, а re-enable `Thinking in dialog` внутри long-running session работает forward-only: только thought-сообщения, emit-нутые после включения, становятся видимыми и переводимыми; ранее скрытые плашки остаются скрытыми.
- Язык видимых Gemini thoughts определяется Core-threaded `reasoningLanguage` (после UI/Reasoning translation split — каноничный путь). Gemini provider adapter сегодня читает legacy alias `messagesForTheUserLanguage` / `translationEngineId`, который Core threads на applied-turn-config envelope с тем же resolved value что и `reasoningLanguage` / `reasoningEngineId` до завершения миграции adapter-а. При `en` overlay translation hop пропускается и в bubble остаётся оригинальный provider text.
- Для Gemini assistant output из leg, который породил `tool_call_request`, считается progress/status output, а не terminal answer всей chain; terminal completion может подтверждаться только output-ом terminal leg без новых tool requests.
- Для Gemini перевод больше не является blocking prerequisite для flush/reply ordering: turn finalization не ждёт overlay translation, а late translation patch только дообогащает уже materialized сообщение.
- Для Gemini `thinking` входит в effective model identity: одинаковый base model с разным `thinkingLevel` считается разным `modelId`, и UI/runtime не должны восстанавливать этот уровень по локальной догадке.
- Gemini runtime не имеет права владеть next-turn identity отдельно от Core: единственный source of truth для следующего turn остаётся `~/.codeai-hub/settings/settings.json`, а provider получает уже вычисленную effective identity через applied turn config.
- Gemini session settings resolver кэширует shared settings snapshot per normalized settings path for `500ms` while building session argv/context-window fallback values. Applied turn config remains authoritative for the next turn; the cache only avoids repeated synchronous `settings.json` reads under rapid session setup/resume.
- Если Gemini stream завис после `model_info`, partial text или другого промежуточного progress event и больше не отдаёт terminal event, stalled-turn watchdog обязан завершить turn контролируемой recoverable ошибкой вместо вечного `working`; для nested `post_tool` legs используется более длинное Gemini-specific окно, чем для initial leg, но отсутствие terminal-leg answer всё равно остаётся failure.
- Provider-owned raw SDK JSONL under `~/.codeai-hub/logs/gemini/` is removed from the runtime path. Exact provider-applied model/thinking при аудите нужно подтверждать по Gemini provider-home/session traces, session-local normalized history, or explicit native request capture, not by an always-on raw SDK mirror.
- `formatGeminiStreamErrorMessage()` остаётся единым formatter-ом для nested Gemini stream payload errors, чтобы router и тесты не расходились по тексту ошибок.
- Installed Gemini bundles must be runnable after deployment without relying on the repo workspace `node_modules`; any shared runtime dependency required by the provider must be copied into the bundle root by the build script.
- Gemini runtime compatibility must not depend on importing CLI bundle chunks into the Core process: bundle-side effects can register conflicting telemetry globals, so provider bootstrap may read Gemini settings from files but must keep module execution limited to the core runtime exports that are required for session startup.
- Gemini post-tool leg contract: output from a leg that already produced `tool_call_request` is progress/status output, not terminal completion proof; terminal completion may be confirmed only by the terminal leg without new tool requests.
- Gemini stalled-turn contract: if the stream stalls after `model_info`, partial text, or other intermediate progress output and never reaches a terminal event, the watchdog must end the turn with a recoverable failure instead of a silent infinite working state. Current defaults (1.2.14): `DEFAULT_STALLED_TURN_WATCHDOG_MS = 240_000` for the initial leg, `DEFAULT_POST_TOOL_STALLED_TURN_WATCHDOG_MS = 240_000` for nested follow-up legs — symmetric. History: 1.2.11 bumped initial 60_000 → 240_000 after first retest on Gemini 3.1 Pro + `thinkingLevel=high`; 1.2.14 bumped post-tool 120_000 → 240_000 after second retest showed the same asymmetry can kill a legitimate post-tool reasoning turn (Gemini 3.1 Pro still in silent deep-reasoning phase after tool_call results). Both values live in `packages/Gemini_Module/src/session/gemini-session-lifecycle.ts` and are overridable per session via `session.stalledTurnWatchdogMs` / `postToolStalledTurnWatchdogMs`. Adaptive-per-thinking-level watchdog remains a planned follow-up only if 240s/240s proves too generous or too tight in future retests.
- **Stop Abort + Resume (1.2.7, see SystemArchitecture Invariant 24).** `GeminiSessionLifecycle.closeSession` in `packages/Gemini_Module/src/session/gemini-session-lifecycle.ts` MUST NOT call `session.client.resetChat()` on Stop. On the Gemini CLI Core side that call materializes a new empty `GeminiChat` against the same `Config.sessionId` and writes a new empty chat file under `~/.gemini/tmp/<projectSlug>/chats/`, orphaning the prior chat-file history. Permitted close steps are `abortController.abort()` to cancel the active turn plus `sessionStore.removeSession` for our own bookkeeping. The pre-stop chat file must remain intact on disk so `gemini --resume <providerSessionId>` can reload it on the next turn. The provider declares `capabilities.requiresPostStopResume = true` in `provider-descriptor-factory.ts`; Core's `SessionProviderBindingService.invalidateProviderBinding` persists the live `providerSessionId` before invalidation, and `SessionRequestHandlerStopRebind.performRebind` threads it back through `resolveProviderSessionId` as `requestedProviderSessionId`. `GeminiProviderAdapter.resumeSession` forwards it as `argv.resume` via `gemini-session-settings-resolver.ts`, and Gemini CLI Core loads the prior chat file back with Description Agent system instruction and prior dialog. Without this contract, Stop → Continue leaves Gemini with an empty context and agents forget the original workflow.
- Adapter-owned session event listeners are deterministic lifecycle resources: `GeminiProviderAdapter` registers a disposer for every bound session emitter, moves that disposer on `sessionIdChanged`, and runs it on `closeSession`. `GeminiSessionLifecycle.closeSession` aborts the active turn, removes the session, runs the existing close emit path, and then clears the session emitter as a safety net; because lifecycle emit filtering currently allows `assistant` events only, this cleanup is not a new user-facing close notification. This prevents duplicate forwarding/listener retention without changing the Stop → Continue resume contract above.
- **Real resume wiring (1.2.8).** `argv.resume` in the embedded cli-core bootstrap path is advisory only — the official `gemini` CLI main binary is what actually runs the three-step resume pipeline (`SessionSelector.resolveSession(uuid)` → `config.setSessionId(...)` → `geminiClient.resumeChat(convertSessionToClientHistory(messages), resumedSessionData)`) and takes the resume branch inside `ChatRecordingService.initialize`. `GeminiSessionBootstrapper` in `packages/Gemini_Module/src/session/gemini-session-bootstrapper.ts` MUST therefore run that same pipeline itself after `config.initialize()` and `monkeyPatchGeminiClient`: scan `config.storage.getProjectTempDir()/chats` for `session-*-<uuid-first-8>.json`, read each candidate, keep only files whose full `conversation.sessionId` matches the resume id, pick the one with the most messages (defensive against pre-1.2.8 state where `resetChat` had created two files for one UUID), then `config.setSessionId(...)`, `sessionUtils.convertSessionToClientHistory(messages)`, and `await client.resumeChat(history, { conversation, filePath })`. `cli-bridge-module-loader.ts` exposes `sessionUtils` (with a small locally-defined subset type in `cli-types.ts` because workspace type-level `@google/gemini-cli-core` pins an older version). All failure paths (missing sessionUtils export, no matching file, malformed JSON, missing `client.resumeChat`) degrade to a reporter.warn and a fresh session; they do NOT throw. Unit coverage lives in `gemini-session-manager.stop-resume.test.ts`.
- **Stale-seed auto-recovery (1.2.8).** Project Manager dialog bootstrap is allowed to seed a brand-new Core session with a stale `providerSessionId` and `providerSessionStatus: "ready"` (observed in retest after rapid Stop → reopen cycles). User sends on such a session bypass `hasStopInvalidatedBinding` in `SessionRequestHandlerStopAction` and hit the provider directly, surfacing as `Gemini session <uuid> not found. Available: [] Aliases: []` from `GeminiSessionStore.requireSession`. `GeminiProviderAdapter.sendMessage` detects this surface via `extractStaleProviderSessionId` and re-throws as `GeminiSessionStaleBindingError` (`code: "GEMINI_SESSION_STALE_BINDING"`, exposes `providerSessionId`). `SessionRequestHandlerMessageDispatch.dispatchUserMessage` catches it by duck-typing on `error.code`, calls `providerBindingService.invalidateProviderBinding` (which captures the stale id into `preStopProviderSessionIdBySession`), runs `stopRebind.ensureSessionReadyForSend` (triggers the real resume pipeline above), re-resolves the bound provider channel, and retries the send once. A second failure falls through to `handleProviderFailure` so we do not loop. The recovery hooks are injected via `messageDispatch.setStaleBindingRecoveryHooks(...)` after construction because `stopRebind` is built after `messageDispatch` in the top-level handler.
- **Inline `[Thought: true]` splitting (1.2.9, see SystemArchitecture Invariant 7).** On post-tool follow-up turns Gemini CLI Core sometimes packs a thought-like English summary, the literal token `[Thought: true]` (or `[Thought: false]`), and the final target-language reply into a single `content`-event stream — with NO accompanying `ptype: "thought"` events. `GeminiAssistantEventNormalizer.handleFinishedEvent` in `packages/Gemini_Module/src/messaging/gemini-assistant-event-normalizer.ts` MUST run `splitInlineThoughtMarker(text)` (regex `/\[Thought:\s*(true|false)\]/`) against the assembled post-tool assistant segment before emitting the final assistant bubble. The pre-marker half is routed through `emitInlineThoughtAsThinking`, which feeds the raw text into `thought-translator-service` as a synthetic `ThoughtSummaryLike` (`{ description: trimmed, subject: "" }`) so it reuses the exact same overlay translation path that native `ptype: "thought"` events use; the translated (or untranslated fallback) text is emitted as `assistant` with `tag: "thinking"`. The post-marker half becomes the ordinary assistant-segment that the existing pending-translations flush path emits with no tag. The literal `[Thought: true]` / `[Thought: false]` token itself MUST never surface in dialog. Unit coverage lives in `gemini-assistant-event-normalizer.inline-thought.test.ts`.
- **Pre-tool non-target-language heuristic (1.2.9, see SystemArchitecture Invariant 7).** At session start Gemini often emits a brief English `content` chunk (e.g. `I will read the questionnaire...`) right before the first `tool_call_request` of the turn, again without `ptype: "thought"` events. `TurnAccumulator` carries `preToolAssistantSegment: string | null` (initialised null by `createAccumulator`); `GeminiAssistantEventNormalizer.snapshotPreToolAssistantSegment(accumulator)` is idempotent and is invoked from `GeminiSystemEventNormalizer.handleToolCallRequestEvent` before the tool request is pushed into `toolRequests`, so the snapshot is taken on the FIRST tool_call_request of the turn and `currentAssistantChunks` is cleared to prevent double-counting. In `handleFinishedEvent`, when `preToolAssistantSegment` has content and `shouldReclassifyAsThinking(text, targetLanguage)` returns true (target in `ab`/`be`/`bg`/`kk`/`ky`/`mk`/`mn`/`ru`/`sr`/`tg`/`uk` AND text contains zero `U+0400..U+052F` characters), the snapshot is routed through `emitInlineThoughtAsThinking` (same overlay path as the Bug A splitter); otherwise it is prepended to the final assistant bubble, preserving the current behaviour for in-target-language pre-tool text. Target `en` / undefined / non-Cyrillic targets disable the heuristic entirely — we cannot reliably detect "not English" from raw characters alone. Wiring: `GeminiSystemEventNormalizer` takes the assistant normalizer through its constructor; `GeminiMessageProcessor` injects `this.assistantNormalizer` at construction time. Unit coverage lives in `gemini-assistant-event-normalizer.inline-thought.test.ts`.
- **Mis-routed thinking prefix reroute (1.2.12, see SystemArchitecture Invariant 7).** Gemini 3.1 Pro Preview on `thinkingLevel=high` with large Description Agent prompts sometimes streams its internal meta-prompt (`sthought`, `CRITICAL INSTRUCTION`, `Related tools:`, `Plan:\n`, `Drafting the content`) through `Content` events instead of `Thought` events, producing 10k+ character English blobs that our normalizer used to write as assistant bubbles. `GeminiAssistantEventNormalizer.handleFinishedEvent` now runs `hasMisroutedThinkingPrefix(text)` against the residual `assistantSegment` AFTER the 1.2.9 Bug A splitter and Bug B pre-tool heuristic have finished. If the check fires, the whole segment is rerouted through `emitInlineThoughtAsThinking` (same overlay path reused by native `ptype: "thought"` events and the 1.2.9 reroute cases) and `assistantSegment` is cleared so no assistant bubble is emitted. The prefix list in `MISROUTED_THINKING_PREFIXES` is an explicit allowlist — extended conservatively based on retest observations, not heuristic fuzzy match. Native `gemini` CLI does NOT need this because its UX is scrollback-only and it has no equivalent of our `Final_Description.md` overlay; when Google ships an upstream fix for the provider-side quirk, the detector can be reverted via the constant.
- **Self-abort uncaughtException suppression (1.2.12, see SystemArchitecture Invariant 30).** `@google/gemini-cli-core` `GeminiClient.processTurn` (client.js:539) internally calls `controller.abort()` when its own loop-detection fires. The resulting `AbortError` is rejected in a background `node-fetch` Promise chain owned by cli-core, parallel to our `GeminiTurnRunner.runTurn` iterator. Our per-turn `try/catch` does NOT own that chain, so the error escalates to `uncaughtException` and used to kill the daemon. `packages/core/src/index.ts` now installs a process-level `uncaughtException` handler that inspects `error.stack` and, if it contains `@google/gemini-cli-core` AND `error.name === "AbortError"`, swallows the error (log-only via `appendFatalLog("core:abortError:suppressed", ...)`). All other `uncaughtException` are re-thrown, preserving Node's default crash semantics for real bugs. Allowlist lives as `PROVIDER_ABORT_SUPPRESSION_STACKS` — adding a new SDK is an explicit decision, not a silent catch.
- **Installer layout (1.2.8).** `GEMINI_INSTALLER_PATHS` in `packages/core/src/provider-registry/provider-installer-paths.ts` points at the full module subpath `<providers-home>/gemini/cli/lib/node_modules/@google/gemini-cli/`. `GeminiInstaller.computePrefix` strips the `/node_modules/...` tail and the `/lib` suffix and lands `npmPrefix` on `<providers-home>/gemini/cli`. Without that full subpath the marker-based stripping did not fire and the fallback `path.resolve(dir, "..", "..")` walked up to `<providers-home>/`, scattering the CLI's `bin/` and `lib/node_modules/` at the providers-home root alongside `gemini/`, `claude/`, `codex/`. Post-1.2.8 layout: `<providers-home>/gemini/<adapter-version>/dist/...` (our adapter) + `<providers-home>/gemini/cli/bin/gemini` (CLI symlink) + `<providers-home>/gemini/cli/lib/node_modules/@google/gemini-cli*` (CLI + Core). Claude and Codex paths are unchanged.
- **Thinking-level whitelist parity (see SystemArchitecture Invariant 27).** `settings.json` is re-normalized by two independent layers: the extension-side `parseSettingsSnapshot` on save, and the Core-side `SettingsRequestHandler.handleLoad` on PM / websocket load. Today Core's `handleLoad` spreads Gemini `thinkingLevelByModel` unfiltered (no per-level whitelist), but the Claude branch next to it DOES carry a hardcoded whitelist + legacy anchor table in `packages/core/src/remote-bridge/handlers/settings-request-handler-claude-thinking.ts` — and that duplicate was the exact cause of the 1.1.998 `xhigh` regression (Core silently rewrote `xhigh` back to `medium` on PM boot). If we ever add a Gemini-side `settings-request-handler-gemini-thinking.ts` sibling with its own hardcoded `GEMINI_THINKING_LEVELS`, it MUST be kept in lockstep with: `src/types/gemini-model-registry.ts` + `packages/core/src/config/provider-defaults-resolver.ts` (`resolveGeminiThinkingFromSettings`) + `src/extension-module/settings/gemini-settings.ts`. Otherwise a new thinking level accepted by the Settings UI will be silently reverted to the Core default on the next PM boot.
