## 1. Мотивация

Ни один провайдер не лучший во всём:

- **Claude** — сила: архитектура, domain expertise, кластеризация. Слабость: больше уточнений на ранних этапах.
- **GPT 5.4** — сила: narrative, глубина рассуждений, continuity. Слабость: больше user input на Diagram Modules.
- **Gemini Flash** — сила: скорость, структурный каркас. Слабость: пропускает нюансы (continuity, downstream sync).

Максимальное качество — через комбинирование. Ручное тестирование подтвердило: два провайдера параллельно с перекрёстным обменом дают лучший результат.

## 2. Точка входа: отправка анкеты

Когда пользователь заполнил анкету шага workflow и нажимает "Отправить", у него два варианта:

- **Одному провайдеру** (текущее поведение) — анкета уходит выбранному агенту, сессия работает как сейчас. Никаких изменений.
- **Двум провайдерам** (dual-agent mode) — анкета уходит обоим, Core создаёт session group из двух сессий, дальше всё по сценарию ниже.

Выбор делается в момент отправки: кнопка "Send" отправляет одному, кнопка "Send to Both" (или toggle рядом с Send) — двум. Пара провайдеров настраивается заранее в preferences или выбирается перед отправкой.

## 3. Сценарий (4 фазы)

### Phase 1 — Cross-Broadcast Q&A

User отправляет задание обоим агентам. Каждый задаёт вопросы из своей зоны экспертизы. Все вопросы и ответы транслируются перекрёстно обоим через буферизованный cross-broadcast (см. раздел 3).

Эффект: агенты дополняют друг друга вопросами, оба draft-а обогащены общим контекстом.

### Phase 2 — Parallel Drafts

Оба агента генерируют draft параллельно. Пользователь видит два артефакта (два таба сессий).

### Phase 3 — Cross-Review

Пользователь решает, что оба агента закончили работу, и нажимает кнопку **"Start Review"** (аналог кнопки перехода на следующий шаг workflow). Core автоматически берёт текущий артефакт из каждой сессии и отправляет перекрёстно: Agent A получает Draft B с промптом "сделай review", Agent B получает Draft A.

Рецензент уже в контексте (участвовал в Q&A), поэтому review осмысленный.

### Phase 4 — User Decision

Пользователь читает оба review → сразу видно, какой draft сильнее. Нажимает **"Accept as SSOT"** на табе выбранного агента. Core помечает эту сессию как **primary** (`primarySessionId` в session group) — её артефакт становится каноническим для следующего шага workflow. Вторая сессия становится read-only.

Если нужно учесть замечания из review второго агента — пользователь копирует их в чат primary-сессии как обычное сообщение. Выбранный агент дорабатывает свой draft.

## 4. UX: два таба, а не один комбинированный dialog

Комбинированный dialog (оба агента в одном потоке) отброшен — каша из чередующихся turn-ов, сложная синхронизация, пользователь не понимает кому отвечает.

**Решение:** два таба сессий в PM. Каждый таб — обычная сессия с одним агентом, привычный UX. Core переключает/подсвечивает таб, когда агент закончил turn и ждёт ответа.

### Буферизованный cross-broadcast

Главная проблема: агенты работают в разном темпе. Agent A закончил turn — user отвечает. В это время Agent B ещё думает. Нельзя "перебивать" Agent B посреди turn-а чужим контекстом.

**Правило: cross-broadcast только вместе с очередным user message.**

Алгоритм:
1. User отвечает Agent A → Core кладёт пару {вопрос_A, ответ_A} в **буфер для Agent B**
2. Когда user в следующий раз отвечает Agent B → Core формирует сообщение:
   - **Сначала** — ответ пользователя на вопросы Agent B (основной контент)
   - **Затем** — блок от Core: *"Дополнительный контекст: пока ты работал, другой агент задал следующие вопросы и получил на них ответы. Учти их тоже:"* + содержимое буфера
3. Буфер очищается

Если за время работы Agent B в буфере накопилось несколько пар Q+A от Agent A — все отправляются одним блоком.

Если буфер пуст (Agent A ещё не задавал вопросов или user ещё не отвечал) — сообщение уходит как обычно, без дополнительного блока.

## 5. Автоматизация vs ручное управление

**Запуск** — Core: создаёт две параллельные сессии, дублирует initial prompt. User: выбирает пару провайдеров.

**Q&A** — Core: буферизует cross-broadcast, подклеивает к user message. User: отвечает на вопросы, переключается между табами.

**Переключение табов** — Core: подсвечивает/переключает таб, когда агент закончил turn. User: может переключиться сам в любой момент.

**Draft** — Core: отслеживает готовность, показывает оба draft-а. User: —

**Cross-Review** — Core: по нажатию "Start Review" отправляет артефакты перекрёстно. User: нажимает кнопку, когда считает, что оба агента закончили.

**Decision** — Core: помечает выбранную сессию как primary, вторую — read-only. User: нажимает "Accept as SSOT", копирует нужные замечания в чат primary-агента.

## 6. UX в Project Manager

- **Toolbar**: toggle "Dual-Agent Mode" + селектор пары провайдеров
- **Session tabs**: два таба — "Session (Claude)" / "Session (GPT)" с аватарами провайдеров
- **Tab highlight**: индикатор "ждёт ответа" на табе, когда агент закончил turn
- **Artifact panel**: две вкладки (Draft A / Draft B) + кнопка "Accept as SSOT"
- **Review panel**: замечания от обоих рецензентов, чекбоксы для выборочного включения

**Provider Modules:** без изменений. Вся логика — в Core.

## 8. Решённые вопросы

- **Синхронизация темпа Q&A**: draft-ы по мере готовности каждого. Cross-review начинается только по ручной команде пользователя ("Start Review"), когда он считает, что оба закончили.
- **Дедупликация вопросов**: не автоматизируем. Если оба спросили похожее — user отвечает дважды (копипаст). Быстрее, чем пытаться автоматизировать.
- **Fallback**: если один провайдер упал — переход в single-agent. Во второй сессии сообщение "агент недоступен".
- **Cost visibility**: используем существующий Limit Visibility, который уже показывается в каждой сессии.
