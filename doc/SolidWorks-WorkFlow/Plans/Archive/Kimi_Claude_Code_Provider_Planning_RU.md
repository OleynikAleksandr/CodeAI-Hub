# Kimi-Claude-Code Provider Experiment — planning

**Status:** active planning source  
**Date:** 2026-05-19  
**Owner:** Oleksandr + Codex  
**Scope:** проверить и, при подтвержденной совместимости, реализовать отдельного провайдера `kimi-claude-code`: Kimi Code / Kimi 2.6 через Claude Code-compatible runtime/protocol.

## 1. Цель

Нужно сравнить поведение Kimi 2.6 в двух условиях:

1. **Native Kimi provider** (`kimiCode`) — уже реализован через Kimi CLI Wire.
2. **Kimi-Claude-Code provider** — Kimi Code вызывается через Claude Code-compatible client/runtime, чтобы проверить, станет ли поведение ближе к Claude Code: обычные progress-сообщения, другой tool loop, другой формат reasoning/progress и лучшее следование CodeAI Hub workflow instructions.

Этот scope заменяет отмененный `kimi-codex` эксперимент. Codex-based spike был откатан коммитом `5902a324f`, потому что текущий Codex CLI требует Responses API, а Kimi Code endpoint подтвержденно работает через Chat Completions / Anthropic-compatible Messages, но не через `/responses`.

## 2. Основная гипотеза

Kimi Code официально поддерживает Anthropic-compatible endpoint для сторонних coding agents. Поэтому Claude Code-compatible runtime имеет более высокий шанс работать с `kimi-for-coding`, чем Codex App Server:

- Kimi Code OpenAI-compatible endpoint: `https://api.kimi.com/coding/v1/chat/completions`;
- Kimi Code Anthropic-compatible endpoint: `https://api.kimi.com/coding/v1/messages`;
- model id: `kimi-for-coding`;
- local CodeAI-owned runtime state target: `~/.codeai-hub/providers/kimi-claude-code/home`.

Проверка должна доказать не только HTTP compatibility, но и agent-loop compatibility: stream events, tool calls, file edits, stop/resume lifecycle, provider session id, usage/token telemetry behavior.

## 3. Provider Identity

Proposed Core/UI identity:

- provider id: `kimiClaudeCode`;
- user-facing label: `Kimi-Claude-Code`;
- model id: `kimi-for-coding`;
- provider family: Kimi, but runtime client family: Claude Code;
- settings placement: Claude-family settings surface may expose Kimi-Claude-Code subsection, but persisted defaults must stay under `providers.kimiClaudeCode`, not under `providers.claude`;
- session artifacts: separate provider namespace, not mixed with `kimiCode` or `claudeCode`.

Reason: пользователь должен видеть и сравнивать три разных runtime conditions:

- `Claude` — Anthropic model through Claude Code runtime;
- `Kimi` — native Kimi CLI Wire runtime;
- `Kimi-Claude-Code` — Kimi model through Claude Code-compatible runtime.

## 4. Runtime Architecture

### 4.1. Не мутировать существующий Claude provider

Existing Claude runtime is subscription/OAuth-oriented:

- `ClaudeAuthRuntime.getAuthEnvironment()` intentionally strips `ANTHROPIC_API_KEY`;
- it sets `CLAUDE_USE_CLI_AUTH=true` and `CLAUDE_SUBSCRIPTION_MODE=true`;
- normal Claude SDK turns use provider-home `~/.codeai-hub/providers/claude/home`;
- normal Claude SDK turns keep CodeAI-owned `systemPrompt`, `tools: ["Read", "Write", "Edit"]`, `settingSources: []`.

`kimi-claude-code` must not weaken those invariants for the real Claude provider.

### 4.2. Новый runtime profile

Kimi-Claude-Code needs a separate runtime/auth profile:

```text
HOME=~/.codeai-hub/providers/kimi-claude-code/home
ANTHROPIC_BASE_URL=https://api.kimi.com/coding
ANTHROPIC_API_KEY=<resolved from Kimi config or explicit env>
```

The exact `ANTHROPIC_BASE_URL` must be proven by live probe. Kimi docs show full Anthropic-compatible endpoint as `https://api.kimi.com/coding/v1/messages`, so the base URL should be the value that Claude Code appends into `/v1/messages` without producing a double path.

API key resolution policy:

1. Prefer explicit CodeAI runtime env if provided (`KIMI_API_KEY` or a dedicated future key).
2. Fallback to existing local `~/.kimi/config.toml` `providers.kimi-for-coding.api_key`, same source currently used for native Kimi usage limits.
3. Never copy the secret into CodeAI settings, provider home, logs, native capture artifacts, or planning docs.

### 4.3. Instruction and tool policy

Initial experiment should reuse the Claude CodeAI-owned workflow profile as much as possible:

- same `CODEAI_CLAUDE_WORKFLOW_SYSTEM_PROMPT`;
- same workflow first user prompt generated by Core;
- same `settingSources: []`;
- same minimal tool allowlist target: `Read`, `Write`, `Edit`;
- no `CLAUDE.md` / AGENTS.md / user-global settings discovery;
- no hidden provider-global project instructions.

If live capture proves Claude SDK treats `tools` as additive rather than restrictive for Kimi-Claude-Code, product integration must stop and record the tool-surface evidence before continuing.

## 5. Feasibility Gates

Implementation must not add UI provider cards before these gates pass:

1. **HTTP/runtime gate:** Claude Code-compatible runtime can start with `ANTHROPIC_BASE_URL` pointed at Kimi Code and can receive a short answer from `kimi-for-coding`.
2. **Workflow prompt gate:** the same runtime can run a CodeAI workflow-style prompt with CodeAI system prompt and minimal tools.
3. **Tool loop gate:** file read/write/edit tool calls either work through Claude Code runtime or fail with categorized evidence.
4. **Lifecycle gate:** Core can observe turn start, visible progress/text, turn completion/failure, and stop behavior without leaving Session UI locked.
5. **Isolation gate:** no Claude subscription home, no real `~/.claude` project instructions, no AGENTS.md/project instruction auto-load.

If any gate fails, the scope records blocker evidence and stops before product integration.

## 6. Integration Shape If Feasible

### Provider module boundary

Preferred implementation: additive module inside or next to `packages/Claude_Module`, but with a separate facade/adapter boundary:

- `KimiClaudeCodeProviderAdapter` is the only Core-facing facade for this runtime.
- Shared Claude SDK helpers may be reused only through explicit profile options; no hidden `if provider === kimi` branches inside the normal Claude runtime path.
- Auth/runtime environment is provided by a dedicated Kimi-Claude-Code auth profile.
- Session lifecycle remains provider-specific enough to classify stale binding and usage unavailable states.

### Core registry

Core provider registry adds `kimiClaudeCode` as a distinct provider id with its own descriptor, installer path/runtime package mapping, effective model identity key, and usage-limits bridge behavior.

Packaging decision: `kimiClaudeCode` does not need a separate provider tarball while it reuses the Claude Code SDK/runtime. The adapter is exported by `@codeai-hub/claude-module`, so release packaging must keep bundling the normal Claude module tarball and should treat Kimi-Claude-Code as an additional runtime profile inside that artifact.

### Settings

Settings should avoid a full duplicate tab if possible:

- render Kimi-Claude-Code in a Claude-family settings section/subsection;
- persist defaults separately under `providers.kimiClaudeCode`;
- do not overwrite `providers.claude`;
- do not overwrite native `providers.kimi`;
- expose only controls that the runtime actually supports after probe.

Likely first-release controls:

- default model: `kimi-for-coding` only;
- thinking/reasoning controls: disabled or explicitly unsupported until Claude Code/Kimi behavior is proven;
- thinking display toggle: only if provider emits visible thinking/progress compatible with existing Session UI.

### Project Manager and Session UI

If feasible, Kimi-Claude-Code must appear in the same user-facing places as other providers:

- Description questionnaire submit provider picker;
- workflow start cards for later steps;
- Development Tree start/fix cards;
- Settings provider surfaces;
- status line/model chip;
- provider label/tint/title mapping;
- provider inheritance into next workflow step defaults.

Provider inheritance must preserve `kimiClaudeCode`; it must not fall back to Claude, native Kimi, or Codex.

## 7. Usage Limits and Context Telemetry

First release should be honest:

- Kimi Code 5-hour/weekly usage can reuse the native Kimi usage endpoint only if the same account/API key source is proven applicable.
- Claude usage-limit readers do not apply to Kimi-Claude-Code.
- Context/token usage from Claude `/context` may not work against Kimi-Claude-Code; if not proven, show unavailable instead of fake values.

## 8. Diagnostics

Required diagnostics:

- live probe artifacts with categorized failure output;
- native/capture evidence showing provider-visible system prompt, tool list, model id, base URL class, and first user prompt;
- no secret values in artifacts;
- clear evidence whether the runtime used Anthropic-compatible `/v1/messages`.

## 9. Risks

- Claude Code may refuse non-Anthropic endpoints in the SDK path even if raw CLI supports env overrides.
- Kimi Code may require a client identity/user-agent compatible with allowed coding agents.
- Tool schemas may differ from Anthropic Claude semantics.
- Thinking/reasoning behavior may still be Kimi-native and not Claude-like.
- Stop/resume/session ids may not map cleanly through the Claude SDK.
- Usage/context telemetry may be unavailable.

## 10. Exit Criteria

Minimum successful experiment:

- Kimi-Claude-Code live probe returns a visible answer through Claude Code-compatible runtime.
- A workflow-style prompt produces at least one normal assistant progress/final message.
- Runtime state is isolated under `~/.codeai-hub/providers/kimi-claude-code/home`.
- Existing Claude and native Kimi providers still work unchanged.
- Product surfaces are added only after compatibility evidence is recorded.

Minimum failed experiment:

- blocker is documented with exact failed gate, endpoint/runtime evidence, and next possible unblocker;
- no incomplete provider cards/settings are shipped.

## 11. Live feasibility evidence — 2026-05-19

### 11.1. Short-answer runtime probe

Result: **passed**.

Observed facts:

- Claude Agent SDK was able to start a Kimi-backed turn through `ANTHROPIC_BASE_URL=https://api.kimi.com/coding`.
- Model id reported by the SDK stream: `kimi-for-coding`.
- CodeAI resolved the Kimi API key from `~/.kimi/config.toml` `providers.kimi-for-coding.api_key`; the secret was not logged.
- Runtime home was isolated under `~/.codeai-hub/providers/kimi-claude-code/home`.
- SDK init event reported tools as `Edit`, `Read`, `Write`.
- SDK init event reported `apiKeySource: ANTHROPIC_API_KEY`, because CodeAI passes the resolved Kimi key to Claude Code through that environment variable.
- Short prompt returned the exact final visible text `KIMI_CLAUDE_CODE_PROBE_OK`.
- The short probe completed with `stopReason=end_turn`.
- Measured short probe: `63` stream messages, `41` thinking deltas, elapsed about `5.5s`.

Important caveat:

- Even with `settingSources: []` and a minimal tool list, Claude Code still advertises built-in slash commands, agents and skills in the init event. The provider-visible executable tool list was restricted to `Edit`, `Read`, `Write`, but the broader Claude Code runtime surface is not empty.

### 11.2. Tool-loop probe

Result after extended checks: **passed with constraints**.

Initial observed facts:

- Probe used a temporary directory under `/tmp/kimi-claude-code-probe-*`, not the repository.
- Prompt asked the model to create `probe.txt` with exact content `KIMI_TOOL_OK` through the `Write` tool.
- First attempt stayed running for more than a minute with no file created and had to be killed.
- Second attempt used `thinking: { type: "disabled" }`, `maxTurns: 2`, `maxBudgetUsd: 0.05`, and an SDK abort controller at `60s`; it still did not create the file and ended as an aborted Claude Code process.
- The temporary probe directories remained empty.

Follow-up checks:

- A minimal Claude Code tool prompt without the full CodeAI workflow system prompt successfully emitted `tool_use: Write`, created `probe.txt`, and returned `DONE`.
- A CodeAI workflow-style prompt with an explicit absolute target path successfully emitted `tool_use: Write`, created the exact target file, and returned `DONE`.
- When the prompt said only "current directory", Kimi sometimes chose `/tmp/probe.txt` rather than the SDK `cwd`; therefore CodeAI prompts must continue to provide the full absolute target artifact path.
- `thinking: { type: "disabled" }` produced no thinking deltas and completed normally.
- `thinking: { type: "adaptive", display: "summarized" }` produced thinking deltas normally.
- If SDK `title` is omitted, Claude Code may generate an `ai-title` and report an additional `claude-haiku-4-5-20251001` usage entry. Passing an explicit `title` removed that extra usage key; only `kimi-for-coding` remained.

Decision:

- Product integration may continue if Kimi-Claude-Code query options enforce:
  - explicit SDK `title`;
  - absolute target artifact paths in Core workflow prompts;
  - `settingSources: []`;
  - minimal tool list;
  - thinking options derived from provider settings, including real disabled mode.
- Usage/context telemetry must treat Claude Code auto-title/modelUsage side effects as a risk and keep explicit title enabled for this provider.

### 11.3. Product integration live smoke

Result: **passed**.

Observed facts:

- Kimi-Claude-Code live smoke used the built `packages/Claude_Module/dist` runtime, Claude Agent SDK `0.2.140`, `ANTHROPIC_BASE_URL=https://api.kimi.com/coding`, model `kimi-for-coding`, `settingSources: []`, tools `Read`, `Write`, `Edit`, and an explicit SDK `title`.
- Kimi-Claude-Code returned the exact visible assistant text `KIMI_CLAUDE_CODE_LIVE_SMOKE_OK`.
- Kimi-Claude-Code stream completed with `22` SDK messages and included `assistant` and `result` events.
- Kimi-Claude-Code auth was resolved from `~/.kimi/config.toml`; the API key was not logged.
- Native Kimi Wire smoke used `KimiProviderAdapter`, created a runtime session, sent a short prompt, emitted `turn_started`, `step_started`, `status_update`, `thinking`, `assistant`, and `turn_completed`, then closed the session.
- Native Kimi returned the exact visible assistant text `KIMI_NATIVE_LIVE_SMOKE_OK`.
- Native Kimi emitted `204` thinking characters on the short prompt, confirming the Wire reasoning path still works independently of the Claude Code-compatible variant.

Decision:

- Both provider variants are runnable from the current build artifacts and can return visible final text.
- Kimi-Claude-Code remains suitable for user retest in the next release as a separate comparison provider, not as a replacement for native Kimi.
