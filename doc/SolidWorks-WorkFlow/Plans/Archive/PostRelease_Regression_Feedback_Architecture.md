# Post-Release Regression Feedback Loop — Architecture Contract

**Status:** Active planning doc
**Updated:** 2026-03-22
**Owner:** Oleksandr

---

## Scope

Этот документ задаёт рабочую рамку для следующего post-release scope после `1.1.762`.

Цель:
- собирать живой regression feedback по агентам на текущем релизе;
- отделять реальные системные проблемы от особенностей пользовательского ввода;
- вносить только минимально необходимые правки в prompt/help/template/DoD/runtime surfaces;
- не открывать новый cleanup или redesign без наблюдаемого повода;
- завершить scope только после следующего локального релиза с подтверждённым regression baseline.

---

## Problem statement

После `Phase 26` и релиза `1.1.762` активный workflow очищен от product-visible legacy `Idea / Idea Collector` semantics.

Следующая задача уже не в naming cleanup, а в качестве поведения агентов на реальном regression pass:
- какие вопросы задаёт агент;
- как он обновляет артефакт;
- где help/prompt/template/DoD расходятся с фактическим поведением;
- какие места ещё провоцируют drift, лишние допущения, meta-комментарии в артефактах или потерю пользовательского смысла.

Эти проблемы нельзя качественно добить спекулятивно. Источником входа должен стать реальный пользовательский feedback по цепочке:

`Description -> Virtual Simulation -> Diagram Modules -> Diagram Facades`

---

## Input sources for this scope

Допустимыми входами для решений в этом scope считаются:
- сообщения агента в диалоге;
- промежуточные версии артефактов;
- финальные артефакты stage chain;
- наблюдения пользователя по help/runtime surface;
- расхождения между ожидаемым DoD шага и фактическим результатом.

Недостаточно одного общего впечатления вроде «выглядит слабее».
Нужен конкретный наблюдаемый кейс: вопрос, формулировка, абзац артефакта, drift между surface-слоями или неправильный stop-condition.

---

## Classification model

### A. User-input issue

Проблема возникает потому, что:
- пользователь не дал нужный факт;
- пользователь сам выбрал слабую или неполную формулировку;
- агент в целом сработал в рамках контракта.

Для этой категории систему не меняем.

### B. Prompt / template / DoD issue

Проблема возникает потому, что:
- агент не дожимает нужную форму артефакта;
- агент задаёт лишние или слабые вопросы;
- prompt разрешает drift или не запрещает нежелательный стиль;
- help/template/DoD не закрепляют нужный результат.

Для этой категории исправление допустимо и желательно.

### C. Runtime / UI / contract drift

Проблема возникает потому, что:
- help, runtime validation, HTTP contract, template или UI copy говорят разное;
- один и тот же шаг имеет несколько truth-sources;
- фактическое поведение не совпадает с declared surface.

Для этой категории исправление обязательно делать в сторону одного источника правды.

### D. Non-issue / expected behavior

Наблюдение выглядит непривычно, но не нарушает контракт и не ухудшает результат.

Для этой категории фикс не нужен.

---

## Decision rules

1. Меняем систему только для категорий `B` и `C`.
2. Каждый accepted finding должен быть локализован до минимального слоя:
   - prompt;
   - help;
   - template;
   - validator/runtime contract;
   - SSOT/docs.
3. Если проблема ограничена одним stage, не делаем cross-stage cleanup без доказанной связи.
4. Если проблема касается артефакта, сначала проверяем, что это не следствие слабого пользовательского ввода.
5. Новый release собираем только после того, как набор принятых правок реально закрывает наблюдаемые кейсы.

## Execution shape

### 1. Regression intake
- пользователь тестирует `1.1.762` и приносит живые наблюдения;
- каждое наблюдение классифицируется по модели выше;
- в план попадают только accepted system-level findings.

### 2. Minimal fix design
- для каждого accepted finding выбирается минимальный исправляющий surface;
- микро-задача не должна затрагивать больше `3` файлов;
- все правки должны быть проверяемы на конкретном regression кейсе.

### 3. Fix execution
- сначала stage-local fix;
- затем связанные docs/SSOT обновления;
- затем таргетная верификация.

### 4. Release and re-test
- после закрытия принятых фиксов собирается новый локальный релиз;
- regression baseline обновляется новым session report;
- следующий проход снова оценивается по реальным артефактам и сообщениям агента.

---

## Non-goals

В этот scope не входит:
- новый большой naming cleanup вне наблюдаемого regression повода;
- speculative refactor внутренних helper-слоёв без подтверждённой пользы;
- redesign workflow или stage chain;
- массовое переписывание prompts «на всякий случай» без конкретного кейса.

## Exit criteria

Scope считается закрытым, когда одновременно выполнено следующее:
1. Все принятые system-level findings из текущего regression pass реализованы или сознательно отклонены с пояснением.
2. `todo-plan.md` переписан из intake-режима в конкретные микро-задачи по фактическим находкам.
3. Собран следующий локальный релиз.
4. Создан новый session report с обновлённым regression baseline.
