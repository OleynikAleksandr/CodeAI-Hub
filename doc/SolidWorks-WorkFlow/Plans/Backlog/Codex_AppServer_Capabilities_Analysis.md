## 1. Введение: текущая интеграционная поверхность Codex

У OpenAI есть коммерческий продукт — коде-агент Codex (модель + утилита `codex`). Сам агент один и тот же, но у него есть **несколько разных «дверей», через которые к нему можно подключиться** из внешнего приложения:

1. **Codex CLI** — консольная команда `codex` для ручного запуска из терминала.
2. **Codex TypeScript SDK** — npm-пакет `@openai/codex-sdk`, который позволяет запускать Codex из Node.js-кода.
3. **Codex App Server** — долгоживущий серверный процесс `codex app-server`, с которым клиентское приложение общается по сетевому протоколу (JSON-RPC).
4. **Codex MCP Server** — альтернативная «дверь» для клиентов, использующих стандарт Model Context Protocol.
5. **Codex Cloud / Web** — облачный режим (нас сейчас не касается).

Для CodeAI Hub актуальна только одна из них: **Codex App Server**. Ядро раньше работало через TypeScript SDK, но этот путь закрыт как основной: мы полностью перешли на App Server и дальше рассматриваем SDK только как историческое сравнение, чтобы понимать, какие product-level возможности стали доступны.

### 1.1. Что говорит сама OpenAI

Ключевая цитата из официальной документации:

> «Codex App Server will be the first-class integration method maintained moving forward, and is the recommended approach for clients integrating with Codex».

Перевод простым языком: **App Server — это тот способ интеграции, который OpenAI называет основным и который они собираются развивать дальше**. На нём же построены собственные клиенты OpenAI — VS Code extension Codex и терминальный TUI. Новый Python SDK OpenAI уже сам является клиентом App Server, а не самостоятельной обёрткой над CLI.

TypeScript SDK по сути остаётся «тонкой обёрткой над CLI» — он запускает бинарь `codex` и обменивается с ним JSONL-событиями через stdin/stdout. Он удобен для автоматизации и CI, но имеет минимальную поверхность API. Для нашего интерактивного продукта он больше не является целевой интеграционной поверхностью.

## 2. Codex TypeScript SDK — что это и чего в нём нет

### 2.1. Как устроен

TypeScript SDK (`@openai/codex-sdk`) — это npm-пакет, который внутри себя:

- скачивает/использует установленный бинарь `codex`;
- на каждый запуск спавнит процесс `codex exec`;
- отдаёт ему ввод через stdin, читает стрим JSONL-событий через stdout;
- превращает это в удобные JS-объекты для вашего кода.

Требования: Node.js 18+, установленный Codex.

### 2.2. Что умеет (полная публичная поверхность)

Публичный API SDK — сознательно минимальный:

- `codex.startThread({ workspace, sandboxMode, skipGitRepoCheck, ... })` — создать новую сессию (тред) с агентом.
- `thread.run("prompt")` — выполнить один запрос и получить финальный результат.
- `thread.runStreamed("prompt")` — выполнить запрос и получать промежуточные события (часть инструментальных вызовов, часть текстовых дельт).
- `codex.resumeThread(threadId)` — восстановить сессию по сохранённому идентификатору.
- `outputSchema` — передать JSON-схему, чтобы получить структурированный ответ.
- Прикрепление картинок через аргумент CLI `--image` (при запуске CLI SDK просто пробросит пути в команду).

Всё. Это весь публичный API.

### 2.3. Чего принципиально нет в SDK

Эти вещи либо полностью отсутствуют, либо недоступны через публичный API SDK:

- Нет нативного понятия **approval** (подтверждений опасных действий). Стоп-кнопка работает грубо — SIGTERM подпроцессу.
- Нет собственного MCP-управления (подключение своих инструментов, OAuth и т.п.).
- Нет доступа к диффам/планам агента как к отдельным потокам событий.
- Нет операций fork / rollback / compact / archive над сессиями.
- Нет server-initiated уведомлений (сервер не может «постучаться» клиенту — только клиент шлёт запросы).
- Нет отдельного API конфигурации, моделей, скиллов, фич, маркетплейсов.
- Нет авторизации через ChatGPT-подписку пользователя как поддерживаемого сценария в публичном API.
- Нет информации о rate limits в живом режиме.
- Нет «steer» активного turn (добавить ввод в уже исполняющийся запрос без остановки).

**Важный вывод**: SDK спроектирован для сценариев «запусти и забудь» — CI-пайплайны, скрипты, серверная автоматизация. Он не рассчитан на богатый интерактивный UI продукта.

## 3. Codex App Server — что это и почему именно он

### 3.1. Как устроен

App Server — это **долгоживущий серверный процесс** `codex app-server`, который:

- Запускается один раз на машине.
- Общается с клиентским приложением (нашим CodeAI Hub) по протоколу **JSON-RPC 2.0**.
- Поддерживает **двунаправленную** связь: и клиент может спросить сервер, и сервер может по собственной инициативе прислать уведомление (например, попросить подтверждение на выполнение команды).
- Транспорт по умолчанию — **stdio** (построчный JSON). Есть экспериментальный **WebSocket**.
- Управляет всеми сессиями, авторизацией, MCP-серверами, подключёнными приложениями и плагинами, sandbox-политиками.

### 3.2. Три фундаментальных понятия

Вся работа App Server построена на трёх примитивах:

- **Thread (тред)** — устойчивая сессия разговора с агентом. Живёт между запусками, сохраняется на диск, имеет имя, статус, историю.
- **Turn (тёрн)** — один «раунд» внутри треда: от сообщения пользователя до завершения работы агента.
- **Item (айтем)** — атомарная единица внутри турна. Это может быть сообщение пользователя, сообщение агента, план, шаг рассуждения, вызов инструмента, запрос на подтверждение, diff файла и так далее. У каждого айтема жизненный цикл: `started` → (потоковые `delta`) → `completed`.

Эта модель принципиально **богаче**, чем у SDK: у SDK есть только «тред» и «прогон», а всё остальное — плоский поток событий без типизированного жизненного цикла.

### 3.3. Схемы и совместимость

OpenAI встроила в App Server команды генерации типов клиента:

- `codex app-server generate-ts --out DIR` — сгенерировать TypeScript-определения протокола.
- `codex app-server generate-json-schema --out DIR` — сгенерировать JSON Schema.

Это значит, что **наш код клиента не нужно поддерживать вручную** — типы можно регенерировать под каждую версию Codex. Плюс OpenAI формально гарантирует обратную совместимость: новые поля и методы добавляются, старых клиентов не ломают, подавить лишние уведомления можно через `optOutNotificationMethods` в `initialize`.

## 4. Что мы уже используем сегодня (базовая поверхность)

Чтобы понимать «сверх чего» идёт остальной список, зафиксируем минимум, который у нас уже работает через App Server:

- Создание и возобновление сессии: `thread/start`, `thread/resume`.
- Запуск и отмена турна: `turn/start`, `turn/interrupt`.
- Получение информации о лимитах: `account/rateLimits/read`.
- Часть item-дельт: текстовые дельты ответа `item/agentMessage/delta`, дельты рассуждений `item/reasoning/summaryTextDelta` и `item/reasoning/textDelta`.
- Уведомления о жизненном цикле турна: `turn/started`, `turn/completed`, ошибки турна.
- Уведомления о токен-юсадже и rate limits: `thread/tokenUsage/updated`, `account/rateLimits/updated`.
- Изолированный `CODEX_HOME` провайдера: App Server стартует с `CODEX_HOME=~/.codeai-hub/providers/codex/home`, а не с пользовательским `~/.codex`.

Что важно: наша текущая интеграция **пока не передаёт** `baseInstructions` и `developerInstructions` в `thread/start` / `thread/resume`, и **пока не управляет** `model_instructions_file` для обычных Codex-сессий. То есть переход на App Server уже завершён, но самый интересный слой динамических стартовых инструкций ещё не использован.

Этого хватает, чтобы иметь полноценный чат с агентом, стримингом текста и рассуждений, с отменой и с информацией об использовании. Ниже — всё, что к этому можно докрутить, не меняя базовую архитектуру.

## 5. Полный каталог дополнительных возможностей

Ниже — сгруппированный список того, что уже доступно через App Server и чего у нас ещё нет в продукте. Каждая группа начинается с простого объяснения «зачем это вообще», дальше — конкретные методы и выгоды для пользователя.

### 5.1. Расширенное управление тредами (сессиями)

**Что такое тред простым языком**: это одна «ветка разговора» с агентом — как отдельный чат в мессенджере. Имеет название, историю, можно закрыть и позже открыть обратно.

**Что даёт App Server сверх «создать и возобновить»**:

- **`thread/fork`** — ветвление треда. Берём существующий тред и делаем его копию под новым идентификатором. В UI это «попробовать иначе, не теряя текущий результат»: пользователь видит, что агент пошёл не туда, форкает сессию на предыдущем шаге и пробует другой путь. Старый тред остаётся нетронутым, новый идёт параллельно.

- **`thread/rollback`** — откат последних N турнов. По сути «Undo» для чата с агентом. В UI — кнопка «отменить последние N шагов». Полезно, если агент сделал что-то ненужное и нам проще откатить историю, чем отменять вручную.

- **`thread/compact/start`** — асинхронная компактация (сжатие) истории. Когда разговор становится длинным, он перестаёт влезать в context window модели. Компактация автоматически превращает старую часть разговора в сжатую сводку. В UI — индикатор «идёт сжатие истории», после чего с треда можно продолжать работать без ошибок переполнения контекста.

- **`thread/list`** — список всех сохранённых тредов с фильтрами и пагинацией. Можно фильтровать по провайдеру модели, типу источника, архивности, рабочей директории, сортировать по дате создания или обновления. В UI — полноценная «боковая панель сессий», где пользователь видит все свои прошлые чаты и умеет в них искать.

- **`thread/read`** — прочитать содержимое треда без «прогрева» сессии в память. С параметром `includeTurns` можно получить всю историю. В UI — быстрый просмотр истории треда в «pre­view» без запуска реальной сессии (экономит ресурсы).

- **`thread/loaded/list`** — список тредов, которые сейчас живы в памяти сервера. Нужно для сценариев, где несколько клиентов подключаются к одному App Server (например, веб + desktop).

- **`thread/archive`** и **`thread/unarchive`** — архивирование сессий. В UI — «убрать из списка, но не удалять», с возможностью восстановления.

- **`thread/unsubscribe`** — отписаться от уведомлений треда. Если к треду подключены несколько клиентов, отписка одного из них не останавливает работу. Когда отписывается последний — сервер эмитит `thread/closed` и сессия выгружается из памяти.

- **`thread/name/set`** + уведомление **`thread/name/updated`** — дать треду человекочитаемое имя, которое видно в списке.

- **`thread/status/changed`** — уведомление о смене статуса треда (`notLoaded`, `idle`, `systemError`, или `active` с `activeFlags`). Позволяет в UI показывать, чем занят тред прямо сейчас.

- **`thread/inject_items`** — программно добавить айтемы в тред (для служебных сценариев).

- **`thread/shellCommand`** — выполнить shell-команду от имени пользователя вне песочницы (полный доступ). Используется в сценариях, где нужно дать пользователю возможность явно, под своим контролем, запустить что-то в его системе.

- **`thread/backgroundTerminals/clean`** (экспериментальный) — остановить все запущенные фоновые терминалы в треде.

### 5.2. Управление ходом выполнения турна

**Что такое турн простым языком**: это одна итерация взаимодействия — от того, как пользователь нажал Enter, до момента, когда агент сказал «готово». В SDK у нас есть только «старт» и «отмена». App Server даёт гораздо больше.

- **`turn/steer`** — добавить новый ввод пользователя в уже исполняющийся турн, **не прерывая его**. В UI это выглядит так: пока агент печатает ответ, пользователь замечает, что забыл важную деталь, и добавляет её прямо на ходу. Старт нового турна при этом не происходит, агент подхватывает уточнение и продолжает. Требуется указать `expectedTurnId`, чтобы избежать гонок.

- **`turn/diff/updated`** — сервер присылает **актуальный сводный diff** по всем файловым изменениям текущего турна в унифицированном формате. В UI — боковая панель «что агент собирается изменить», обновляющаяся в реальном времени, с подсветкой добавленных/удалённых строк. Это одна из самых заметных фич Codex VS Code extension.

- **`turn/plan/updated`** — сервер присылает **актуальный план работы** агента: список шагов с явным статусом (`pending`, `inProgress`, `completed`). В UI — чек-лист «что агент планирует сделать / что уже сделал». Пользователь видит прогресс не только по тексту ответа, но и по структурированному плану.

- **Per-turn overrides** — при старте турна можно переопределить параметры **только для этого турна**, без пересоздания треда: `model`, `effort` (глубина рассуждений), `personality`, `cwd`, `sandboxPolicy`, `summary` (режим сводки reasoning), `collaborationMode`, `outputSchema`. В UI — быстрое переключение «для этого ответа ответь более глубоко» или «для этого ответа используй другую модель», без создания новой сессии.

### 5.3. Полноценная система подтверждений (Approvals)

**Зачем это нужно простым языком**: агент может попытаться выполнить команду в терминале, изменить файлы на диске, сходить в интернет. Для многих из этих действий правильно **спросить пользователя**: «разрешаете?». Это и есть approval-поток. В SDK он по-настоящему не поддержан — там есть только грубая остановка подпроцесса. App Server даёт полноценный интерактив.

Как работает поток:

1. Агент создаёт айтем, требующий подтверждения: `item/started` с типом `commandExecution` или `fileChange`.
2. Сервер по собственной инициативе шлёт клиенту запрос: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval` или `item/permissions/requestApproval`.
3. Клиент (наш UI) показывает пользователю карточку с описанием предлагаемого действия и кнопками выбора.
4. Клиент отвечает одним из вариантов: `accept`, `acceptForSession` (разрешить всему этому треду), `decline`, `cancel`, `amendExecPolicy` (разрешить с правкой политики).
5. Сервер подтверждает решение уведомлением `serverRequest/resolved`.
6. Айтем завершается `item/completed` с финальным статусом.

**Что важно знать об approvals в деталях**:

- В запросе на подтверждение команды приходят: `reason` (почему агент хочет её запустить), `command`, `cwd`, список `commandActions`, опционально `proposedExecpolicyAmendment` (предложение агента «давай добавим правило, чтобы в будущем не спрашивать»).
- Есть `networkApprovalContext` — контекст «агент хочет сходить в сеть на такой-то host по такому-то протоколу». Сервер **группирует** одновременные запросы по одному и тому же destination, чтобы пользователь не кликал «разрешить» 30 раз подряд.
- В запросе на изменение файлов приходят: причина, список предлагаемых изменений `changes`, опциональное `grantRoot` (расширение прав на корень).
- С флагом `capabilities.experimentalApi: true` приходит и `additionalPermissions` — детализация, какие именно права в sandbox нужны для конкретной команды.

В UI это выглядит как привычная по VS Code карточка подтверждения с описанием действия, опциями «Allow», «Allow for session», «Deny» — плюс более тонкая настройка политик, если нужно.

### 5.4. Встроенный Review mode (AI code review)

**Зачем это нужно простым языком**: отдельный сценарий, когда пользователь хочет, чтобы агент **не писал код**, а **прочитал и прорецензировал** существующий. В Codex это оформлено как самостоятельный режим.

- **`review/start`** — запуск ревью с выбором target:
  - `uncommittedChanges` — отрецензировать всё, что сейчас не закоммичено.
  - `baseBranch` — отрецензировать разницу с базовой веткой.
  - `commit` — отрецензировать конкретный коммит.
  - `custom` — произвольный сценарий.
- **Delivery** — способ доставки результата:
  - `inline` — добавить ревью в текущий тред.
  - `detached` — открыть **новый тред** под ревью и не засорять текущий разговор.
- Жизненный цикл отмечается айтемами `enteredReviewMode` и `exitedReviewMode` с финальным текстом ревью.

В UI — кнопка «Ask Codex to review this change» на panel с diff или в panel git. Результат приходит как отдельное окно ревью с комментариями.

### 5.5. Первоклассная интеграция с MCP (Model Context Protocol)

**Зачем это нужно простым языком**: MCP — это открытый стандарт, по которому внешние «инструменты» (базы знаний, плагины, коннекторы к сервисам) могут быть подключены к AI-агенту. Если пользователь поставил себе MCP-сервер (например, доступ к его базе Notion или к его внутренней wiki), то агент сможет им пользоваться.

В SDK прямого управления MCP нет. App Server предоставляет **полноценный surface**:

- **`mcpServerStatus/list`** — список настроенных MCP-серверов с их состоянием (подключён / не подключён / ошибка), списком доступных инструментов, ресурсов и статусом авторизации. Поддерживает `detail: "full"` или `"toolsAndAuthOnly"`, курсорную пагинацию. В UI — страница «MCP Servers» со статусом каждого.
- **`mcpServer/oauth/login`** — запуск OAuth-логина в MCP-сервер. Возвращает `authUrl`, который наш UI открывает в браузере. По завершении сервер шлёт уведомление **`mcpServer/oauthLogin/completed`**.
- **`config/mcpServer/reload`** — перечитать конфигурацию MCP с диска. Нужно, если пользователь вручную отредактировал `config.toml` и хочет применить без перезапуска.
- **`mcpServer/resource/read`** — прочитать один ресурс через уже подключённый MCP-сервер.
- **`mcpServer/tool/call`** — вызвать конкретный MCP-инструмент напрямую.
- **`mcpServer/startupStatus/updated`** — уведомление об изменении состояния MCP-сервера (запустился / упал).

Дополнительно App Server даёт surface **приложений и плагинов** (экосистема Codex):

- **`app/list`** — список доступных приложений (коннекторов) с фильтрацией по `threadId`, флагом `forceRefetch`, метаданными, брендингом, `isAccessible`, `isEnabled`.
- **`plugin/list`**, **`plugin/read`**, **`plugin/install`**, **`plugin/uninstall`** — управление плагинами из маркетплейсов: список магазинов, чтение конкретного плагина (с бандл-скиллами/коннекторами/MCP-серверами), установка, удаление.
- **`marketplace/add`** — добавление нового маркетплейса.
- Пользователь может упомянуть приложение в запросе через синтаксис `$app-slug`, а в структурированном вводе — через айтем `{ "type": "mention", "name": "App Name", "path": "app://id" }`.

### 5.6. Skills (навыки агента)

**Зачем это нужно простым языком**: skill — это именованный набор инструкций/знаний, который можно подключить к агенту для решения определённого класса задач (например, «работа с нашим внутренним API»).

- **`skills/list`** — получить список навыков, релевантных для одного или нескольких `cwd`. Поддерживает `forceReload`, дополнительные корневые директории через `perCwdExtraUserRoots`. Возвращает интерфейс каждого скилла и его зависимости.
- **`skills/config/write`** — включить/выключить скилл по пути. В UI — переключатели «какие скиллы сейчас активны для этого проекта».
- **`skills/changed`** — уведомление, что набор скиллов изменился (например, пользователь добавил новый).
- В ввод турна можно передать айтем `{ "type": "skill", "name": "skill-name", "path": "..." }` параллельно с упоминанием `$skill-name` в тексте. Это гарантирует, что инструкции скилла будут инжектированы в контекст без надежды на то, что модель сама их найдёт.

### 5.7. Управление конфигурацией и enterprise-ограничения

**Зачем это нужно простым языком**: в корпоративной среде администратор хочет централизованно задавать политики (какие модели разрешены, какой sandbox допустим), а клиент Codex должен эти политики уважать.

- **`config/read`** — прочитать эффективную конфигурацию Codex. С `includeLayers` — увидеть, из каких слоёв конфигурации (глобальной, пользовательской, проектной) пришло каждое значение.
- **`config/value/write`** — записать один ключ в `config.toml`. `mergeStrategy: "replace"` или `"upsert"`.
- **`config/batchWrite`** — атомарно применить несколько правок.
- **`configRequirements/read`** — прочитать административные требования из `requirements.toml` или MDM (Mobile Device Management для корпоративных машин): `allowedApprovalPolicies`, `allowedSandboxModes`, `featureRequirements`, сетевые настройки. В UI — серые/заблокированные настройки с tooltip «Заблокировано администратором».

### 5.8. Discovery — модели, фичи, режимы

**Зачем это нужно простым языком**: вместо того чтобы нам самим вести списки моделей в коде или в настройках, можно спрашивать App Server «какие модели сейчас доступны, какие у них возможности».

- **`model/list`** — список моделей. Для каждой модели приходит: `supportedReasoningEfforts`, `defaultReasoningEffort`, `inputModalities` (какие типы ввода принимает — текст, картинка), `supportsPersonality`, `upgrade` (рекомендуемый upgrade), `hidden`, `isDefault`. В UI — выпадающий список моделей с иконками возможностей.
- **`experimentalFeature/list`** — список экспериментальных фич с lifecycle-стадиями: `beta`, `underDevelopment`, `stable`, `deprecated`, `removed`. Позволяет клиенту знать, что можно включать, а что уже помечено как deprecated.
- **`experimentalFeature/enablement/set`** — включить/выключить конкретную экспериментальную фичу.
- **`collaborationMode/list`** — список режимов совместной работы (экспериментально).

### 5.9. Богатые sandbox-политики

**Зачем это нужно простым языком**: sandbox — это «песочница», в которой агент может запускать команды. Нужно точно контролировать, что ему разрешено читать, писать, выходить ли в сеть.

Поддерживаются политики:

- **`dangerFullAccess`** — без ограничений. Используем только когда пользователь явно согласился.
- **`readOnly`** — только чтение. Опционально с `access: restricted` + `readableRoots` (можно читать только эти директории).
- **`workspaceWrite`** — можно писать в рабочие корни, опционально с `readOnlyAccess` ограничением и отдельным флагом `networkAccess` (разрешён ли выход в сеть).
- **`externalSandbox`** — пропустить собственное песочницы Codex, если родительский процесс (наш CodeAI Hub) уже изолирует. Значение `networkAccess` может быть `restricted` или `enabled`.

Специфика для macOS: при `includePlatformDefaults: true` добавляется курированная Seatbelt-политика, совместимая с системой. Это избавляет нас от необходимости самим писать platform-specific правила.

### 5.10. Command Exec API — исполнение команд вне треда

**Зачем это нужно простым языком**: иногда нужно запустить произвольную команду под sandbox-политикой Codex, не создавая новую сессию агента. Например, «прогони вот эти тесты» или «собери проект». App Server даёт для этого отдельный API.

- **`command/exec`** — запуск команды. Принимает `argv`, `cwd`, `sandboxPolicy`, `timeoutMs`, `tty` (включить ли эмуляцию терминала), `streamStdoutStderr` (стримить или вернуть буфером).
- **`command/exec/write`** — записать байты в stdin запущенного процесса или закрыть поток. Позволяет интерактивно кормить команду вводом.
- **`command/exec/resize`** — изменить размер PTY (псевдотерминала), если процесс запущен с `tty: true`.
- **`command/exec/terminate`** — остановить процесс.
- **`command/exec/outputDelta`** — уведомления с кусками stdout/stderr в реальном времени.

### 5.11. Файловая система v2

**Зачем это нужно простым языком**: вместо того чтобы нам из клиента напрямую лезть в диск и самим отслеживать изменения, можно делать это **через App Server** — под теми же политиками безопасности, что применяются ко всему остальному.

- **`fs/readFile`** — прочитать файл по абсолютному пути.
- **`fs/writeFile`** — записать файл.
- **`fs/createDirectory`** — создать директорию.
- **`fs/getMetadata`** — получить метаданные (размер, время модификации и т.п.).
- **`fs/readDirectory`** — список содержимого директории.
- **`fs/remove`** — удалить файл/директорию.
- **`fs/copy`** — копировать.
- **`fs/watch`** / **`fs/unwatch`** — подписаться/отписаться на изменения пути.
- **`fs/changed`** — уведомление об изменениях на подписанных путях.

### 5.12. Авторизация (Auth) по протоколу

**Зачем это нужно простым языком**: Codex можно использовать либо по API key (как «API подписка»), либо по ChatGPT-подписке пользователя. Второй сценарий хочется полноценно поддерживать, потому что именно через него продукт становится доступным широкому кругу пользователей без отдельной оплаты.

Поддерживаемые режимы:

- **`apikey`** — клиент передаёт OpenAI API key. Подходит для корпоративных и разработческих сценариев.
- **`chatgpt`** — Codex сам управляет OAuth-входом в ChatGPT и сам рефрешит токены. Наиболее удобный для пользователя режим.
- **`chatgptAuthTokens`** — клиентское приложение (CodeAI Hub) само владеет токенами `idToken`/`accessToken` и передаёт их серверу. При истечении сервер по собственной инициативе шлёт запрос **`account/chatgptAuthTokens/refresh`**, на который клиент должен ответить свежими токенами.

Методы управления:

- **`account/read`** — прочитать текущее состояние аккаунта, опционально с принудительным рефрешем токенов. Вернёт тип аккаунта или `null`, если не авторизован.
- **`account/login/start`** — начать логин (apiKey / chatgpt / chatgptAuthTokens).
- **`account/login/cancel`** — отменить начатый ChatGPT-логин по `loginId`.
- **`account/logout`** — выход.
- **`account/rateLimits/read`** — прочитать текущие лимиты ChatGPT. Возвращает single-bucket представление и multi-bucket (по `limitId`).
- **`account/sendAddCreditsNudgeEmail`** — отправить пользователю письмо «пополни кредиты» (если применимо).

Уведомления:

- **`account/login/completed`** — успех или ошибка с `loginId`.
- **`account/updated`** — сменился режим авторизации.
- **`account/rateLimits/updated`** — лимиты изменились (используется для живой индикации остатка в UI).

### 5.13. Типы item'ов, которые мы сейчас не обрабатываем

**Зачем это нужно простым языком**: агент производит разные «сущности» в ходе работы — не только текст. У каждой сущности есть свой айтем-тип, и, обрабатывая его, мы можем показать пользователю богатый UI вместо сырого текста.

Полный список типов айтемов и что с ними можно делать:

- **`userMessage`** — сообщение пользователя (базовое, уже используется).
- **`agentMessage`** — финальный текстовый ответ агента (базовое, уже используется).
- **`plan`** — структурированный план работы агента (с `item/plan/delta` + `turn/plan/updated`). UI: чек-лист шагов со статусами.
- **`reasoning`** — цепочка рассуждений (с `item/reasoning/summaryTextDelta` и `item/reasoning/textDelta`). UI: раскрывающийся блок «как агент думал».
- **`commandExecution`** — запуск терминальной команды (с `item/commandExecution/outputDelta`). UI: live-окно терминала с потоковым выводом.
- **`fileChange`** — изменение файла (с `item/fileChange/outputDelta`, ответом от `apply_patch`). UI: diff-viewer для каждого изменённого файла.
- **`mcpToolCall`** — вызов MCP-инструмента. UI: карточка «вызван инструмент X, параметры Y, результат Z».
- **`dynamicToolCall`** — вызов динамического инструмента, исполняемого на стороне клиента (экспериментально). Даёт фреймворк «мы можем добавить свои инструменты, которые агент сможет вызывать».
- **`collabToolCall`** — вызов в рамках collaboration mode.
- **`webSearch`** — веб-поиск. UI: список цитат и источников.
- **`imageView`** — просмотр картинки (агент показывает изображение).
- **`enteredReviewMode`** / **`exitedReviewMode`** — вход в ревью-режим и его завершение.
- **`contextCompaction`** — агент сжал историю (см. раздел про `thread/compact/start`).

### 5.14. Динамические инструменты и пользовательский ввод (experimental)

**Зачем это нужно простым языком**: иногда агенту не хватает информации, и ему нужно **спросить пользователя** — не «подтвердить», а именно «уточнить». Или мы хотим сами давать агенту инструменты, которые он сможет вызывать.

- **`tool/requestUserInput`** — сервер просит пользователя ответить на 1–3 вопроса прямо в UI. Каждый вопрос может поддерживать `isOther: true` для свободного ввода. В UI — модальное окно с формой.
- Айтемы `dynamicToolCall` — наш клиент регистрирует «динамический инструмент» (например, «вызвать нашу внутреннюю функцию»), и агент может его вызывать так же, как обычный MCP-инструмент. Исполнение идёт на стороне клиента.

### 5.15. Realtime (голос, experimental)

**Зачем это нужно простым языком**: это совершенно отдельная линия продукта — работа с агентом голосом. Микрофон → агент → синтез речи в ответ.

- **`thread/realtime/start`** / **`thread/realtime/stop`** — начать и завершить realtime-сессию в треде.
- **`thread/realtime/appendAudio`** — отправить очередной кусок аудио с микрофона.
- **`thread/realtime/appendText`** — добавить текстовый ввод в realtime-сессию.
- **`thread/realtime/sdp`** — обмен SDP для WebRTC.
- **`thread/realtime/itemAdded`** — уведомление о новом айтеме.
- **`thread/realtime/transcript/delta`** / **`thread/realtime/transcript/done`** — потоковая транскрипция речи.
- **`thread/realtime/outputAudio/delta`** — потоковое аудио-выход агента.
- **`thread/realtime/error`** / **`thread/realtime/closed`** — ошибки и закрытие.

Это потенциал «голосового Codex», который при желании мы можем оформить как отдельную премиум-фичу.

### 5.16. Структурированный ввод турна

**Зачем это нужно простым языком**: вместо простой строки текста пользователь может прислать сложный ввод — с картинками, с упоминанием скиллов и приложений, с файлами.

Поддерживаемые типы ввода в `turn/start`:

- **`{ "type": "text", "text": "..." }`** — обычный текст.
- **`{ "type": "image", "url": "https://..." }`** — картинка по URL.
- **`{ "type": "localImage", "path": "/tmp/..." }`** — картинка с локального диска.
- **`{ "type": "skill", "name": "skill-name", "path": "..." }`** — явная инъекция инструкций скилла (парится с `$skill-name` в тексте).
- **`{ "type": "mention", "name": "App Name", "path": "app://id" }`** — упоминание приложения/коннектора (парится с `$app-slug` в тексте).

### 5.17. Инфраструктурные операции

- **`windowsSandbox/setupStart`** + уведомление **`windowsSandbox/setupCompleted`** — автоматическая настройка Windows Sandbox в режиме `elevated` или `unelevated`. Асинхронная — команда возвращает управление сразу, результат придёт уведомлением с `{ mode, success, error }`.
- **`externalAgentConfig/detect`** — найти конфигурацию других агентов на диске: `AGENTS_MD` (файл с инструкциями для агента), `CONFIG`, `SKILLS`, `MCP_SERVER_CONFIG`. С флагами `includeHome` и `cwds`.
- **`externalAgentConfig/import`** — применить найденные элементы миграции атомарно. Это путь «пришёл пользователь от другого агента — плавно перенесли настройки».
- **`feedback/upload`** — отправить отчёт с обратной связью: классификация, причина, логи, `conversationId`, опциональный `extraLogFiles`. В UI — кнопка «Send feedback».
- **`serverRequest/resolved`** — техническое уведомление, что клиент обработал server-initiated запрос.

### 5.18. Транспорт, версионирование, безопасность протокола

- **stdio-транспорт (по умолчанию)** — newline-delimited JSON через stdin/stdout.
- **WebSocket-транспорт (экспериментальный)** — позволяет сценарий «App Server на одной машине, клиент на другой». Запускается с флагами `--ws-auth capability-token`, `--ws-token-file`. Есть bounded queues, при перегрузке — JSON-RPC ошибка `-32001`. Loopback безопасен по умолчанию, удалённые listeners требуют явной конфигурации.
- **`initialize`-хендшейк** — обязательный первый запрос. Содержит `clientInfo` (имя, заголовок, версия нашего продукта — идёт в compliance-логи) и `capabilities`:
  - **`experimentalApi: true`** — разблокирует экспериментальные методы и поля.
  - **`optOutNotificationMethods: [...]`** — список уведомлений, которые мы НЕ хотим получать (снижаем шум).
- После `initialize` клиент должен прислать **`initialized`**-уведомление, и только после этого можно слать методы.
- **Генерация типов под конкретную версию** — `codex app-server generate-ts` и `generate-json-schema`. Гарантирует полную совместимость клиента и сервера.
- **Обратная совместимость** — формально гарантирована: новые поля добавляются, старые — сохраняются, новых уведомлений можно избегать через opt-out.

### 5.19. Управление стартовыми инструкциями и отключение лишнего контекста

**Зачем это нужно простым языком**: наши workflow-агенты не являются универсальным ассистентом «на всё». На шаге Description агент должен вести Description, на шаге Virtual Simulation — Virtual Simulation, на Diagram Modules — Diagram Modules. Поэтому стартовый контекст Codex должен быть максимально узким: минимум системного шума, короткая provider-level рамка и подробный первый запрос пользователя из нашего template.

Новые возможности, которые мы дополнительно проверили в локальной схеме app-server и исходниках `openai/codex`:

- **`thread/start.baseInstructions`** и **`thread/resume.baseInstructions`** — замена базовых model/system instructions для треда. Это thread-level override: задаётся при старте или resume сессии, а не как обычное сообщение пользователя.
- **`thread/start.developerInstructions`** и **`thread/resume.developerInstructions`** — developer-role инструкции для треда. Это правильное место для короткой, обязательной рамки workflow-агента: роль шага, границы источников, запрет уходить в соседние workflow stages.
- **`model_instructions_file`** — config/profile-level замена built-in instruction file. Это более тяжёлый рычаг, чем `baseInstructions`: он подходит для изолированного per-step `CODEX_HOME` или per-profile запуска. В upstream-коде OpenAI это поле явно помечено как рискованное при неосторожном использовании, потому что можно потерять важные harness/tool/safety инструкции.
- **`developer_instructions`** в config.toml — developer-role сообщение из конфигурации. Может быть полезно для provider-home defaults, но для наших workflow steps лучше thread-level `developerInstructions`, чтобы не менять весь provider home глобально.
- **`personality`** — только стиль общения (`none` / `friendly` / `pragmatic`). Это не замена инструкций и не инструмент для stage-specific workflow.
- **`collaborationMode.settings.developer_instructions`** — режимный developer-блок. Если `developer_instructions: null`, Codex использует built-in instructions выбранного mode; если строка задана, она становится developer-инструкцией режима. Для обычных workflow-агентов это вторичный механизм, а не основа.

Что можно отключать, чтобы убрать нерелевантный стартовый шум:

- **Global AGENTS discovery**: Codex читает `AGENTS.override.md` или `AGENTS.md` из `CODEX_HOME`. Наш provider home сейчас изолирован и не содержит такого файла.
- **Project AGENTS discovery**: Codex читает `AGENTS.override.md` / `AGENTS.md` по пути от project root до `cwd`. Полное отключение делается через `project_doc_max_bytes = 0`. `project_root_markers = []` останавливает подъём к родителям, но текущую директорию Codex всё равно проверит, поэтому для полного disable нужен именно нулевой лимит.
- **Skills instructions**: `[skills] include_instructions = false` отключает автоматическую инъекцию skill descriptions/instructions. Для нашего workflow это важно: stage-specific agent уже знает свою задачу из первого запроса пользователя, ему не нужно выбирать между несколькими skills.
- **Apps/plugins noise**: `features.apps = false`, `features.multi_agent = false` и отключение plugin/app surfaces уместны для узких workflow-агентов, если конкретный шаг не использует эти возможности.
- **Environment / permissions / apps blocks**: в config есть `include_environment_context`, `include_permissions_instructions`, `include_apps_instructions`. Эти блоки можно отключать только если мы осознанно заменяем их минимальной provider-level рамкой; нельзя просто вырезать tool/sandbox инструкции и оставить агенту доступ к инструментам без объяснения правил.

Отдельно: **Codex hooks** (`SessionStart`, `UserPromptSubmit`) могут вернуть `additionalContext`, который добавляется как extra developer context. Это полезно для инъекции динамического контекста, но это **append-only механизм**, а не замена base/system instructions. Через hooks нельзя «отключить» built-in инструкции, можно только добавить ещё один слой.

Практический вывод для CodeAI Hub:

1. Ввести provider-neutral `WorkflowInstructionProfile` для каждого шага (`description`, `virtual_simulation`, `diagram_modules`, далее development tree).
2. Для Codex при создании нового workflow-thread передавать:
   - `baseInstructions`: короткая минимальная рамка agent harness + CodeAI Hub workflow.
   - `developerInstructions`: конкретная роль шага и non-negotiable ограничения.
   - первый user message: полный template шага из `~/.codeai-hub/templates/...`.
3. Для шагов, где нужно максимально чистое окружение, запускать Codex с изолированным profile / provider home и `model_instructions_file`, но только после отдельной проверки, что мы не потеряли нужные tool/sandbox правила.
4. Не использовать skills как основной механизм выбора workflow-поведения. Skills полезны для универсального ассистента, а наши workflow-агенты уже специализированы.

### 5.20. Ошибки как данные

Когда турн завершается с ошибкой, в `turn/completed` приходит объект `error` с полем `codexErrorInfo`. Его варианты — готовый словарь для UX-обработки:

- **`ContextWindowExceeded`** — история не влезает в контекст модели. UX: предложить запустить компактацию.
- **`UsageLimitExceeded`** — исчерпан лимит. UX: показать «обновите план» или «подождите сброса лимита», с подсказкой когда.
- **`HttpConnectionFailed`** — проблема с соединением к API (4xx/5xx). Может содержать `httpStatusCode`.
- **`ResponseStreamConnectionFailed`** / **`ResponseStreamDisconnected`** — стрим ответа оборвался.
- **`ResponseTooManyFailedAttempts`** — слишком много неуспешных попыток подряд.
- **`BadRequest`** / **`Unauthorized`** / **`SandboxError`** / **`InternalServerError`** / **`Other`** — остальные категории.

В UI — разные текстовки и разные кнопки действий для каждой категории, вместо одной общей «что-то пошло не так».

## 6. Приоритеты для CodeAI Hub

Ниже — рекомендованный порядок внедрения. Отсортировано по соотношению «видимая польза пользователю / цена внедрения».

### Приоритет 0. Динамические стартовые инструкции для workflow-агентов

Это главный новый вывод после перехода на App Server.

0. **`WorkflowInstructionProfile` для Codex** — provider-neutral структура, которая раскладывается в `baseInstructions`, `developerInstructions`, config toggles и первый user prompt.
1. **Передача `baseInstructions` / `developerInstructions` в `thread/start` и `thread/resume`** — убрать противоречие между широкими системными инструкциями и узким первым запросом шага.
2. **Опциональное отключение AGENTS/skills/apps/env blocks** для узких workflow-сессий: `project_doc_max_bytes = 0`, `[skills] include_instructions = false`, отключение нерелевантных features.
3. **Проверочный debug-loop** через `codex debug prompt-input` в тестах/diagnostics — фиксировать, какой prompt реально видит модель для каждого workflow step.

### Приоритет 1. Делает продукт визуально сопоставимым с Codex VS Code

Это то, что пользователь заметит **сразу** при первом использовании.

1. **`turn/diff/updated`** — живой сводный diff по турну. Вывод в боковой панели.
2. **`turn/plan/updated`** — живой чек-лист шагов агента.
3. **Item `commandExecution` с `outputDelta`** — терминальная панель с потоковым stdout/stderr.
4. **Item `fileChange` с `outputDelta`** — diff-viewer для каждого изменённого файла отдельно.
5. **Полный approvals-поток** — карточки подтверждений для команд и файлов с вариантами `accept` / `acceptForSession` / `decline`.

### Приоритет 2. Экосистема и инструменты

Это то, что делает продукт расширяемым и подключает к нему экосистему.

6. **MCP surface** — `mcpServerStatus/list`, `config/mcpServer/reload`, OAuth-flow с `mcpServer/oauth/login`, `mcpServer/tool/call`, `mcpServer/resource/read`.
7. **Skills** — `skills/list` с per-cwd фильтрацией, `skills/config/write`, структурированный ввод скиллов в турне.
8. **Apps/plugins** — `app/list`, `plugin/list|read|install|uninstall`, `marketplace/add`. Позволяет пользователю устанавливать расширения.

### Приоритет 3. UX сессий

Это то, что делает работу с большими/долгими сессиями удобной.

9. **`thread/list` с фильтрами** — боковая панель всех сессий.
10. **`thread/fork`** — ветвление разговора.
11. **`thread/rollback`** — откат последних N турнов.
12. **`thread/compact/start`** — сжатие длинной истории.
13. **`thread/archive` / `unarchive`** — архивирование.
14. **`thread/name/set`** + `thread/name/updated` — именование тредов.
15. **`turn/steer`** — дополнение активного турна без перезапуска.

### Приоритет 4. Интеллект продукта (встроенные сценарии)

Отдельные ценные фичи, которые можно вынести отдельными кнопками.

16. **`review/start`** — встроенный AI code review с выбором target (uncommitted / baseBranch / commit) и delivery (inline / detached).
17. **Per-turn overrides** — «для этого ответа используй другую модель / более глубокое рассуждение».

### Приоритет 5. Инфраструктура и enterprise

Это важно для корпоративных клиентов и долгосрочной поддержки.

18. **`model/list`** — перестаём вести свой список моделей.
19. **`experimentalFeature/list`** + `experimentalFeature/enablement/set` — управляем экспериментальными фичами по серверу.
20. **`configRequirements/read`** — уважаем корпоративные политики.
21. **`config/read`** / **`config/value/write`** / **`config/batchWrite`** — редактирование `config.toml` из UI продукта.
22. **Auth полностью** — `chatgptAuthTokens` (наш хост владеет токенами), `account/login/*`, `account/rateLimits/updated` для живой индикации остатка.
23. **Ошибки как данные** — разная обработка `ContextWindowExceeded`, `UsageLimitExceeded`, `Unauthorized`, `HttpConnectionFailed`, `SandboxError` и т.д.

### Приоритет 6. Безопасные операции из клиента

Позволяют делать «хозяйственные» операции аккуратно, через сервер.

24. **Sandbox policies** — явное использование `workspaceWrite`, `readOnly` с `readableRoots`, `externalSandbox` (если мы сами изолируем).
25. **Command Exec API** — `command/exec`, `exec/write`, `exec/resize`, `exec/terminate`, `exec/outputDelta` для запуска произвольных команд под политикой из UI.
26. **Filesystem v2** — `fs/readFile|writeFile|createDirectory|getMetadata|readDirectory|remove|copy|watch|unwatch` и уведомления `fs/changed`.

### Приоритет 7. Долгосрочные и специальные возможности

Не обязательные к немедленному внедрению, но полезные в будущем.

27. **Dynamic tools** (`dynamicToolCall`) — собственные клиентские инструменты.
28. **`tool/requestUserInput`** — агент спрашивает уточнения через модалку.
29. **Realtime (голос)** — `thread/realtime/*` как отдельная линия продукта.
30. **WebSocket-транспорт** — remote-сценарии «сервер на одной машине, клиент на другой».
31. **Схемы как истина** — `generate-ts` / `generate-json-schema` в CI, чтобы наш типовой слой автоматически обновлялся.
32. **`externalAgentConfig/detect|import`** — импорт конфигурации из других агентов.
33. **`feedback/upload`** — встроенный фидбэк с extraLogFiles.
34. **`windowsSandbox/setupStart`** — автонастройка для Windows-пользователей.

### Что НЕ стоит делать в ближайшее время

- **Возвращаться к TypeScript SDK как fallback-интеграции** — текущая архитектура уже app-server-first, а SDK не даёт нужного нам управления thread lifecycle, approvals, инструкциями и UI-событиями.
- **Полностью заменять Codex built-in instructions без минимального harness-пакета** — `model_instructions_file` мощный, но опасный рычаг. Если его использовать, нужно сохранить правила инструментов, sandbox, approvals, streaming и output expectations.
- **Использовать skills как основной способ stage-specific workflow** — это механизм для универсального ассистента, который сам выбирает навык. Наш workflow уже создаёт отдельного агента под конкретный шаг.
- **Гнаться за экспериментальными фичами** без явного `capabilities.experimentalApi: true`. Это отдельное решение — всегда за ним должна стоять осмысленная оценка рисков совместимости.

## 8. Итог одной строкой

Codex App Server — это официально рекомендованный OpenAI путь интеграции с Codex-агентом, который вместо тонкой обёртки над CLI даёт богатую двунаправленную серверную поверхность с полноценным управлением сессиями, approvals, MCP, скиллами, плагинами, авторизацией, песочницей, файловой системой, исполнением команд, ревью кода, live-диффами, live-планами и встроенным realtime-режимом. После полного перехода CodeAI Hub на App Server главный следующий выигрыш — не просто новые UI-события, а управление стартовым instruction stack: `baseInstructions`, `developerInstructions`, `model_instructions_file` и отключение нерелевантных AGENTS/skills/apps слоёв для каждого workflow step.
