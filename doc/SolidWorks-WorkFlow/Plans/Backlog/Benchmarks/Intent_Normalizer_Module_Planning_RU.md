## 1. Короткое решение

Перед дорогим executor-agent можно поставить дешевую локальную или недорогую модель, которая не выполняет задачу, а переводит сырой пользовательский текст в строгий intent packet.

Intent packet нужен не пользователю, а следующему сильному агенту и Core:

- сделать косноязычный запрос машиночитаемым;
- отделить задачу от мусора, эмоций и неполных формулировок;
- определить, можно ли начинать безопасный минимальный шаг;
- задать до трех уточняющих вопросов, если начинать нельзя;
- передать executor-agent короткий brief, ограничения и первый шаг;
- снизить расход дорогой модели на разбор мутного входа.

Минимальный рабочий вариант не требует нового workflow engine: это pre-turn слой для standalone chat/research/review сессий. Workflow-шаги можно подключать позже, только после подтверждения качества на чатовых задачах.

## 2. Почему это отдельный модуль

Обычный пользовательский запрос часто выглядит так:

- несколько задач в одном сообщении;
- нет явного объекта работы;
- есть запреты, но они спрятаны в разговорной фразе;
- пользователь просит "сделай нормально", но сам не знает, review это, fix или explore;
- задача относится к продуктовой разработке, но формулируется через UX, поддержку, баги, релиз, документацию, интеграции или бизнес-процесс.

Сильная модель справляется с этим сама, но тратит дорогой контекст и внимание. Слабая модель может быть полезна как "помощник оркестратора", если ее держать в узком режиме:

- вход: только сырой пользовательский текст;
- выход: только валидный JSON;
- никаких tool calls;
- никакого исполнения;
- никаких файлов;
- никаких рассуждений в ответе;
- строгая схема и ограниченные enum-значения.

## 3. Граница ответственности

### Normalizer делает

- читает один `SOURCE_REQUEST`;
- нормализует смысл запроса без выполнения;
- выбирает task type;
- определяет, нужны ли уточнения;
- формирует brief для будущего executor-agent;
- выделяет разрешенные и запрещенные действия executor-agent;
- возвращает JSON по фиксированной схеме.

### Normalizer не делает

- не запускает команды;
- не читает проект;
- не создает и не меняет файлы;
- не вызывает инструменты;
- не выбирает production-решение;
- не делает архитектуру вместо пользователя;
- не заменяет executor-agent.

Эта граница критична. В наших тестах слабые модели чаще всего ошибались именно здесь: начинали "проектировать", "реализовывать", предполагать доступ к интерфейсу или писать план работы вместо intent packet.

## 4. Целевой JSON intent packet

После расширенных тестов рабочий MVP-контракт упрощён до 10 полей. Старый 12-полевой вариант был богаче, но слабые модели чаще путали `allowed/forbidden` с собственными ограничениями normalizer-а и ломали смысл. Новый формат ближе к реальной цели: подготовить инструкцию для сильной модели и оставить достаточно машинных полей для оркестратора.

```json
{
  "canStart": true,
  "questions": [],
  "taskType": "",
  "riskLevel": "",
  "suggestedAgentProfile": "",
  "contextToRead": [],
  "task": "",
  "instructionForStrongModel": "",
  "do": [],
  "doNot": []
}
```

### Поля

| Поле | Тип | Назначение |
| --- | --- | --- |
| `canStart` | boolean | `true`, если сильная модель может начать с безопасного первого шага. |
| `questions` | string[] | До 3 вопросов. Если `canStart=true`, всегда `[]`. |
| `taskType` | string enum | Главный тип задачи. |
| `riskLevel` | string enum | `low`, `medium` или `high`. |
| `suggestedAgentProfile` | string enum | Рекомендуемый профиль будущего агента. |
| `contextToRead` | string[] | Только явно названные файлы, директории, ссылки, документы или артефакты. |
| `task` | string | Короткая ясная версия пользовательского запроса без потери смысла. |
| `instructionForStrongModel` | string | Готовая инструкция для сильной модели: что делать дальше и чего не додумывать. |
| `do` | string[] | Что разрешено сильной модели. |
| `doNot` | string[] | Что запрещено сильной модели. |

### Будущее расширение: routing packet

10-полевой packet остается MVP для проверки качества нормализации. Но реальная цель чатового режима шире: не только очистить запрос, а выбрать минимальный релевантный пакет запуска для сильной модели.

После подтверждения качества normalizer должен быть расширен whitelisted-полями:

```json
{
  "systemProfileId": "chat.software.review.ux",
  "toolProfileId": "tools.readonly.browser_optional"
}
```

Важно: normalizer не пишет системные промпты и не придумывает инструменты. Он выбирает идентификаторы из заранее заданного перечня. Core/оркестратор затем делает обычный lookup:

```text
systemProfile = systemProfiles[systemProfileId]
toolProfile = toolProfiles[toolProfileId]
```

Это сохраняет контроль у Core и не дает слабой модели расширять права executor-agent. Примеры будущих профилей:

| Класс запроса | systemProfileId | toolProfileId |
| --- | --- | --- |
| UX/product review без реализации | `chat.software.review.ux` | `tools.readonly.browser_optional` |
| Баг/регрессия с возможным фиксом | `chat.software.fix.diagnose_patch` | `tools.repo.patch.tests` |
| Архитектурное обсуждение без кода | `chat.software.discuss.architecture` | `tools.none` |
| Документ/продуктовый материал | `chat.software.document.product` | `tools.none` |
| Web research | `chat.software.research.web` | `tools.web` |
| Release/build gate | `chat.software.release.gate` | `tools.release_confirmed_only` |

MVP не должен сразу включать эти поля, чтобы не смешивать две задачи: сначала доказать надежную нормализацию, потом добавить routing selection.

### Enum-значения

`taskType`:

- `explore` — разобраться, исследовать, сравнить варианты, оценить идею или процесс.
- `review` — проверить код, текст, архитектуру, UX, производительность, существующий процесс, результат или решение.
- `implement` — создать новую функцию, модуль, интерфейс, документ или прототип.
- `fix` — исправить конкретный баг, ошибку, регрессию или неправильное поведение.
- `test` — проверить гипотезу, прогнать кейсы, сравнить результаты.
- `document` — написать или обновить документацию, презентацию, письмо, страницу, описание, статью или другой текстовый материал.
- `release` — собрать, упаковать, подготовить или опубликовать релиз.
- `discuss` — обсудить без немедленного выполнения.
- `other` — если ни один тип не подходит.

`suggestedAgentProfile`:

- `explorer`
- `reviewer`
- `implementer`
- `tester`
- `architect`
- `documenter`
- `default`

`riskLevel`:

- `low` — анализ, обсуждение, чтение, план, без изменений файлов и внешних действий.
- `medium` — локальные изменения файлов, запуск команд, прототипирование, тесты, создание материалов.
- `high` — production, удаление данных, секреты, платежи, персональные данные, безопасность, массовые изменения, автоматизация действий во внешних системах или с клиентами.

Если провайдер поддерживает structured output, использовать schema-first. Для LM Studio и OpenAI-compatible runtime обычно достаточно тела схемы без лишних wrapper-объектов:

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": [
    "canStart",
    "questions",
    "taskType",
    "riskLevel",
    "suggestedAgentProfile",
    "contextToRead",
    "task",
    "instructionForStrongModel",
    "do",
    "doNot"
  ],
  "properties": {
    "canStart": { "type": "boolean" },
    "questions": {
      "type": "array",
      "maxItems": 3,
      "items": { "type": "string" }
    },
    "taskType": {
      "type": "string",
      "enum": ["explore", "review", "implement", "fix", "test", "document", "release", "discuss", "other"]
    },
    "riskLevel": {
      "type": "string",
      "enum": ["low", "medium", "high"]
    },
    "suggestedAgentProfile": {
      "type": "string",
      "enum": ["explorer", "reviewer", "implementer", "tester", "architect", "documenter", "default"]
    },
    "contextToRead": {
      "type": "array",
      "items": { "type": "string" }
    },

      "type": "array",

## 6. Универсальный prompt для weak/local model

Это baseline prompt для моделей без structured output. Он длиннее, чем хочется, но слабые модели без таких рельсов начинают исполнять задачу или выдумывать контекст.

```text
Ты — Intent Normalizer для задач создания программных продуктов.

Твоя задача — преобразовать SOURCE_REQUEST в один валидный JSON-объект.
Не выполняй запрос пользователя. Только нормализуй его.

Запрос может быть на любую тему в разработке продукта: код, баги, UX, ревью, документация, релиз, архитектура, тесты, бизнес-процесс, интеграции, поддержка, продуктовая аналитика.
Запрос может быть косноязычным, длинным, неполным, противоречивым или с мусором.

Нормализуй только текст между <SOURCE_REQUEST> и </SOURCE_REQUEST>.

<SOURCE_REQUEST>
{{USER_REQUEST}}
</SOURCE_REQUEST>

Верни только один валидный JSON-объект.
Без Markdown, без пояснений, без ```json, без текста до или после JSON.
JSON должен парситься через JSON.parse без исправлений.

Верни ровно эти 10 полей, без дополнительных полей:

{
  "canStart": true,
  "questions": [],
  "taskType": "",
  "riskLevel": "",
  "suggestedAgentProfile": "",
  "contextToRead": [],
  "task": "",
  "instructionForStrongModel": "",
  "do": [],
  "doNot": []
}

Правила:

- Не выполняй запрос пользователя. Только нормализуй его.
- Не создавай файлы, не пиши код, не запускай команды.
- Не пиши уверенно о фактах, которые пользователь подал как возможные причины. Используй "возможно", "может", "вероятно".
- Не добавляй новые факты, причины, файлы, инструменты, метрики, стек или инфраструктуру, которых нет в SOURCE_REQUEST.
- "canStart": true, если сильная модель может начать с безопасного первого шага.
- "canStart": false, если без ответа пользователя нельзя разумно работать.
- "questions": если "canStart": false, задай максимум 3 вопроса; если "canStart": true, верни [].
- "taskType": одно из значений: "explore", "review", "implement", "fix", "test", "document", "release", "discuss", "other".
- "riskLevel": одно из значений: "low", "medium", "high".
- "suggestedAgentProfile": одно из значений: "explorer", "reviewer", "implementer", "tester", "architect", "documenter", "default".
- "contextToRead": только конкретные файлы, директории, ссылки, документы или артефакты, явно названные пользователем. Если их нет — [].
- "task": краткая ясная версия запроса без потери смысла.
- "instructionForStrongModel": точная инструкция сильной модели, что делать дальше.
- "do": список разрешенных действий для сильной модели.
- "doNot": список запрещенных действий для сильной модели.

Выбор taskType:

- "explore" — разобраться, исследовать, сравнить варианты, оценить идею или процесс.
- "review" — проверить код, текст, архитектуру, UX, производительность, существующий процесс, результат или решение.
- "implement" — создать новую функцию, модуль, интерфейс, документ или прототип.
- "fix" — исправить конкретный баг, ошибку, регрессию или неправильное поведение.
- "test" — проверить гипотезу, прогнать кейсы, сравнить результаты.
- "document" — написать или обновить документацию, презентацию, письмо, страницу, описание, статью или другой текстовый материал.
- "release" — собрать, упаковать, подготовить или опубликовать релиз.
- "discuss" — обсудить без немедленного выполнения.
- "other" — если ни один тип не подходит.

Выбор suggestedAgentProfile:

- "explorer" — исследование идеи, процесса, вариантов, ограничений или первого безопасного шага.
- "reviewer" — ревью существующего кода, UX, текста, процесса, результата или ответа модели.
- "implementer" — пользователь явно просит писать код или вносить изменения.
- "tester" — пользователь просит прогнать проверки, сравнить результаты или проверить гипотезу.
- "architect" — пользователь явно просит архитектуру или системный дизайн.
- "documenter" — пользователь просит подготовить документ, презентацию, письмо, страницу или текст.
- "default" — если профиль неочевиден.

Выбор riskLevel:

- "low" — анализ, обсуждение, чтение, план, без изменений файлов и внешних действий.
- "medium" — локальные изменения файлов, запуск команд, прототипирование, тесты, создание материалов.
- "high" — production, удаление данных, секреты, платежи, персональные данные, безопасность, массовые изменения, автоматизация действий во внешних системах или с клиентами.

Правила уточнений:

- Не задавай вопросы только потому, что запрос мутный, если можно начать с безопасного минимального review/explore.
- Если пользователь просит "посмотреть", "разобраться", "понять что происходит", обычно можно начать без уточнений.
- Если пользователь просит исправить баг, но нет логов, можно начать с диагностики. Не ставь canStart=false только из-за отсутствия логов.
- Не задавай вопросы только потому, что нет аналитики, логов, скриншотов или доступа к продукту, если пользователь просит первичный review, гипотезы, анализ идеи или безопасную диагностику по описанию.
- Если пользователь просит оценить текст, файл, ответ модели или артефакт, но сам объект не приложен, ставь canStart=false и попроси прислать объект.
- Если пользователь просит оценить, исправить, переписать или проверить конкретный объект, но сам объект не приложен (ответ модели, текст, документ, файл, ссылка, скриншот, лог), ставь canStart=false и спроси только этот объект.
- Если пользователь просит подготовить материал, но не указал формат, аудиторию и цель, ставь canStart=false и задай до 3 вопросов.
- Если пользователь просит собрать релиз, сделать deploy, удалить данные или выполнить другое внешнее/необратимое действие, но пишет, что не уверен в проверках или подтверждении, ставь canStart=false.
- Если задача касается production-данных, секретов, безопасности, платежей, удаления данных или действий во внешних системах, ставь riskLevel="high" и не давай окончательных рекомендаций.

Перед ответом молча проверь:

- JSON валиден.
- Все строки в двойных кавычках.
- Все 10 полей присутствуют.
- Дополнительных полей нет.
- Если "canStart": true, "questions" равно [].
- Если "canStart": false, "questions" содержит от 1 до 3 вопросов.
- "do" и "doNot" относятся к сильной модели, а не к normalizer-у.
- Ответ нормализует запрос, а не выполняет его.
```

## 7. Калибровочный prompt для слабых моделей

Универсальный prompt важен для production, но слабым моделям часто нужна калибровка на конкретных классах запросов. В калибровке допустимо добавить блок "для этого запроса обязательно". В production такой блок нельзя хардкодить глобально.

Шаблон:

```text
Ты — Intent Normalizer.

Нормализуй запрос между <SOURCE_REQUEST> и </SOURCE_REQUEST>.
Не выполняй задачу. Верни только валидный JSON.

<SOURCE_REQUEST>
{{USER_REQUEST}}
</SOURCE_REQUEST>

Верни JSON ровно с этими полями:
{
  "canStart": true,
  "questions": [],
  "taskType": "",
  "riskLevel": "",
  "suggestedAgentProfile": "",
  "contextToRead": [],
  "task": "",
  "instructionForStrongModel": "",
  "do": [],
  "doNot": []
}

Для этого запроса обязательно:
- "canStart": {{EXPECTED_CAN_START}}
- "questions": {{EXPECTED_QUESTIONS}}
- "taskType": "{{EXPECTED_TASK_TYPE}}"
- "riskLevel": "{{EXPECTED_RISK_LEVEL}}"
- "suggestedAgentProfile": "{{EXPECTED_AGENT_PROFILE}}"
- "contextToRead": {{EXPECTED_CONTEXT_TO_READ}}

Пиши только то, что есть в SOURCE_REQUEST.
Не добавляй новые факты, причины, файлы, инструменты, метрики, стек или инфраструктуру.

{{CASE_SPECIFIC_ALLOWED_MEANING}}

{{CASE_SPECIFIC_FORBIDDEN_MEANING}}

Перед ответом проверь:
- это валидный JSON;
- нет Markdown;
- нет дополнительных полей;
- все строки в двойных кавычках.
```

Этот режим хорошо сработал на слабой модели, когда универсальный prompt давал ошибки:

- модель выдумывала доступ к интерфейсу;
- добавляла причины, которых не было в запросе;
- путала `explorer` и `reviewer`;
- писала "MVP", "стек", "архитектура", хотя пользователь этого не просил;
- делала `assumptions` слишком уверенными.

## 8. Отточенные формулировки, которые нужно сохранить

### Роль

```text
Ты — Intent Normalizer.
Не выполняй запрос пользователя. Только нормализуй его.
```

Это лучше, чем "ты помощник" или "проанализируй запрос": слабая модель иначе начинает выполнять задачу.

### Якорь исходного текста

```text
Нормализуй только текст между <SOURCE_REQUEST> и </SOURCE_REQUEST>.
```

Это надежнее, чем `RAW_USER_REQUEST:`. На одном тесте модель решила, что RAW_USER_REQUEST отсутствует; XML-like теги снизили риск.

### Запрет на мета-ответ

```text
Тебе запрещено отвечать, что исходный запрос отсутствует.
```

Использовать только в калибровке, если модель уже ошибалась таким образом. В production достаточно строгих тегов.

### Исполнение запрещено

```text
Не создавай файлы, не пиши код, не запускай команды.
```

Это собственные ограничения normalizer-а. Их нельзя путать с `doNot`, где пишутся ограничения для сильной модели.

### `do` / `doNot` принадлежат сильной модели

```text
"do" — что разрешено сильной модели.
"doNot" — что запрещено сильной модели.
```

Переход от `allowedActions` / `forbiddenActions` к коротким `do` / `doNot` оказался проще для слабых моделей и всё равно остается понятным оркестратору.

### Не добавлять скрытый план

```text
Не добавляй новые факты, причины, файлы, инструменты, метрики, стек или инфраструктуру, которых нет в SOURCE_REQUEST.
```

Без этой фразы модели часто кладут в `task`, `do` или `instructionForStrongModel` лишние действия и выдуманные условия.

### Не предполагать доступ

```text
Не пиши, что доступ к продукту, экранам, письмам, CRM, аналитике или файлам уже есть, если пользователь их не предоставил.
```

Это одна из самых важных фраз для software-product домена. Слабые модели любят писать "просмотреть интерфейс", "изучить таблицы", "проанализировать CRM", даже когда есть только разговорное описание.

### Возможные причины остаются возможными

```text
Не пиши уверенно о фактах, которые пользователь подал как возможные причины. Используй "возможно", "может", "вероятно".
```

Пример: "может тексты плохие, может первый экран непонятный" не должно превращаться в "тексты плохие и первый экран непонятный".

### contextToRead строгий

```text
"contextToRead": только конкретные файлы, директории, ссылки, документы или артефакты, явно названные пользователем. Если их нет — [].
```

Не класть туда "структура проекта", "документация", "текущий запрос", "правила схемы", если пользователь не называл конкретный объект. Иначе executor-agent может начать читать лишний контекст.

## 9. Clarification policy

Главное правило: уточнения нужны не для идеальности, а только если нельзя безопасно начать.

### Не спрашивать, если можно начать безопасно

Примеры:

- "посмотри проект, где неудобно и тормозит" -> `review`, `canStart=true`;
- "кнопка иногда не работает, логов нет" -> `fix`, `canStart=true`, первый шаг диагностика;
- "разберем идею без кода" -> `explore`, `canStart=true`;
- "онбординг непонятный, найди 3-5 вероятных проблем" -> `review`, `canStart=true`.

### Спрашивать, если отсутствует объект работы

Примеры:

- "оцени вот этот ответ", но ответ не приложен -> `review`, `canStart=false`;
- "сделай материал о продукте", но нет формата, аудитории и цели -> `document`, `canStart=false`;
- "собери релиз", но нет явного release confirmation gate -> `release`, `canStart=false`.

### Максимум три вопроса

Если `canStart=false`, вопросы должны быть короткими и закрывать критичные неизвестные. Нельзя задавать список из 8-10 вопросов "на всякий случай".

## 10. Software-product доменные правила

### UX/Product review

Если пользователь просит посмотреть путь пользователя, найти проблемы и предложить правки:

- `taskType=review`;
- `suggestedAgentProfile=reviewer`;
- `riskLevel=low`, если нет изменений файлов или production;
- `canStart=true`, если можно начать экспертный review;
- не выдумывать аналитику, конверсию или причины оттока;
- помечать неподтвержденные причины как гипотезы.

Калибровочная фраза для слабой модели:

```text
Разрешай будущему агенту выделять гипотезы, но только из причин, названных пользователем.
Не предполагай доступ к реальному продукту, аналитике или экранам, если пользователь их не предоставил.
```

### Баги и регрессии

Если пользователь просит починить баг, но причина неизвестна:

- `taskType=fix`;
- `canStart=true`, если можно начать диагностику;
- `riskLevel=medium`, если возможны локальные изменения и тесты;
- first step: диагностика недавних изменений, воспроизведение или проверка релевантных обработчиков;
- логи можно запросить позже, но их отсутствие не всегда блокирует старт.

Калибровочная фраза:

```text
Если пользователь просит "починить", но причина неясна, все равно можно начать с диагностики.
Не ставь canStart=false только из-за отсутствия логов.
```

### Идеи и архитектурные гипотезы

Если пользователь говорит "может стоит сделать", "давай без кода", "сначала разберемся":

- `taskType=explore` или `discuss`;
- `suggestedAgentProfile=explorer`;
- `riskLevel=low`;
- не выбирать `implement`;
- не проектировать большую архитектуру.

Калибровочная фраза:

```text
Если пользователь явно говорит "без кода", "не создавать", "сначала разобраться", не выбирай implement.
```

### Автоматизация процессов

Если пользователь хочет автоматизировать бизнес-процесс, но сам не знает, где узкое место:

- `taskType=explore`;
- `suggestedAgentProfile=explorer`;
- не выбирать `implement`;
- не строить интеграцию;
- не покупать сервисы;
- не автоматизировать действия с клиентами без решения пользователя.

Калибровочная фраза:

```text
Если пользователь сам не уверен, где главный затык, не выбирай implement.
```

### Документы и материалы

Если пользователь просит "какой-нибудь материал" без формата и аудитории:

- `taskType=document`;
- `suggestedAgentProfile=documenter`;
- `canStart=false`;
- вопросы: формат, аудитория, цель/канал использования;
- не выдумывать фичи, метрики, клиентов или позиционирование продукта.

### Release/build просьбы

Если пользователь просит собрать, упаковать или выпустить релиз:

- `taskType=release`;
- `riskLevel=medium` минимум, потому что сборка меняет артефакты и версии;
- `canStart=false`, если в текущем lifecycle требуется отдельное подтверждение на release build;
- не запускать release scripts без явного подтверждения;
- не подменять release просьбу обычным `implement` или `test`.

## 11. Runtime pipeline MVP

Минимальный runtime:

1. Chat/Core получает raw user request.
2. Intent Normalizer строит prompt:
   - structured output schema, если модель поддерживает;
   - JSON-only prompt, если structured output недоступен.
3. Дешевая модель возвращает JSON.
4. Core делает `JSON.parse`.
5. Core валидирует 10 полей и enum-значения.
6. Если JSON невалиден:
   - один repair retry с текстом ошибки парсинга и той же схемой;
   - если второй ответ невалиден, fallback: отправить raw request сильной модели без normalizer.
7. Если JSON валиден:
   - если `canStart=false`, показать пользователю `questions`;
   - если `canStart=true`, передать strong executor-agent `instructionForStrongModel`, `task`, `do`, `doNot` и исходный запрос как provenance;
   - в будущем routing-режиме выбрать `systemProfileId` и `toolProfileId` только из whitelist и подставить соответствующие Core-owned system/tool пакеты.

Не добавлять tools в MVP normalizer. Модуль должен быть text-in / JSON-out. Инструменты нужны executor-agent, не normalizer-у.

## 12. Provider/model рекомендации

По экспериментам есть два полезных класса кандидатов:

- локальная структурно-переводческая модель типа `Hy-MT2-30B-A3B-MIX`: без reasoning, быстрая, около 16 GB, хорошо следует шаблону;

Текущий hosted baseline-кандидат: `google/gemini-2.5-flash-lite`.

Проверенные кейсы для `google/gemini-2.5-flash-lite`:

- UX review с мутным описанием: валидный JSON, верные `review` / `low` / `reviewer`;
- отсутствующий объект ревью: `canStart=false`, точные вопросы, `review` / `low` / `reviewer`;
- мутный bugfix без логов: `canStart=true`, `fix`, `medium`, точечная диагностика без запроса логов как блокера;
- идея "умного диспетчера" без кода: `explore`, `low`, без ухода в `implement`;
- продуктовый материал без формата и аудитории: `canStart=false`, 3 вопроса, `document` / `medium` / `documenter`.
- release/build просьба без подтвержденного gate: `canStart=false`, `release`, вопросы о проверках и подтверждении.

Выводы из неудачных кандидатов:

- `liquid/lfm-2.5-1.2b-thinking:free` очень быстрый и держит JSON, но возвращает пустые `do/doNot` и generic task вроде "Нормализовать запрос"; latency не должна поднимать такие модели в топ.
- `openai/gpt-4.1-nano` и `openai/gpt-4o-mini` стабильно парсят JSON, но хуже определяют блокирующие случаи: могут ставить `canStart=true`, когда отсутствует объект работы или нужен release gate.
- `google/gemini-3.1-flash-lite` и preview на усиленном prompt склонны переуточнять UX-review: ставят `canStart=false` там, где можно начать экспертный review.
- бесплатные агрегаторные модели часто непригодны для production из-за timeout, 429 и нестабильного backend routing.

Практические настройки:

- temperature: `0` или близко к `0`;
- top_p: низкий или default, если модель ухудшается от ручной настройки;
- structured output включать, если модель реально держит схему;
- reasoning выключать, если задача только нормализация;
- max tokens достаточно для JSON, но без большого запаса;
- один и тот же prompt + один и тот же test set для сравнения моделей.

Важно: меньшие модели могут выигрывать по скорости, но чаще:

- ломают JSON;
- добавляют факты;
- путают role normalizer/executor;
- делают `implement` там, где нужен `explore` или `review`;
- заполняют `contextToRead` мусором.
- возвращают формально валидный, но смыслово пустой packet.

## 13. Оценочная шкала

10-балльная проверка:

1. Валидный JSON.
2. Все 10 полей присутствуют.
3. Нет дополнительных полей.
4. Верный `taskType`.
5. Верный `canStart`.
6. Нет выполнения задачи вместо нормализации.
7. Нет выдуманных фактов.
8. `contextToRead` не заполнен мусором.
9. `do` и `doNot` относятся к сильной модели.
10. Верный `riskLevel` и пригодная `instructionForStrongModel`.

Для слабых моделей отдельно считать:

- стабильность при 3-5 повторах с разной temperature;
- долю валидного JSON;
- склонность к лишним уточнениям;
- склонность к преждевременной реализации;
- склонность выдумывать доступ к проекту, интерфейсу, аналитике или файлам.

После OpenRouter benchmark latency больше не считается частью качества. Итоговая таблица должна иметь две независимые колонки:

- `quality` — смысловая пригодность intent packet;
- `speed` — latency/TTFT/tokens-per-second, используется только для выбора между моделями с близким quality.

Качество должно жестко штрафовать:

- пустые `do` / `doNot`;
- generic `task` вроде "Нормализовать запрос";
- неправильный `canStart`;
- отсутствие вопросов при реально отсутствующем объекте работы;
- лишние вопросы для безопасного review/explore;
- неправильный `taskType` / `suggestedAgentProfile`;
- hallucinated access к проекту, интерфейсу, аналитике, логам или файлам.

## 14. Минимальный калибровочный набор

| Класс запроса | Ожидаемый результат |
| --- | --- |
| Мутный UX/onboarding review | `taskType=review`, `profile=reviewer`, `canStart=true`, не выдумывать аналитику. |
| Нестабильный баг без логов | `taskType=fix`, `canStart=true`, первый шаг диагностика. |
| Идея "умного диспетчера" без кода | `taskType=explore`, `profile=explorer`, не `implement`. |
| Документ о продукте без формата и аудитории | `taskType=document`, `canStart=false`, 3 вопроса. |
| Ревью ответа модели, но ответ не приложен | `taskType=review`, `canStart=false`, попросить объект ревью. |
| Автоматизация таблица -> CRM -> календарь -> письмо | `taskType=explore`, не `implement`, не автоматизировать внешние действия. |
| Release/build просьба | `taskType=release`, `canStart=false` без отдельного release confirmation gate. |

## 15. Acceptance criteria будущего модуля

Модуль можно считать готовым к первому runtime experiment, если:

- structured-output path и JSON-only path возвращают одинаковую 10-полевую форму;
- невалидный JSON не попадает к executor-agent;
- `questions` показываются пользователю вместо запуска executor-agent;
- валидный packet передается сильной модели вместе с raw request;
- выбранная local/hosted модель на калибровочном наборе дает не ниже 8/10 в среднем и 10/10 на основных software-product кейсах после prompt tuning;
- при отказе normalizer-а система безопасно fallback-ит на raw request без потери пользовательского запроса;
- normalizer не получает file/tool surface.
- routing-расширение, если включено, выбирает только whitelisted `systemProfileId` и `toolProfileId`; normalizer не пишет системные инструкции и не объявляет инструменты сам.

## 16. Non-goals

- Не строить универсальный AGI-orchestrator.
- Не маршрутизировать workflow steps в MVP; routing сначала нужен только для standalone chat/research/review сессий.
- Не выбирать модель автоматически без benchmark results.
- Не создавать новый tool layer.
- Не заменять сильного executor-agent.
- Не делать multi-agent planning на стороне normalizer-а.
- Не писать production-интеграцию до отдельного execution scope.

## 17. Следующий минимальный шаг

Сначала зафиксировать benchmark pack:

1. 7-10 мутных software-product запросов.
2. Expected packet для каждого.
3. Один universal prompt.
4. Один calibration prompt template.
5. Таблица результатов по моделям, temperature и structured-output режиму.
6. Черновой whitelist `systemProfileId` / `toolProfileId` для чатовых software-product классов.

Только после этого решать, нужен ли runtime module в Core или достаточно user-facing экспериментального normalizer mode в standalone chat. Runtime routing включать только после отдельного теста на выбор профилей, а не одновременно с базовой нормализацией.
