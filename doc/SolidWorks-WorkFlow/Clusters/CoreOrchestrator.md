## 1) Назначение

Core Orchestrator — автономное ядро, которое:
- принимает команды клиентов (PM/Webview/Launcher) и держит multi-workspace scope;
- управляет lifecycle каждого turn (`turn_started` → `turn_completed|turn_failed`);
- обеспечивает routing сообщений в актуальный provider segment (resume/rollover);
- пишет/читает историю диалогов (unified-session JSONL) и continuity chain;
- публикует snapshot-first состояние для UI (lock/usage/status).

## 3) Ключевые инварианты (коротко)

- **Никогда не оставлять UI в stuck working/resuming**: любой provider/core failure обязан завершать turn (fail + rollback `turnState="idle"`), иначе UI может остаться locked навсегда.
- **Немедленный lock на submit**: Core обязан эмитить `turnState="running"` до реального provider send.
- **dialogId ≠ sessionId**: история диалога стабильна, live статус/usage привязан к текущему сегменту.
- **Continuity**: Core выбирает path по stage/contract. Documentation Tree trunk stages используют synthetic rollover без report/resume bootstrap; report-based handoff остаётся fallback для implementation-heavy flows и обязан иметь delivery/ack/retry, иначе UI получает явный failure, а не вечный lock.
- **Post-turn continuity arbitration**: threshold breach на `token_usage` не имеет права сам по себе запускать flow-node rollover во время активного one-shot turn; до `turn_completed` Core только кеширует usage snapshot.
- **Trunk flow-node rollover eligibility**: production flow-node rollover разрешён для `description`, `virtual_simulation`, `diagram_modules`, `application_skeleton` и `quality_gates` только при `runSlug=null` и hydrated context (`initiativeSlug + stage`). Branch/run agents остаются rejected до отдельного continuity contract.
- **Documentation Tree synthetic continuation**: after post-turn threshold breach Core materializes target session, captures last user-visible assistant message, clears stale create-report state, emits `resume_ready`, and attaches continuation instructions only to the next real user message. The provider sees workflow start/step contract + `Continuation Mode`; UI/history sees only the user's original message.
- **Managed orchestration runtime boundary**: `diagram_modules`, `application_skeleton`, and `quality_gates` run through the Core-owned Managed Workflow Orchestration cluster. The retired post-turn service, generated child-plan flow, provider-visible repair/continuation dispatch, and acceptance handoff are not active runtime contracts. PM workflow-state readers, sidebars, status panels, cards, and artifact panes remain read-model only and must not send automatic provider messages or run managed commits.
- **Managed turn completion boundary**: provider `turn_completed` is not an immediate UI unlock for managed workflow sessions. Core first persists provider messages, runs managed validation/arbitration, performs required cleanup/commit effects, and then opens the current review gate or settles the transition. Review confirmation uses a Core action scoped to the active review message id; stale confirmations are rejected without provider dispatch.
- **No-stop dual outcome**: every Core settlement of a managed turn, validation, commit boundary, or internal error ends either as an agent repair/continuation dispatch or as a button gate with a concrete user action; informational stop cards are defects. Continuation dispatch is awaited with one retry and a released-input failure message on exhaustion; managed turn arbitration is time-boxed (120s) so a hung handler settles with the input released; repair dispatch attempts per artifact are bounded (3) and exhaustion degrades to the review gate (accept as is / describe corrections). Dirty Git is never a stop: managed terminal boundaries auto-commit with two-basket classification (step-owned residue into the managed step commit, everything else into a separate `chore: preserve workspace changes` commit), boundary anchors preserve-commit unknown files before creation, accepted-step commits preserve residual files instead of throwing, and idempotent no-staged turns advance with the current HEAD hash instead of blocking.
- **Name-agnostic gate validation**: Quality Gates integration validates entities, not names. Each required gate must have `commands.<gate-id>.proposedCommand` as the single source of truth for how the gate runs; the command must resolve (every `npm run <script>` it uses exists in `package.json`, transitively) and be reachable from the matching `.husky` hook directly or through package scripts the hook calls. Script names, `qg:*` prefixes, aggregate scripts, and direct-vs-transitive wiring are never rejection reasons; `qg:*` is only a recommended style. Verification proves enforcement by running the hooks themselves (`sh .husky/pre-commit` / `sh .husky/pre-push`) plus contract commands for module-execution gates, with aggregates accepted as optional alternatives. Diagnostics name the exact unreachable command (`gate_command_missing` / `gate_command_unresolved` / `gate_command_not_reachable`).
- **Repair-limit gate continuation**: the repair-limit review gate obeys the dual outcome itself. A single managed-stage dispatcher (`managed-stage-repair-limit-review`) runs ahead of the per-stage review handlers whenever a stage plan sits on an open repair attempt above the limit. Confirm performs accept-as-is: residue is auto-committed, the open repair task closes with the `not-created-user-accepted-repair-limit-as-is` disposition, the stage plan advances to its next phase task (Quality Gates: contract review after draft, formal verification after integration, persistent return after verification; Diagram Modules: user review; Application Skeleton: contract review after draft, final user review after materialization), the managed ledger is committed, and the matching continuation is dispatched. Revision text dispatches a user-corrections repair prompt that executes the already-open repair attempt. A review confirmation no handler can match never dies silently: Core appends a released-input message naming the unmatched state alongside the `managed_review_gate_unhandled` session error.
- **Provider-order tolerance**: providers may deliver usage telemetry before or after `turn_completed`; Core обязан завершать одно и то же continuity-решение независимо от порядка событий.
- **Turn-scoped usage cache**: cached usage snapshot очищается при старте нового outbound turn-а и после финального решения post-turn arbitration, чтобы usage прошлого turn-а не протекал в следующий.
- **Replay-first usage telemetry**: `usage_limits` для ready session сначала реплеится из cached stream snapshot и только потом, при допустимом lifecycle trigger, может инициировать provider refresh; idle session без lifecycle trigger не должна дёргать provider ради usage reread.
- **One-shot ready-binding bootstrap**: automatic usage bootstrap разрешён только один раз на конкретный ready-binding lifecycle (`providerId + providerSessionId`); повторные reopen/rebind того же lifecycle обязаны переиспользовать replay cache вместо нового provider read.
- **Turn completion owns fresh usage delivery**: `turn_completed` остаётся единственной unconditional automatic boundary для свежего usage telemetry; provider completion path обязан доставить terminal `usageLimits`/`tokenUsage` сам, а websocket layer — переиграть последние `token_usage` и `usage_limits` после connect/scope switch, включая legacy `usage_limits` payload через normalizing `stream_event`.
- **Runtime session materialization on dialog:list**: `RemoteBridgeDialogCommandRouter.handleDialogList` через `materializeContinuityEntries` обязан для каждой `ContinuityIndexEntry` с полной связкой (`latestSessionId + providerId + providerSessionId`) создавать stub runtime session в `SessionManager` / paper-binding в `SessionProviderBindingService` / hydrate в `WorkspaceStore` с `turnState: "idle"`, `continuityLockActive: false`, `bindingStatus: "ready"`, если такая session ещё не существует. Materialized workflow session обязана получить `initiativeSlug=workspaceSlug` и `stage` из continuity entry; если старый stub был создан без этого context, `dialog:send` repair-ит его до provider dispatch. Provider adapter turn, Create Report и resume/bootstrap prompt в момент materialize не стартуются; Documentation Tree continuation instructions добавляются только lazy envelope на первом real user message, а обычный provider binding остаётся ленивым через `resolveProviderSessionId`. Это гарантирует, что `workspace:snapshot` содержит runtime session для любого reopened workflow dialog до следующего reconciliation loop'а, и что `handleStop` не возвращает `"Session not found"` для reopened sessions.
- **Settings snapshot read cache**: Core settings/default/translation reads use path-scoped short TTL snapshots through `packages/core/src/config/json-file-snapshot-cache.ts`. Settings write/reset/default-materialization/migration paths must invalidate the canonical settings path immediately after write, so live Core can reduce hot-path disk reads without serving stale user settings after explicit mutation.
- **Remote Bridge before provider warmup**: Core may open the Remote Bridge and accept Project Manager connections before heavy provider warmup completes. Provider descriptors/actions must stay unavailable while their adapters are still `starting`, but the PM shell/status surface must not wait for active provider version probes or SDK/CLI warmup before first paint. Provider warmup status changes are Core-owned events: after each provider status reporter update, Remote Bridge must broadcast both the loading-status event and a fresh `core:state` snapshot so clients replace early `starting` provider rows with the final available/unavailable state. Manual/Settings-triggered provider version reloads remain valid; first socket open must not eagerly run provider version checks.
- **Core WebSocket command boundary**: `WebSocketManager` валидирует каждый incoming client frame через `packages/core/src/remote-bridge/handlers/incoming-message-validator.ts` до dispatch в `RemoteBridgeMessageRouter`. Invalid JSON, non-object envelopes, unknown commands и malformed command payloads отклоняются с sanitized warn log + `session:error`; router получает только структурно валидные `IncomingMessage` команды.
- **Session Text-to-Speech boundary**: Core owns native speech process lifecycle through `packages/core/src/session-speech/session-speech-service.ts`. PM/UI may request `session:speech:speak-message` and `session:speech:stop`, but only Core resolves the packaged Apple Speech helper, clamps rate to `0.75-2.0`, kills/replaces the active helper process, and broadcasts `session:speech:state` for UI active/stop feedback.
- **Core WebSocket error ownership**: `WebSocketManager` owns WebSocketServer/client-socket `error` events. Server errors are logged through Core logger instead of relying on Node's unhandled `EventEmitter` semantics; client socket errors log sanitized context, disconnect that client through the normal disconnect path, and terminate the affected socket. `stop()` clears owned clients plus replay/scope maps (`token_usage`, `usage_limits`, session workspace scope).
- **Startup/workspace best-effort diagnostics**: startup settings default materialization and workspace-session side effects remain non-blocking, but they must emit sanitized Core logger warnings on failure. Silent `.catch(() => undefined)` / `.catch(() => {})` is not allowed on these ownership boundaries because corrupt settings files or workspace bootstrap failures need operational evidence.
- **Runtime factory callback wiring**: `createSessionRequestHandlerRuntimeCore` и верхнеуровневый `createSessionRequestHandlerRuntime` держат циклические callback-dependencies (`messageDispatch`, `sessionResolution`, `continuityRolloverOrchestrator`) через явные deferred refs. Continuity callbacks должны вызываться только после полной сборки runtime; если порядок будет нарушен, factory обязан падать явной initialization error вместо скрытого `undefined` access.
- **Workflow prompt source and directory preflight**: Core prepares stage directories before provider prompt dispatch. `Description` gets `description/`, `Virtual Simulation` gets `virtual_simulation/`, `Diagram Modules` gets `diagram_modules/` plus `diagram_modules/product-parts/`, `Application Skeleton` gets `application_skeleton/`, and `Quality Gates Baseline` gets `quality_gates/`. First prompts include authoritative inline source payloads where Core already has the document: `Description` gets full `questionnaire.md`, `Virtual Simulation` gets full `Final_Description.md`, `Diagram Modules` gets full `Final_Description.md` + `virtual-simulation.md`, `Application Skeleton` gets staged Diagram Modules Product Part artifacts, and `Quality Gates Baseline` gets `application-skeleton.md` + `application-skeleton-map.json`. They also embed the exact artifact templates, field references, parser-visible examples, and required identity fields for every artifact the agent is about to create or repair. Provider-visible input paths are not recovery instructions when Core embedded the text; they may appear only as output targets or explicitly marked truncated/stale/debug fallback metadata. Agent instructions should name ready target artifact paths instead of asking the agent to discover or create stage folders.
- **Managed artifact parser authority**: Core owns the parser/validator/read-model contract for managed stage artifacts. Diagram Modules Product Part / Cluster / Module graph parsing, renderability diagnostics, and repair targets are Core/shared contract outputs, not Project Manager backend behavior. Clients consume Core-produced projections and diagnostics; if a client temporarily parses locally, that parser must be generated from or delegated to the Core-owned contract and treated as migration debt. A repair button in any client sends user intent plus Core diagnostics to Core, and Core creates the repair microtask, paired commit item, provider-visible repair prompt, validation result, and accepted/rejected attempt commit.
- **Quality Gates draft-scope cleanup**: draft/review Quality Gates work may produce only contract artifacts. Before Core records a pre-acceptance review commit, it restores or cleans prohibited integration paths (`package.json`, package-manager lockfiles, `.husky/pre-commit`, `.husky/pre-push`, `scripts/quality-gates/**`). Integration-side files become managed outputs only after Core records user acceptance and enters the integration phase.
- **Workflow localized prompt materialization**: Core/PM prompt builders may prepend localized instruction blocks keyed by `Settings > General > Reasoning` and repeat artifact prose language from `Settings > General > Artifacts for the User`. Protected canonical tokens stay stable: filenames, ids, statuses, YAML/frontmatter keys, HTML comments, `agent-fill`, DSL markers, field names, method/event names, output filenames, and structural headings. Runtime/tooling facts (`python3`, `node`, `npm`, UTF-8 + LF, patch-first sentinel replacement) belong in the first prompt so agents do not spend routine turns discovering them.
- **Development Tree materialization**: Core разделяет read-model и downstream bootstrap. `DevelopmentTreeStateFacade` остаётся extension текущей PM snapshot-читалки: читает валидные Diagram Modules artifacts и может отдавать P/C/M preview snapshot до implementation unlock. `DevelopmentTreeFilesystemStructuratorFacade` и `DevelopmentTreeNodeBootstrapFacade` не запускаются, пока `application-skeleton-map.json` и `quality-gates.json` не приняты. После unlock filesystem structurator применяет accepted skeleton `codePath` mappings к production folders внутри workspace и поддерживает neutral draft mirror under `.codeai-hub/<workspaceSlug>/development_tree/materialized/`. `DevelopmentTreeNodeBootstrapFacade` стартует от materialized folders, создаёт patch-friendly draft skeletons (`PartDescription`, `ClusterDescription`, `ClusterFacadeContract`, `ModuleSpec`, `ModuleFacadeContract`), сохраняет agent-owned `agent-fill` зоны при rerun, и создаёт per-node first-draft agent sessions через gateway к существующему session/request контуру. Product Part prompts receive the exact owner `diagram_modules/product-parts/<part-id>.md` whole when path/id match plus protected skeleton/gates context; Cluster/Module prompts receive scoped excerpts. The automatic draft pass is no-read beyond first-prompt context and listed target draft files unless the user explicitly permits more reading. Draft readiness вычисляется из файловой правды draft-файлов, TODO/frontmatter state, balanced `agent-fill` markers and fill completion, then enters `developmentTree` snapshot as optional field. Unbalanced `agent-fill` markers keep readiness `in_progress`, and refreshed snapshots must be broadcast so PM can update selected artifact panes and sidebar color live.
- **Development Tree Product Part review boundary**: Product Part draft completion and Product Part review acceptance are separate Core responsibilities. Turn completion may reopen the actionable review gate after provider revisions; it must not infer acceptance from ordinary user text. The `managedReviewAction` acceptance path commits the accepted Product Part draft and updates the node plan. Secondary parts advance to `User Return And Revisions`; the lead part advances only to the next managed assignment boundary for `Development Order Plan Draft`, leaving downstream order-plan execution as a later slice.
- **Lead Product Part downstream orchestration**: The lead Product Part agent creates an accepted `DevelopmentOrderPlan.v2` artifact; Core is the only component allowed to validate it, persist unlock-state, and start the next wave. First-wave cluster nodes run in deterministic Git worktrees/branches, with Core-owned managed plans and provider prompts. The cluster sub-agent writes only the Cluster Specification and Cluster Facade Contract artifacts. On review acceptance Core writes review-result and merge-boundary artifacts, merges accepted artifacts back to the main workspace, and updates the lead Product Part coordination graph from `unlocked`/`merge_ready` to `merged` while leaving dependent modules `locked`.
- **Development Tree Product Part Clear/Undo MVP**: `workflow-step-clear` supports only Product Part root targets (`development_tree/materialized/product-parts/<partId>`) in the Development Tree. Core deletes the matching runtime session, provider-native/unified session files, continuity folder/index entry, managed Product Part decision, Product Part root drafts/order/research files, and `doc/TODO/stages/development-tree/product-parts/<partId>/todo-plan.md`, then immediately calls Product Part bootstrap through the existing session gateway. The response includes `productPartRestart` with deleted/recreated path lists. Cluster/module clear remains fail-closed until branch/worktree boundaries are implemented.
