# Архитектура автономного ядра CodeAI-Hub

**Версия документа:** 0.1 (draft)
**Дата:** 2025-11-17
**Статус:** Проект целевой архитектуры (Autonomous Core)

Этот документ описывает целевую архитектуру CodeAI-Hub, в которой ядро системы (Core Orchestrator) становится автономным, независимым от UI-клиентов (VS Code Extension, CEF Launcher, CLI), а все клиенты и модули-провайдеры рассматриваются как подключаемые компоненты к уже работающему ядру.

Документ должен служить основой для подготовки нового `doc/TODO/todo-plan.md` и планирования рефакторинга.

---

## 1. Цели и мотивация

### 1.1. Проблемы текущей архитектуры

По результатам экспериментов (фиксированы в `doc/Sessions/Session126.md`) и практического использования выявлены ключевые проблемы:

1. **Ядро зависит от UI-клиентов**:
   - Старт ядра жёстко привязан к жизненному циклу VS Code extension или CEF launcher.
   - Существует логика `ensureCoreAndProviders` / `ensureStarted` на стороне extension/launcher, которая решает, когда и как запускать ядро.

2. **Неустойчивость при смене "хозяина" ядра**:
   - Когда **лаунчер** поднимает и мониторит ядро, а VS Code extension только подключается (`attach`), система ведёт себя стабильно.
   - Когда **extension** становится владельцем жизненного цикла ядра (поднимает его сам), каждая перезагрузка VS Code/расширения приводит к перезапуску ядра и потере активных сессий.

3. **Провайдеры завязаны на UI и старт ядра**:
   - Установка/инициализация модулей Claude/Codex/Gemini частично выполняется при старте клиентов.
   - Ядро не умеет само поднимать провайдеры из локального реестра; без UI оно не является полностью рабочим сервисом.

4. **Сценарий автономного управления ядром невозможен**:
   - Скрипт `codeai-core-control.js` (ручной контроль ядра: start/stop/status) не может запустить ядро, пока оно жёстко привязано к UI.
   - Это противоречит идее "ядро как центральный сервис" и мешает использованию ядра как системного демона.

### 1.2. Целевое видение

Цель рефакторинга — перейти к архитектуре **Autonomous Core**:

- Ядро — **центральный, автономный сервис**, который можно запускать и останавливать независимо от UI.
- Любой клиент (VS Code extension, launcher, CLI, внешний процесс) — всего лишь **клиент живого ядра**, который:
  - не принимает решений о запуске/перезапуске ядра;
  - не занимается установкой/инициализацией провайдеров;
  - лишь подключается, запрашивает статус и отображает состояние.
- Провайдеры — **плагиноподобные модули** ядра. Ошибка или отсутствие одного провайдера не валит ядро целиком, а просто делает конкретный провайдер `inactive`.
- Управление жизненным циклом ядра и провайдеров сосредоточено в самом ядре и в одном специализированном компоненте — **Core Supervisor**.

## 2. Глоссарий и роли

### 2.1. Core Orchestrator (ядро)

- Реализуется в пакете `packages/core`:
  - основной файл оркестратора: `packages/core/src/orchestrator/core-orchestrator.ts`;
  - статус и health: `packages/core/src/status/runtime-status-reporter.ts`;
  - удалённый мост для клиентов: `packages/core/src/remote-bridge/index.ts`;
  - управление сессиями: `packages/core/src/session-manager/index.ts`;
  - работа с unified session storage: `packages/core/src/unified-session/storage.ts`.
- Отвечает за:
  - запуск HTTP/WebSocket API;
  - управление сессиями, провайдерами, unified session storage;
  - логирование и диагностику.

### 2.2. Core Supervisor (надзорный процесс ядра)

- Отдельный процесс/скрипт, эволюция текущего `codeai-core-control.js`.
- Обязанности:
  - гарантировать, что ядро запущено (команда `start`);
  - корректно останавливать ядро (команда `stop`);
  - предоставлять однозначный статус (команда `status` → `running | starting | stopped | failed`).
- Знает:
  - где находится runtime и бинарь/бандл ядра (`~/.codeai-hub/core/<platform>/<version>`);
  - какой порт/host использует ядро;
  - где хранится lock-файл/registry (`~/.codeai-hub/state/runtime-registry.json`).

### 2.3. UI-клиенты

1. **VS Code Extension** (расширение):
   - реализуется в `src/extension.ts` и модуле `src/extension-module/**`;
   - содержит `HomeViewProvider`, message router и логику подключения к ядру;
   - после рефакторинга НЕ отвечает за запуск/restart ядра и установку провайдеров.

2. **CEF Launcher** (десктопный лаунчер):
   - код лаунчера: `packages/cef-launcher/src/**`;
   - сейчас содержит логику запуска ядра и health monitoring;
   - после рефакторинга превращается в ещё одного клиента, использующего Core Supervisor.

3. **CLI / вспомогательные скрипты**:
   - `codeai-core-control.js` и потенциальный CLI для разработчиков;
   - будут использовать те же команды `start/stop/status`, что и UI-клиенты.

### 2.4. Provider Modules (модули провайдеров)

- Реализуются отдельными пакетами:
  - Claude: `packages/Claude_Module/**`;
  - Codex: `packages/Codex_Module/**`;
  - Gemini: `packages/Gemini_Module/**`.
- В каждом модуле:
  - адаптеры провайдера: `src/provider/**`;
  - управление сессиями и жизненным циклом провайдера: `src/session/**`;
  - установка/инсталляция SDK/CLI: `src/installer/**`.
- После рефакторинга:
  - их инсталляция инициируется **не UI**, а отдельной процедурой (например, через Core Supervisor / CLI команду `Repair installation`);
  - ядро на старте только обнаруживает уже установленные модули и подключает их как плагины.

## 3. Высокоуровневая целевая модель (Autonomous Core)

### 3.1. Общая схема

На высоком уровне новая архитектура выглядит так:

```mermaid
graph TD
  subgraph System
    Core[Core Orchestrator]\n(packages/core)
    Supervisor[Core Supervisor]\n(codeai-core-control.js)
  end

  VSCode[VS Code Extension]\n(src/extension-module/**) -->|attach via RemoteBridge| Core
  Launcher[CEF Launcher]\n(packages/cef-launcher) -->|attach via RemoteBridge| Core
  CLI[CLI / Dev Tools] -->|start/stop/status| Supervisor

  VSCode -->|ensure core ready| Supervisor
  Launcher -->|ensure core ready| Supervisor

  subgraph Providers
    Claude[Claude Module]\n(packages/Claude_Module)
    Codex[Codex Module]\n(packages/Codex_Module)
    Gemini[Gemini Module]\n(packages/Gemini_Module)
  end

  Claude -->|register & init| Core
  Codex -->|register & init| Core
  Gemini -->|register & init| Core
```

Ключевые принципы:

1. **Ядро — единственный источник истины**:
   - все UI-клиенты работают только через публичные API ядра (HTTP/WS);
   - информация о сессиях, провайдерах и состоянии хранится и обрабатывается в ядре.

2. **Core Supervisor — один владелец жизненного цикла ядра**:
   - только он занимается фактическим запуском/остановкой процесса core;
   - любое обращение `start` от клиентов приводит к одному и тому же поведению: "если живо — не трогать; если мёртво — запустить".

3. **UI-клиенты — attach-only**:
   - VS Code extension и CEF launcher больше никогда не содержат логики `ensureCoreAndProviders`;
   - их ответственность — гарантировать, что Supervisor вернул `ready`, и затем подключиться к работающему ядру.

4. **Провайдеры — плагины, а не условия старта**:
   - ядро стартует даже при отсутствии части провайдеров;
   - провайдер может быть в статусе `inactive`, и это не мешает core обслуживать другие провайдеры и сессии.

## 4. Жизненный цикл ядра

### 4.1. Старт ядра

1. Клиент (VS Code extension или Launcher) инициирует запуск ядра так:
   - вызывает команду Core Supervisor `start` (через CLI/Node API);
   - ожидает статус `ready` или ошибку.

2. Core Supervisor:
   - проверяет по lock-файлу и/или `runtime-registry`:
     - если ядро уже запущено и отвечает по `/api/v1/health` → возвращает `running`/`ready` без действий;
     - если ядро не запущено → запускает новый процесс core.
   - ждёт ответа от эндпоинта готовности ядра (`/api/v1/status`/`/health`);
   - при успешном старте обновляет `runtime-registry.json` и возвращает клиенту `ready`.

3. Ядро при старте:
   - инициализирует собственную конфигурацию (`packages/core/src/config/index.ts`);
   - читает registry (`~/.codeai-hub/state/runtime-registry.json`);
   - стартует HTTP/WS-сервер (RemoteBridge);
   - запускает инициализацию провайдеров (см. раздел 5).

### 4.2. Время жизни (TTL)

Цель: ядро должно **жить независимо от перезапусков UI-клиентов** и не останавливаться при каждом закрытии окна VS Code или лаунчера.

Базовая модель:

- Ядро живёт **не менее часа после последней активности** (TTL ≥ 60 минут), при этом:
  - под "активностью" понимается любой входящий запрос клиента (HTTP/WS) или активная сессия;
  - ядро или Supervisor сбрасывают idle-таймер при любой активности.
- Дополнительно предусматривается режим "долго живущее ядро":
  - TTL может быть конфигурируемым вплоть до "бесконечного" (ядро живёт до ручной остановки или перезагрузки системы).

Механизм TTL должен быть реализован **в ядре и/или Supervisor**, а не в UI:

- ядро сообщает в статусе (`/status`), сколько времени осталось до auto-shutdown (если применимо);
- Supervisor может инициировать мягкую остановку после истечения TTL, а UI только отображают это состояние.

### 4.3. Остановка ядра

Остановка — всегда **явное действие** Core Supervisor или TTL-механизма, а не побочный эффект закрытия UI:

- Supervisor выполняет `stop`:
  - отправляет в ядро запрос на graceful shutdown (`/api/v1/shutdown`);
  - ждёт завершения процесса в заданный тайм-аут;
  - при необходимости выполняет форсированное завершение.
- UI-клиент может лишь инициировать `stop` через Supervisor (например, команда "Stop Core" в UI).

### 4.4. Ошибки и перезапуск

- Если ядро падает по внутренней ошибке:
  - Supervisor фиксирует это как `failed` с кодом ошибки/причиной в логах;
  - перезапуск происходит только по явному запросу (`start`) либо по политике auto-restart Supervisor (если такая будет введена отдельно).
- UI при этом:
  - видят статус ядра как `failed` через Supervisor или `/status`;
  - не выполняют самовольный рестарт ядра.

## 5. Автономная инициализация провайдеров

### 5.1. Цели

- Поднять провайдеры **один раз** при старте ядра.
- Не трогать провайдеры при подключении/отключении UI.
- Обеспечить устойчивость: ошибка одного провайдера не валит ядро и не мешает другим.

### 5.2. Процесс инициализации провайдера

При старте ядро выполняет следующие шаги (логика сосредоточена вокруг `packages/core/src/provider-registry/index.ts`):

1. Читает реестр установленных провайдеров из файловой системы:
   - базовый путь: `~/.codeai-hub/providers/<provider>/<version>/`;
   - наличие `install.json`/маркерных файлов подтверждает установку.

2. Для каждого провайдера ядро:
   - пытается загрузить адаптер (Claude/Codex/Gemini) как модуль Node.js;
   - выполняет инициализацию (SDK, CLI-bridge и т.д.) **один раз на старт ядра**;
   - регистрирует провайдера в `ProviderRegistry` со статусом `active`.

3. Если при инициализации или последующей работе возникает ошибка:
   - ядро записывает детальную ошибку в лог (`core.log` + отдельные логи провайдера);
   - выставляет статус провайдера `inactive` или `degraded` и продолжает запуск/работу остальных;
   - **ядро не падает** целиком.

4. По завершении инициализации:
   - эндпоинт `/status` возвращает список провайдеров и их статусы `active/inactive/degraded` вместе с диагностикой;
   - UI-клиенты строят меню/список провайдеров исходя из этого статуса.

### 5.3. Поведение UI при неактивных провайдерах

- Если провайдер есть в реестре, но статус `inactive`:
  - он отображается в списке провайдеров, однако недоступен для выбора при создании новой сессии;
  - UI показывает подсказку/диагностику (на основе поля `reason` или `diagnostics`, которое ядро может отдавать вместе со статусом).
- Ни extension, ни launcher не пытаются "починить" провайдера автоматически.

### 5.4. Установка и ремонт провайдеров

Операции установки/ремонта провайдеров выносятся в отдельный, явный процесс:

- Инструменты/скрипты установки провайдера находятся в:
  - Claude: `packages/Claude_Module/src/installer/**`;
  - Codex: `packages/Codex_Module/src/installer/**`;
  - Gemini: `packages/Gemini_Module/src/installer/**`.
- Core Supervisor или отдельный CLI предоставляет команды вида:
  - `install-provider --name claude`;
  - `repair-provider --name gemini`.
- UI-клиенты могут вызвать эти команды через Supervisor (например, кнопка "Repair installation"), но не содержат внутри логики установки.

## 6. Контракты UI-клиентов в новой архитектуре

### 6.1. VS Code Extension

Ключевые роли extension в целевой архитектуре:

- Использовать Core Supervisor и RemoteBridge как единственный способ работы с ядром:
  - `CoreProcessManager` больше не запускает процессы напрямую и не содержит `ensureCoreAndProviders`;
  - последовательность: `Supervisor.start()` (через CoreProcessManager) → ожидание `ready` → `attach` к уже работающему ядру.

- Не выполнять скрытую установку ядра и провайдеров при активации:
  - `core-installer.ts` отвечает только за доставку core runtime при отсутствии установленной версии;
  - провайдеры (Claude/Codex/Gemini) устанавливаются скриптами/CLI, а extension лишь отображает их статус и, при необходимости, триггерит явный сценарий Repair через Supervisor/CLI.

- Делегировать управление жизненным циклом ядра Supervisor’у:
  - выбор порта, lock-файл и мониторинг процесса находятся на стороне Supervisor;
  - extension использует только публичные контракты (`start`/`stop`/`status`) и WebSocket‑подключение.

- Сохранять responsiblity за UX:
  - `core-keep-alive.ts` поддерживает живое подключение к ядру через WebSocket, не инициируя перезапуск ядра;
  - UI‑компоненты (HomeView, provider picker, status panel) отображают состояние Supervisor, список провайдеров и их статусы `active/inactive/degraded`.

### 6.2. CEF Launcher

Ключевые модули (пакет `packages/cef-launcher` и связанные extension-модули):

Ключевые модули (пакет `packages/cef-launcher` и связанные extension-модули):

- `packages/cef-launcher/src/core_launcher.cc`, `launcher_app.cc`, `launcher_handler.cc`
  - Лаунчер больше не запускает core напрямую через `node dist/index.js` и не управляет lock-файлом:
    - старт ядра выполняется через Core Supervisor (`codeai-core start`), лаунчер ожидает доступности API и затем подключается к RemoteBridge;
    - мониторинг здоровья опирается на `/api/v1/status`; при недоступности ядра лаунчер пишет диагностические сообщения, но не выполняет самовольный рестарт.

- `src/extension-module/cef/launcher.ts`, `launcher-installer.ts`, `runtime-installer.ts`, `runtime-files.ts`
  - Extension отвечает только за установку и обновление лаунчера и CEF‑runtime;
  - все операции, связанные со стартом/остановкой core, выполняются через Supervisor, а не через CEF‑обвязку.

### 6.3. CLI и dev-инструменты

- Скрипт `codeai-core-control.js` (расположен вне репозитория, но логика должна быть отражена в кодовой базе — например, в `packages/core` или отдельном пакете `packages/core-supervisor`).
- План:
  - формализовать интерфейс CLI: `start`, `stop`, `status`, `install-provider`, `repair-provider`;
  - реализовать этот интерфейс как часть проекта, чтобы и extension, и launcher использовали единый механизм.

## 9. Риски и открытые вопросы

1. **Интеграция Supervisor с ОС**:
   - Будет ли Supervisor запускаться как сервис (systemd/LaunchAgent), или останется только CLI-утилитой?
   - Нужно определить минимально жизнеспособный сценарий для разработчика и обычного пользователя.

2. **Совместимость с текущими релизами**:
   - Необходимо продумать, как автономный core будет сосуществовать с уже установленными версиями (миграция конфигов, registry, логов).

3. **Управление версиями провайдеров**:
   - Требуется чёткая стратегия выбора версии провайдера при наличии нескольких копий;
   - Нужно определить политику совместимости ядра и модулей (минимальные/максимальные версии).

4. **Диагностика отказов провайдеров**:
   - Формат и уровень детализации ошибок, которые ядро будет передавать UI;
   - Как предоставлять рекомендации пользователю (например, "переустановите Gemini CLI").

5. **Безопасность и многопользовательские сценарии**:
   - Если ядро будет работать как long-lived процесс, важно продумать права доступа, разделение окружений и логов.
