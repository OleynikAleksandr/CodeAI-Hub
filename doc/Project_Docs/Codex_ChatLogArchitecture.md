# Архитектура нормализованных чат-логов

## Цель
Сформировать единый источник данных для отображения истории сессий в интерфейсах CodeAI-Hub, не вмешиваясь в форматы JSONL, которые ведут сами AI-провайдеры. Наши нормализованные логи служат основой для real-time показа, рефреша UI и Resume старых сессий.

## Контекст и ограничения
- Провайдеры (Claude, Codex, Gemini) продолжают писать свои JSONL-файлы, которые используются SDK для поддержания контекста и Resume на стороне провайдеров. Мы не заменяем и не модифицируем эти файлы.
- Форматы real-time потоков и файлов у провайдеров различаются, поэтому требуется thin-wrapper, приводящий события к общему виду.
- Нужен единый парсер для UI, чтобы избегать дублирования логики между live-потоком и восстановлением истории.
- В перспективе появятся многопровайдерные сессии; архитектура должна позволять расширение без пересмотра базовых решений.

## Общая схема потоков
1. SDK-провайдер отдаёт real-time события (assistant/user/tool/meta) с уникальным `providerSessionId`.
2. Адаптер провайдера преобразует событие в нормализованный формат и:
   - синхронно пишет запись в наш JSONL-файл;
   - прокидывает событие в UI через RemoteBridge.
3. При рефреше интерфейса или Resume мы читаем наш JSONL-файл и воспроизводим события в UI в том же формате.
4. Провайдер для продолжения сессии читает **свои** файлы; зависимости между их файлами и нашими отсутствуют.

## Размещение файлов
- Базовая директория: `~/.codeai-hub/logs/chat/<provider>/<sessionId>/`.
- Для каждой сессии один основной файл: `<sessionId>.jsonl`.
- Дополнительные файлы (например, snapshot метаданные) размещаются рядом, но их структура описывается отдельно.

## Формат JSONL
Каждая строка — валидный JSON-объект, кодировка UTF-8.

Обязательные поля:
- `version`: строка, версия схемы (например, `"1"`).
- `timestamp`: ISO 8601 в UTC, отражает момент записи.
- `sessionId`: строка, идентификатор сессии (совпадает с SDK).
- `provider`: строка (`"claude"`, `"codex"`, `"gemini"`, и т. д.).
- `eventType`: строка (`"user"`, `"assistant"`, `"tool"`, `"system"`, `"meta"`).
- `payload`: объект с нормализованными данными.

Рекомендованные поля payload:
- для `user`/`assistant`: `text`, `annotations`, `attachments`.
- для `tool`: `toolName`, `request`, `response`, `status`.
- для `meta`: `kind` (например, `stream-start`, `stream-end`, `error`), `details`.

Расширения формата оформляются через `payload.extensions` (объект с namespaced ключами) и документируются отдельно.

## Жизненный цикл
- **Создание**: при старте новой сессии создаётся директория и файл; первая запись — мета-событие `session-open`.
- **Дополнение**: все события проходят через один writer; порядок строк соответствует порядку доставки в UI.
- **Завершение**: финальная запись `session-close` с итоговой статистикой; файл закрывается, writer освобождает ресурсы.
- **Resume/Refresh**: при возобновлении UI читает файл целиком (или инкрементально, если известно смещение) и воспроизводит события.
- **Ротация**: политика очистки описывается отдельно; по умолчанию файлы хранятся до явного удаления пользователем.

## Требования к следующему этапу (для планирования)
- Специфицировать интерфейсы writer/adapter в core и контракт RemoteBridge → UI.
- Определить набор событий и структуру `payload` для каждого eventType.
- Спроектировать API UI для чтения JSONL (full replay и incremental tail).
- Описать политику каталогов и управление правами доступа.
- Подготовить стратегию миграции с имеющихся логов (если требуется сохранение истории).
