## 1. Контекст и цели консилиума

Цель сценария “Консилиум”:
- Позволить пользователю вести **один логический чат**, в котором участвуют **несколько провайдеров одновременно** (Claude, Codex, Gemini).
- Каждый провайдер:
  - видит **полный контекст** диалога;
  - слышит ответы других провайдеров;
  - действует согласно **своей роли** (решатель, критик, арбитр и т.п.).
- Пользователь выступает ведущим: задаёт вопросы, переключает режимы, принимает финальное решение.

Ключевое ограничение:
- API провайдеров позволяют посылать только `user`-сообщения и получать `assistant`-ответы.
- Мы **не можем** встроить ответы одного ассистента напрямую как `assistant`-сообщения для другого;  
  всё, что видит провайдер — это текст от имени пользователя.

Отсюда следует необходимость:
- **центрального Оркестратора**, который:
  - определяет роли провайдеров;
  - управляет раундами (phases/rounds);
  - решает, какие части unified-истории и в каком виде пересказывать каждому провайдеру;
  - контролирует, чтобы не возникал хаос (все говорят одновременно, никто никого не слышит).

## 2. Использование UnifiedSessionArchitecture

В `UnifiedSessionArchitecture` уже заложена идея:

```text
~/.codeai-hub/sessions/{workspace-slug}/
├── claude/{sessionId}.jsonl
├── codex/{sessionId}.jsonl
├── gemini/{sessionId}.jsonl
└── combined/
    ├── claude-codex/      (будущее)
    ├── claude-gemini/     (будущее)
    ├── codex-gemini/      (будущее)
    └── all/               (будущее - все 3 провайдера)
```

Для консилиума естественным становится путь:

- вести историю такого чата в:

```text
~/.codeai-hub/sessions/{workspace-slug}/combined/all/{sessionId}.jsonl
```

- хранить там **единый Unified JSONL**, в котором:
  - `role` — `user | assistant | system | tool`;
  - `providerId` — для всех не-user сообщений: `claude | codex | gemini | orchestrator`;
  - `metadata` — расширяется для поддержки ролей консилиума и фаз.

Таким образом:
- консилиум — это **частный случай combined-сессии**, но с дополнительным уровнем управления: PanelState/Orchestrator.

## 3. Слои архитектуры консилиума

### 3.1. Unified JSONL (каноническая история)

- Хранит:
  - все пользовательские сообщения;
  - все ответы провайдеров, с указанием `providerId`;
  - системные маркеры:
    - смена раунда;
    - назначение ролей;
    - финальные выводы.
- Выступает:
  - источником истины для UI;
  - источником контекста для всех провайдеров (через Out-адаптеры).

### 3.2. PanelState (состояние консилиума)

Отдельная структура в ядре, отражающая “режиссуру” сессии:

```ts
type PanelRole = 'solver' | 'critic' | 'arbiter' | 'observer';

interface ProviderPanelConfig {
  providerId: 'claude' | 'codex' | 'gemini';
  role: PanelRole;
  enabled: boolean;
}

type PanelPhase =
  | 'initial-opinions'   // первый раунд ответов
  | 'critique'           // критика/обсуждение
  | 'arbitration'        // финальная оценка/вердикт
  | 'custom';            // расширение на будущее

interface PanelState {
  sessionId: string;
  providers: ProviderPanelConfig[];
  currentPhase: PanelPhase;
  roundNumber: number;
  // Дополнительно: правила, лимиты, настройки пользователя
}
```

Назначение PanelState:
- знать, какие провайдеры участвуют в консилиуме;
- понимать, **кто** сейчас должен говорить и **в какой роли**;
- служить входом для Out-адаптеров при формировании запросов.

### 3.3. Orchestrator (управление раундами)

Оркестратор консилиума:
- отслеживает события:
  - новые сообщения пользователя;
  - завершение ответов от провайдеров;
  - команды UI (смена фаз, отключение провайдера, смена ролей).
- на основе PanelState:
  - решает, кому и когда отправлять запрос;
  - формирует для каждого провайдера **свой текст** user- сообщения, включающий:
    - исходный запрос пользователя;
    - нужные ответы других провайдеров;
    - инструкцию по роли (“ты критик”, “ты арбитр” и т.п.);
  - фиксирует раунды и переходы фаз в Unified JSONL (как `system`-сообщения).

## 4. Роли и сценарии консилиума

### 4.1. Базовые роли

- **Solver (решатель)**  
  Задача: предложить прямое решение/ответ на запрос пользователя.

- **Critic (критик)**  
  Задача: анализировать ответы других (обычно Solver), искать ошибки, пробелы, альтернативы.

- **Arbiter (арбитр)**  
  Задача: взвесить все ответы, отфильтровать шум, сформулировать взвешенный финальный ответ для пользователя.

- **Observer (наблюдатель)**  
  Не обязательно даёт ответы; может собирать мета-информацию, подсчитывать риски, предлагать план действий.

Роли назначаются в PanelState и могут динамически меняться по ходу сессии.

### 4.2. Сценарий A: “Панель мнений + один круг обсуждения”

1. **Фаза `initial-opinions` (Раунд 1)**  
   - Пользователь задаёт вопрос.
   - Оркестратор:
     - записывает `user`-сообщение в Unified JSONL;
     - рассылает одинаковый запрос всем включённым провайдерам, независимо от роли (как Solver’ам).
   - Все провайдеры дают ответы, которые:
     - врапятся через ProviderInAdapter → UnifiedMessage;
     - попадают в Unified JSONL с `providerId` каждого.

2. **Фаза `critique` (Раунд 2)**  
   - Оркестратор собирает ответы из Unified JSONL.
   - Для каждого провайдера P формирует новое `user`-сообщение:
     - включает:
       - исходный вопрос пользователя;
       - “портрет” всех ответов:
         - `Ответ Claude: ...`
         - `Ответ Codex: ...`
         - `Ответ Gemini: ...`
       - инструкцию по роли:
         - “Твоя задача: проанализировать ответы других, отметить сильные и слабые стороны, предложить улучшения. Не повторяй дословно свой предыдущий ответ.”
   - Ответы в этой фазе тоже нормализуются в Unified JSONL, но в `metadata` фиксируется, что это сообщения фазы `critique`.

3. **Фаза `arbitration` (опционально Раунд 3)**  
   - Оркестратор выбирает одного провайдера (или специальную роль `arbiter`).
   - Формирует для него user- сообщение:
     - “Вот исходный вопрос, вот ответы всех, вот критика.  
        Твоя задача: вынести взвешенный вердикт и предложить финальный ответ пользователю.”
   - Ответ арбитра становится:
     - финальным предложением пользователю (можно выделить в UI);
     - частью Unified JSONL с `providerId` арбитра и фазой `arbitration`.

### 4.3. Сценарий B: Жёсткие роли с начала

1. При старте консилиума:
   - в PanelState задаются роли:
     - Claude — `solver`,
     - Codex — `critic`,
     - Gemini — `arbiter`.

2. **Фаза `initial-opinions`**  
   - Пользователь задаёт вопрос.
   - Оркестратор отправляет запрос **только solver’у**:
     - “Ты решатель. Ответь на вопрос пользователя.”
   - Ответ solver’а сохраняется в Unified JSONL.

3. **Фаза `critique`**  
   - Оркестратор формирует для `critic`:
     - “Вот вопрос пользователя.  
        Вот ответ решателя.  
        Твоя задача — найти ошибки, слабые места, предложить улучшения, но не переписывать всё с нуля.”
   - Ответ критика тоже сохраняется в Unified JSONL.

4. **Фаза `arbitration`**  
   - Оркестратор формирует для `arbiter`:
     - “Вот вопрос, вот ответ решателя, вот критика.  
        Твоя задача — взвесить аргументы и дать финальный ответ.”
   - Финальный ответ арбитра становится итогом консилиума.

Этот сценарий даёт максимально структурированное поведение и минимизирует хаос.

## 5. Out-адаптеры в консилиуме

Out-адаптеры (см. документ по смене провайдера) здесь получают дополнительный контекст — PanelState и фазу.

```ts
interface ConsiliumOutAdapterContext extends ProviderOutAdapterContext {
  panelState: PanelState;
  targetProviderId: 'claude' | 'codex' | 'gemini';
}

interface ConsiliumOutAdapter {
  buildConsiliumPrompt(ctx: ConsiliumOutAdapterContext): ProviderOutAdapterResult;
}
```

Задача ConsiliumOutAdapter:
- из Unified JSONL и PanelState:
  - выбрать, какие сообщения показать провайдеру;
  - как пометить (например, `Ответ Claude: ...`, `Критика Codex: ...`);
  - какую инструкцию по роли добавить.

При этом:
- в prompt текст всегда идёт как `user`-сообщение;
- роль “assistant”, “critic”, “arbiter” — только в инструкции и структуре текста.

## 6. Расширения Unified JSONL для консилиума

Чтобы поддержать консилиум, Unified JSONL должен хранить:

- `providerId` — уже есть.
- `metadata.panel`:

```ts
interface PanelMetadata {
  role?: PanelRole;          // роль автора сообщения в рамках консилиума
  phase?: PanelPhase;        // фаза (initial-opinions / critique / arbitration / ...)
  round?: number;            // номер раунда
  shownTo?: string[];        // (опционально) каким провайдерам это сообщение было явно показано
}
```

Таким образом:
- UI может визуализировать, кто что говорил в какой роли;
- Orchestrator может анализировать историю (например, какие ответы уже были учтены в критике/арбитраже).

## 7. Интеграция с переключением провайдера

Смена провайдера внутри консилиума:
- естественный частный случай:
  - можно:
    - добавить нового провайдера как `solver` / `critic` / `arbiter`;
    - временно отключить другого (через `enabled: false` в PanelState).
- Контекст для нового провайдера:
  - строится по тем же правилам, что и в документе о смене провайдера;
  - но дополнительно учитывает фазу и роли:
    - какие ответы ему показываются;
    - под какой инструкцией.

Таким образом:
- “просто смена провайдера” и “консилиум” живут в одной архитектурной плоскости;
- отличие — только в PanelState и сценариях управления.

## 8. Фазы реализации консилиума

### Фаза 1 — Базовый консилиум (панель мнений)

- Реализовать:
  - хранение combined-сессии `combined/all/{sessionId}.jsonl`;
  - PanelState с примитивной моделью (фаза `initial-opinions`, без ролей);
  - Orchestrator, который:
    - при вопросе пользователя отправляет один и тот же запрос всем выбранным провайдерам;
    - собирает их ответы и пишет в Unified JSONL.
- UI:
  - отображает ответы всех провайдеров по вертикали;
  - отмечает `providerId` (иконки/цвета).

### Фаза 2 — Добавление роли Critic

- Расширить PanelState:
  - ввод ролей `solver` и `critic`.
- Добавить фазу `critique`:
  - после первого раунда ответов:
    - Orchestrator формирует для `critic` промпт с ответами solver’ов;
    - ответ критика сохраняется с `role: 'assistant'` и `metadata.panel.role = 'critic'`.
- UI:
  - визуально различает ответы solver’ов и критику.

### Фаза 3 — Добавление роли Arbiter

- Ввести роль `arbiter` и фазу `arbitration`.
- Orchestrator:
  - собирает исходный вопрос, ответы и критику;
  - формирует промпт для арбитра;
  - принимает финальный ответ.
- UI:
  - позволяет пользователю быстро увидеть финальный вердикт;
  - при желании — раскрыть “внутреннюю кухню” консилиума.

### Фаза 4 — Расширенные сценарии

- Поддержка кастомных фаз и ролей.
- Настройки пользователя:
  - какие провайдеры участвуют;
  - какие роли им назначены;
  - сколько раундов и при каких условиях.

## 9. Риски и вопросы

- **Сложность UX.**  
  Консилиум легко превратить в перегруженный интерфейс. Нужно:
  - аккуратно подать роли и раунды;
  - дать возможность “свернуть” технические детали и видеть только итог.

- **Стоимость по токенам.**  
  Пересказ ответов и критики в prompt каждого провайдера может быть дорогим. Требуется:
  - продуманная политика суммаризации;
  - настройка глубины контекста.

- **Поведение провайдеров.**  
  Некоторые модели могут “сбиваться” от слишком сложных инструкций (роль + много вложенных ответов). Нужно:
  - тестировать разные подсказки;
  - выработать стайлгайд промптов для ролей.

- **Согласованность ролей.**  
  Роли и фазы должны быть понятно описаны в документации, чтобы их можно было воспроизвести и расширить.

---

## 10. Вывод

Архитектура консилиума строится на уже существующем фундаменте:

- Unified JSONL как единый лог;
- combined-сессии для мульти-провайдерских чатов;
- двусторонние враперы (In/Out) для нормализации и генерации контекста.

Добавляя поверх этого:
- PanelState (роли, фазы, раунды);
- Orchestrator, который управляет, **кто кому и что говорит**,

мы получаем гибкую платформу для сложных коллективных сценариев:
- от простого “хочу услышать всех сразу”,
- до структурированных панелей с solver/critic/arbiter,
- не ломая изоляцию провайдеров и не входя в конвертацию их нативных логов.
