## 1. Контекст и проблема

В текущей архитектуре CodeAI Hub:
- Есть три AI-провайдера: Claude, Codex, Gemini.
- Каждый провайдер:
  - ведёт **свои** локальные JSONL-файлы (их территория) и использует их для продолжения контекста;
  - отдаёт real-time stream в собственном формате.
- CodeAI Hub строит над этим **унифицированный слой сессий**:
  - для каждого провайдера записывается `~/.codeai-hub/sessions/{workspace-slug}/{providerId}/{sessionId}.jsonl` в едином формате (Unified JSONL);
  - UI читает и отображает только **наш** Unified JSONL;
  - родные JSONL провайдеров остаются непрозрачными для нас (мы их не трогаем).

Проблема, которую нужно решить:
- Пользователь начинает диалог с провайдером A (например, Claude).
- В какой-то момент хочет **переключиться** на провайдера B (Codex или Gemini),  
  при этом:
  - B должен получить **весь релевантный контекст** предыдущего диалога;
  - UI должен продолжать видеть **единый** лог, не “рвать” историю;
  - мы не хотим конвертировать нативные JSONL A → нативные JSONL B (слишком сложно и хрупко).

## 2. Базовая архитектура сессий (напоминание)

### 2.1. Двухслойная система логов

1. **Слой провайдера (их территория)**
   - Claude: `~/.claude/projects/.../*.jsonl`
   - Codex: `~/.codex/sessions/.../*.jsonl`
   - Gemini: `~/.gemini/tmp/.../chats/*.json`
   - Назначение: провайдеры сами используют эти файлы для context continuation.
   - Политика: CodeAI Hub **не читает, не модифицирует** эти файлы.

2. **Слой CodeAI Hub (наша территория)**
   - `~/.codeai-hub/sessions/{workspace-slug}/{providerId}/{sessionId}.jsonl`
   - Формат: **Unified JSONL**, общий для всех провайдеров (см. UnifiedSessionArchitecture).
   - Назначение: UI-отображение (live-stream, refresh, resume), будущие multi-provider-сценарии.
   - Политика:
     - пишем только через враперы;
     - читаем единым парсером;
     - не содержим сырых SDK payload’ов, только нормализованные сообщения.

### 2.2. ProviderWrapper (в текущей архитектуре)

Для каждого провайдера есть враперы (In-адаптеры), которые:
- принимают real-time stream и/или события из родного JSONL;
- **нормализуют** их в `UnifiedMessage`;
- работают как:

```ts
type UnifiedMessage = {
  timestamp: string;
  role: 'user' | 'assistant' | 'system' | 'tool';
  providerId: 'claude' | 'codex' | 'gemini';
  content: string;
  metadata?: Record<string, unknown>; // thinking, tool-calls и т.п.
};

// Схематично:
ProviderWrapperIn.handleRawEvent(rawEvent) -> UnifiedMessage -> UnifiedSessionStorage.append(...)
```

Unified JSONL уже задуман как **каноническая лента диалога** для UI.

## 3. Цели и ограничения для смены провайдера

### 3.1. Цели

- Позволить пользователю **переключать провайдера** в рамках одной логической сессии.
- Дать новому провайдеру **релевантный контекст**:
  - историю диалога,
  - ответы предыдущего провайдера
  - (возможно) краткое резюме длинной истории.
- Сохранить:
  - простую и устойчивую архитектуру логов;
  - независимость от внутренних форматов SDK;
  - единое UI-представление через Unified JSONL.

### 3.2. Ограничения

- API провайдеров понимают только схему `user → assistant`.  
  Любое содержимое, которое мы передаем, будет воспринято как слова пользователя.
- Мы **не можем**:
  - честно “переиграть” чужой native JSONL как будто он родной;
  - полностью восстановить внутренний формат SDK из Unified JSONL (часть деталей уже отброшена).
- Мы **не хотим**:
  - конвертировать native JSONL одного провайдера в native JSONL другого;
  - ломать изоляцию провайдеров.

---

## 4. Ключевая идея: Unified JSONL как источник истины

Архитектурное решение:

1. **Канонический лог диалога** — это Unified JSONL, а не нативные логи провайдеров.
2. При смене провайдера:
   - мы **читаем** unified-лог для данной UI-сессии;
   - строим для нового провайдера **контекст** (prompt/историю) на его языке;
   - запускаем для него новую нативную сессию, но уже с “готовым” контекстом.
3. Нативные JSONL каждого провайдера остаются локальной оптимизацией:
   - могут использоваться самим SDK;
   - но не участвуют в cross-provider конвертации.

Таким образом, смена провайдера всегда выглядит как:

```text
Unified JSONL (канон) → ProviderWrapperOut(newProvider) → prompt/контекст нового провайдера
```

а не:

```text
NativeLog(A) → (сложная конвертация) → NativeLog(B)
```

## 5. Двусторонние враперы: In/Out адаптеры

### 5.1. In-адаптеры (уже есть концептуально)

```ts
interface ProviderInAdapter {
  providerId: 'claude' | 'codex' | 'gemini';
  handleStreamEvent(event: ProviderRawEvent): UnifiedMessage[];
  // Опционально: handleNativeLogLine(line: string): UnifiedMessage | null;
}
```

Задача:
- превратить real-time поток/родные логи в последовательность UnifiedMessage;
- захватить только то, что **нужно UI и оркестратору**.

### 5.2. Out-адаптеры (новый элемент)

```ts
interface ProviderOutAdapterContext {
  unifiedHistory: UnifiedMessage[];
  // Политика контекста (см. ниже)
  contextPolicy: ContextPolicyConfig;
}

interface ProviderOutAdapterResult {
  promptMessages: ProviderPromptMessage[]; // то, что пойдет в SDK
  syntheticNativeLogEntries?: string[];    // опционально: для реконструкции native JSONL
}

interface ProviderOutAdapter {
  providerId: 'claude' | 'codex' | 'gemini';
  buildContext(ctx: ProviderOutAdapterContext): ProviderOutAdapterResult;
}
```

Задача:
- взять Unified JSONL (каноническую историю);
- применить политику построения контекста;
- построить структуру сообщений под конкретный SDK.

Важно:  
Out-адаптер **не обязан** восстанавливать native JSONL в точности,  
его задача — предоставить провайдеру **семантически корректный** контекст.

## 6. Поток при смене провайдера

Предположим, есть UI-сессия `S`, которая шла с провайдером `A`, и пользователь хочет переключиться на `B`.

### 6.1. Шаг 1: Определение типа сессии

Есть два сценария:

1. **Single-provider сессия**  
   - История хранится в:
     - `~/.codeai-hub/sessions/{workspace-slug}/{A}/{sessionId}.jsonl`
   - При переходе на B:
     - либо создаём новую UI-сессию `S2` с провайдером `B`;
     - либо “переезжаем” в combined-сессию (см. UnifiedSessionArchitecture: `combined/all`).

2. **Combined-сессия (multi-provider)**  
   - История хранится в:
     - `~/.codeai-hub/sessions/{workspace-slug}/combined/all/{sessionId}.jsonl`
   - Все сообщения уже имеют `providerId` и могут принадлежать разным провайдерам.

Рекомендуемая перспектива:
- считать, что любые сложные сценарии (смена провайдера, консилиум) живут в `combined/*` сессиях;
- single-provider сессия — частный случай, который можно “мигрировать” в combined при первом переключении.

### 6.2. Шаг 2: Чтение unified-истории

Оркестратор:
- находит unified JSONL для UI-сессии `S` (single-provider или combined);
- читает его через UnifiedSessionReader в массив `UnifiedMessage[]`:

```ts
const history: UnifiedMessage[] = unifiedSessionReader.readAll(sessionPath);
```

### 6.3. Шаг 3: Применение политики контекста

Политика контекста задаёт, какие части истории попадут в prompt нового провайдера:

- **Политика A: Reconstruction**
  - Пытаемся максимально точно восстановить список сообщений:
    - все `user` и `assistant`;
    - опционально `system`/`tool` в упрощённом виде;
  - обрезаем по токенам сверху или снизу.

- **Политика B: Summary + Tail**
  - Строим summary “дальней истории” (старые сообщения);
  - добавляем последние N пар `user/assistant` как есть;
  - удобно для длинных диалогов и экономии токенов.

- **Политика C: Hybrid**
  - summary для всего до определённого “важного” момента;
  - выбранные ключевые сообщения отображаются полностью;
  - всё после “важного момента” передаётся без суммаризации.

Политика хранится в `ContextPolicyConfig` и может зависеть:
- от типа провайдера;
- от режима (single-provider vs combined);
- от настроек пользователя.

### 6.4. Шаг 4: Вызов Out-адаптера нового провайдера

```ts
const ctx: ProviderOutAdapterContext = {
  unifiedHistory: history,
  contextPolicy: resolvePolicyForProvider('codex', mode),
};

const result = codexOutAdapter.buildContext(ctx);
// result.promptMessages → отправляем в Codex SDK
// result.syntheticNativeLogEntries → при необходимости пишем в нативный JSONL Codex
```

Out-адаптер:
- знает, как превратить UnifiedMessage → `messages[]` под конкретный SDK;
- может маркировать в тексте, какие реплики были от какого провайдера:
  - например: `"[Claude]: …"`, `"[Gemini]: …"`;
- добавляет системные инструкции:
  - “Ты продолжаешь диалог, начатый с другим ассистентом…”;
  - “Считай приведённые реплики контекстом, но отвечай от своего имени”.

### 6.5. Шаг 5: Запуск новой нативной сессии

- Для нового провайдера B создаётся **новая** native-сессия:
  - новый sessionId по правилам B;
  - B пишет свои JSONL/JSON в свою директорию.
- При этом:
  - первый запрос в B уже содержит весь контекст, сконструированный из Unified JSONL;
  - дальнейшие ответы B:
    - идут в его native JSONL;
    - одновременно попадают в Unified JSONL через In-адаптер.

### 6.6. Шаг 6: Продолжение UI-сессии

С точки зрения UI:
- логическая сессия `S` продолжается,  
  просто `providerId` у новых `assistant`-сообщений меняется на B;
- UI показывает единую ленту:
  - ранние ответы от A;
  - более поздние от B;
  - опционально — маркер смены провайдера (system-сообщение).

## 7. Модель данных и расширения Unified JSONL

Чтобы Out-адаптеры могли работать качественно, нужно убедиться, что UnifiedMessage содержит всю необходимую информацию:

- `providerId` — уже предусмотрен (по UnifiedSessionArchitecture).
- `role` — `user | assistant | system | tool`.
- `metadata`:
  - тип события (`thinking`, `tool_call`, `tool_result`, `code_block`, и т.п.);
  - при необходимости — ссылки на внешние артефакты (файлы, ошибки).

В перспективе, для более точной реконструкции контекста:
- можно добавить `messageKind` (например, `plain`, `code`, `analysis`, `final_answer`);
- можно в `metadata` хранить структурированное описание инструментов (tool name, arguments, result).

Важно:
- Unified JSONL **не должен** превращаться в полный дамп SDK;
- он должен оставаться “минимально достаточным” для:
  - отображения в UI,
  - построения контекста для других провайдеров.

## 8. Фазы реализации

### Фаза 1 — Формализация UnifiedMessage и адаптеров

- Уточнить и зафиксировать интерфейсы:
  - `UnifiedMessage`;
  - `ProviderInAdapter`;
  - `ProviderOutAdapter`.
- Обновить `UnifiedSessionArchitecture`, если потребуются новые поля.
- Добавить тестовую реализацию Out-адаптера для одного провайдера (например, Claude).

### Фаза 2 — MVP смены провайдера

- Реализовать:
  - чтение Unified JSONL для текущей UI-сессии;
  - политику `Summary + Tail` как дефолтную;
  - Out-адаптеры для минимум двух провайдеров (например, Claude и Codex).
- Добавить команду в UI:
  - “Continue this session with provider X”.
- Вести весь диалог в `combined/all` для таких сессий.

### Фаза 3 — Расширение и улучшение

- Добавить гибкие политики контекста (Hybrid, индивидуальные настройки).
- Добавить отображение смены провайдера в UI (system-сообщения).
- При необходимости — синтетические записи в native JSONL нового провайдера:
  - чтобы его собственные инструменты тоже видели историю.

## 9. Риски и открытые вопросы

- **Потеря точности контекста.**  
  Unified JSONL хранит не все SDK-поля, поэтому контекст при смене провайдера будет “семантически эквивалентным”, но не идентичным для разных провайдеров.

- **Стоимость по токенам.**  
  Передача summary + нескольких реплик может быть заметно дороже, чем чистое продолжение native JSONL в рамках одного провайдера.

- **Поведение инструментов.**  
  Если провайдер активно использует tool-calls, может потребоваться явное кодирование информации о вызовах инструментов в Unified JSONL, чтобы другой провайдер мог “понимать”, что уже было сделано.

- **UX-вопросы.**  
  Пользователь должен явно понимать, что:
  - провайдер поменялся;
  - новый провайдер видит историю через нашу призму (summary/пересказ), а не нативный лог.

Эти риски не блокируют архитектуру, но должны быть явно учтены в Design Phase и тестировании.

---

## 10. Вывод

Ключевой принцип смены провайдера по ходу чата:

> **Unified JSONL — единственный канонический лог диалога.  
> Смена провайдера = новая нативная сессия,  
> контекст которой собирается из Unified JSONL через Out-адаптер.**

Такой подход:
- избегает сложных и хрупких конвертаций native JSONL между провайдерами;
- переиспользует уже заложенную архитектуру унифицированных сессий;
- естественно расширяется до multi-provider сценариев и консилиумов.
