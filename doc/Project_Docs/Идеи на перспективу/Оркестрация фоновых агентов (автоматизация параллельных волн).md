# Идея: Оркестрация фоновых агентов (автоматизация параллельных волн)

**Дата:** 2025-12-29
**Статус:** Draft
**Контекст:** сейчас параллельные задачи выполняются вручную (несколько терминалов/агентов), а результаты собираются в одном диалоге.

---

## 1. Проблема

Сегодня «параллельность» достигается вручную:
- пользователь запускает нескольких агентов в разных терминалах;
- агенты выполняют задачи и присылают отчёты;
- пользователь вручную переносит результаты в основной диалог и принимает решения.

Ограничение: сам LLM в одном диалоге не может надёжно «держать фоновые чаты» и автоматически получать подтверждения от других агентов.

---

## 2. Цель

Сделать так, чтобы CodeAI Hub сам умел:
- запускать несколько задач одной «волны» параллельно;
- стримить статус выполнения в текущий `SessionView`;
- собирать результаты в единый отчёт;
- безопасно контролировать область изменений (scope) и предотвращать конфликты.

---

## 3. Ключевая идея решения

Решение — не «научить LLM держать фоновые сессии», а реализовать внутри продукта **рантайм оркестрации**:

- **Orchestrator Engine** управляет задачами (jobs), зависимостями и состояниями;
- **Agent Runner** запускает провайдера (Codex/Claude/… ) как отдельный процесс/SDK-вызов;
- все события пишутся в машиночитаемый лог (например JSONL), который UI может стримить.

---

## 4. Базовые сущности

### 4.1 Agent Job (контракт выполнения задачи)
Минимальный набор полей:
- `job_id`, `wave_id`, `agent_id` (A/B/C), `provider`
- `must_read`: список путей, которые агент обязан загрузить
- `prompt_path`, `schema_path` (для Structured Outputs)
- `allowed_write_scope`: список файлов/путей, которые разрешено менять
- `expected_outputs`: ожидаемые артефакты (файлы/структурированный результат)
- `completion_schema`: схема итогового отчёта (статус, summary, changed_files, artifacts, вопросы)

### 4.2 Job Status (машиночитаемое состояние)
- `queued` → `running` → `completed` | `blocked` | `failed` | `canceled`

### 4.3 Артефакты и логи
- `~/.codeai-hub/orchestrator/runs/<job_id>.jsonl` — поток событий выполнения
- `~/.codeai-hub/orchestrator/results/<job_id>.json` — финальный отчёт по `completion_schema`

---

## 5. Компоненты системы

### 5.1 Orchestrator Engine (логика, планирование, контроль)
Функции:
- читает план (например волны из `doc/TODO/todo-plan.md` или будущий `Plan.md`);
- запускает все jobs текущей волны параллельно;
- не стартует следующую волну, пока текущая не завершена;
- агрегирует результаты и формирует единый отчёт;
- публикует события в UI (через bridge).

### 5.2 Agent Runner (процессный слой)
Функции:
- запускает провайдера как отдельный процесс/SDK-вызов;
- для Codex использует `--output-schema`;
- валидирует каждый structured output по schema;
- пишет события `stdout/stderr/result` в JSONL;
- возвращает Orchestrator Engine итоговый `completion_schema`.

### 5.3 UI интеграция (SessionView)
Подход MVP:
- Orchestrator публикует в активную сессию сообщения вида:
  - `Agent A: IN_PROGRESS …`
  - `Agent B: DONE (artifacts …)`
  - `Agent C: BLOCKED (question …)`
- Для интерактивных jobs (например Idea Collector) — UI остаётся тем же `SessionView`, но сообщения/ответы маршрутизируются в активный `job_id`.

---

## 6. Как обеспечить «подтверждение о выполнении» без ручной пересылки

Ввести стандарт событий (event protocol), который Orchestrator публикует в UI:
- `jobStarted(job_id, agent_id, wave_id)`
- `jobProgress(job_id, percent, note)`
- `jobBlocked(job_id, question, required_inputs)`
- `jobCompleted(job_id, summary, artifacts, changed_files)`
- `jobFailed(job_id, error)`

UI подписывается на события и показывает их в реальном времени.

---

## 7. Параллельность без конфликтов (очень важно)

Параллельный запуск безопасен только при контроле области записи:

1) **Явный write-scope** у каждой задачи (у вас уже правило ≤3 файлов — это идеальная база).
2) Orchestrator не запускает параллельно jobs с пересекающимся `allowed_write_scope`.
3) После завершения job — автоматическая проверка фактических изменений:
   - `git diff --name-only` для задач в репо;
   - сравнение с `allowed_write_scope`.
4) Если job вышел за scope → `failed` или `blocked` (требуется решение пользователя).

---

## 8. MVP-путь внедрения (без Project Manager)

Чтобы проверить идею «на сложном примере», можно сделать MVP без новой UI-системы:

- Источник задач: текущий `doc/TODO/todo-plan.md` (волны W1.A/W1.B/W1.C).
- UI: отображение статусов в текущем `SessionView`.
- Первые jobs:
  - A: UI FlowWizard (изменения в репо)
  - B/C: schema/prompt (изменения в `~/.codeai-hub/templates/`)

После доказательства работоспособности — перенос визуализации волн/диаграмм в Project Manager.

---

## 9. Вопрос архитектурного размещения

Где жить оркестрации:
- **Core**: логичнее для управления процессами/провайдерами/IO и единого event-stream.
- **Launcher**: логичнее для управления окнами/Project Manager UI.

Практичный компромисс:
- Engine/Runner в **core** (как сервис/модуль).
- Визуализация (графики, диаграммы готовности артефактов) — в **Project Manager** (launcher), подписка на события.

---

## 10. Связь с будущими диаграммами готовности артефактов

Чтобы строить real-time диаграммы готовности (Idea/Spec/Plan), оркестратор должен уметь:
- определять наличие `.codeai-hub/orchestrator/{idea,spec,plan}.md`;
- читать `**Статус:**` из шапки документа (Draft/Approved/…);
- публиковать агрегированное состояние проекта как отдельное событие.
