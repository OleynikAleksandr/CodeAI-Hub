# Автоматизация Flow разработки — Project Orchestrator

## Исполняемый план как источник оркестрации AI-агентов

**Версия:** 2.0
**Дата:** 2025-12-28
**Статус:** В разработке

---

## 1. Назначение документа

Этот документ описывает **практическую модель автоматизации процесса разработки**, в которой:

* центральным механизмом является **Project Orchestrator**;
* AI-агент **не управляется пользователем напрямую**, а следует Flow;
* человек вмешивается **только в контрольных точках**;
* **Structured Outputs** используются как протокол исполнения и гарантия качества.

---

## 2. Ключевая идея

> **Инверсия ролей: не пользователь создаёт документы, а AI-агенты собирают информацию и генерируют артефакты.**

Пользователь:
* отвечает на вопросы агента;
* утверждает артефакты;
* визуально проверяет результаты.

AI-агент:
* ведёт диалог для сбора требований;
* генерирует артефакты по шаблонам;
* выполняет план пошагово;
* отчитывается через Structured Outputs.

---

## 3. Этапы Flow (4 артефакта)

| Этап | Артефакт | Описание |
|------|----------|----------|
| 1. Обсуждение идеи | **Idea.md** | Агент ведёт живую беседу, собирает требования |
| 2. Спецификация | **Spec.md** | Архитектура, классы, контракты, алгоритмы |
| 3. Планирование | **Plan.md** | Исполняемый план с волнами параллелизма |
| 4. Реализация | **Code + Reports** | Выполнение плана с гейтами качества |

Каждый этап завершается **артефактом**, который утверждает пользователь.

## 4. Guided Conversation (не анкета!)

### Проблема жёстких опросников

Формальный список вопросов:
* даёт только ответы на заданные вопросы;
* не позволяет пользователю добавить важное;
* не учитывает контекст предыдущих ответов.

### Решение: направляемая беседа

Агент получает:

1. **Цель** — какой артефакт создать
2. **Чек-лист** — что нужно выяснить (не порядок вопросов!)
3. **Стиль диалога** — живая беседа, уточняющие вопросы
4. **Критерии завершения** — когда информации достаточно

Агент **сам решает** какие вопросы задавать и в каком порядке.

### Structured Output для диалога

После каждого ответа пользователя агент возвращает:

```json
{
  "conversation_state": {
    "collected": {
      "module_name": "Project Orchestrator",
      "problems": ["..."],
      "solutions": null
    },
    "coverage_percent": 65,
    "next_action": "ask_clarification",
    "suggested_response": "Вы упомянули сессии — расскажите подробнее..."
  }
}
```

Это гарантирует, что агент:
* отслеживает прогресс;
* не забывает важные темы;
* завершает когда достаточно.

## 5. Структура Plan.md с волнами параллелизма

### Принцип: структура = визуализация

Не метки и атрибуты, а **сама организация плана** показывает параллелизм:

```markdown
## Волна 1 — Независимые задачи

> Можно запустить несколько агентов параллельно.

### [Агент A] Компонент UI
- Task 1
- Task 2

### [Агент B] Schema
- Task 3

### [Агент C] Prompt
- Task 4

---

## Волна 2 — После Волны 1

### [Агент A] Интеграция UI
**Ждёт:** Компонент UI готов (Волна 1, Агент A)

- Task 5
- Task 6
```

### Правила группировки

1. **Волна 1** — задачи без зависимостей
2. **Волна N** — задачи, зависящие от Волны N-1
3. **[Агент X]** — логический поток, можно раздать разным агентам
4. **"Ждёт:"** — человекочитаемая зависимость

## 6. Сессия как единица работы

### Проблема

Контекстное окно AI конечно. Работа может прерваться:
* по лимиту токенов;
* по таймауту;
* по команде пользователя.

### Решение: автоматическое управление сессией

```
[70%] — Предупреждение, не начинать новую задачу
[80%] — ТРИГГЕР: начать сворачивание (настраивается)
[90%] — РЕЗЕРВ: только на Session Report
```

### Session Report (Structured Output)

```json
{
  "session_id": "S023",
  "status": "completed",
  "plan_progress": {
    "current_wave": 1,
    "completed_tasks": ["P1.S1.T1", "P1.S1.T2"],
    "next_task": "P1.S2.T1"
  },
  "commits": [...],
  "context_for_next_session": {
    "must_read": ["plan.md", "src/component.tsx"],
    "resume_from": "P1.S2.T1"
  },
  "agent_notes": "..."
}
```

### Восстановление контекста

Следующая сессия:
1. Читает Session Report
2. Загружает файлы из `must_read`
3. Продолжает с `resume_from`
4. Задаёт вопросы, если нужно

## 7. Роль Structured Outputs

**Structured Outputs** — не промпт, а **контракт**:

* Агент **обязан** вернуть структуру
* Поля **обязательны** — нельзя пропустить
* Формат **машиночитаем** — можно автоматизировать

### Где используются

| Этап | Schema | Назначение |
|------|--------|------------|
| Idea Collector | idea-collector-schema.json | Направление диалога |
| Spec Generator | spec-generator-schema.json | Генерация спецификации |
| Plan Generator | plan-generator-schema.json | Создание плана с волнами |
| Task Executor | task-executor-schema.json | Отчёт о выполнении задачи |
| Session Report | session-report-schema.json | Завершение сессии |

## 9. Роль пользователя

Пользователь:
* **Старт** — выбирает Flow
* **Ответы** — на вопросы агента
* **Утверждение** — артефактов
* **Проверка** — визуальная, промежуточных результатов
* **Корректировка** — Escape + пауза + правка

Всё остальное:
> **делает Flow и агенты.**

## 10. Поддержка провайдеров

| Провайдер | Structured Outputs | Статус |
|-----------|-------------------|--------|
| Codex | Да (`--output-schema`) | Полная поддержка |
| Claude | Да (SDK) | Полная поддержка |
| Gemini CLI | Нет (feature request) | Только инструкции |

Gemini CLI используется там, где отсутствие гарантий не критично.

## 11. Итог

Project Orchestrator позволяет:

* Автоматизировать до 80–90% Flow разработки
* Сохранить качество через Structured Outputs
* Параллелить работу нескольких агентов
* Управлять сессиями автоматически
* Сделать AI-разработку воспроизводимой

> **Пользователь проектирует систему.**
> **Flow управляет процессом.**
> **Агенты исполняют.**
