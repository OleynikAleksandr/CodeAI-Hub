# Quality Gate Manager — видение модуля и визарда (v2)

Этот документ описывает **будущее видение** модуля Quality_Gate_Manager и установочного визарда, который будет:

- ставиться вместе с CodeAI Hub как отдельный модуль (аналогично провайдерам Claude/Codex/Gemini);
- автоматизировать первичную настройку гейтов качества;
- объединять несколько инструментов качества (Ultracite, архитектурный скрипт, jscpd, ts-prune, проверку ссылок и т.д.);
- расширяться на языки и фреймворки, которые **Ultracite сам по себе не покрывает** (например, C#, C++).

---

## 1. Проблемы текущего подхода

С тем, что есть сейчас (см. `Quality_Gate_Manager_Current_State.md`), мы уже достигаем высокой планки качества, но:

- **Настройка фрагментирована**:
  - Ultracite настраивается через `npx ultracite init`;
  - архитектурный чек — через `scripts/check-architecture.sh`;
  - jscpd, ts-prune, markdown‑links — самостоятельные куски;
  - Git‑хуки — через Husky.
- **Нет единого визарда**:
  - новый разработчик/агент должен прочитать несколько документов и сам собрать картину;
  - первая настройка часто идёт через “попробовал — упало — фиксил по месту”.
- **Ultracite покрывает только JS/TS**:
  - C# (например, бэкенды или сервисы) и C++ (наш CEF‑лаунчер) сейчас не включены в общий Quality‑пайплайн;
  - нет централизованного места, где заданы правилá и инструменты для этих языков.
- **Проблема больших/сгенерированных файлов**:
  - Ultracite/Biome из коробки пытается анализировать крупные артефакты (бандлы, dist‑каталоги и т.п.);
  - отладка ignore‑паттернов сейчас делается вручную, уже после первых падений.

Quality_Gate_Manager должен решить все эти проблемы единым, прозрачным слоем.

---

## 2. Цели модуля Quality_Gate_Manager

Высокоуровневые цели:

1. **Единая точка входа**:
   - команда вроде `npx quality-gate init` (или сценарий, запускаемый из расширения при первом старте);
   - единый wizard, который настраивает всё: Ultracite, Husky, архитектурный чек, jscpd, ts-prune, link-check и т.д.
2. **Кросс‑языковой подход**:
   - TS/JS → через Ultracite/Biome (как сейчас);
   - C# → через Roslyn analyzers, `dotnet format` / `dotnet analyzers`;
   - C++ → через `clang-format`, `clang-tidy`/`cppcheck`, правила для CMake/сборки;
   - Markdown/документация → через markdown‑линтеры и link‑check.
3. **Инкрементальная настройка**:
   - на первом запуске wizard сам обнаруживает тяжёлые/сгенерированные файлы;
   - предлагает настроить ignore‑паттерны **до** того, как всё начнёт падать.
4. **Интеграция с CodeAI Hub**:
   - модуль ставится и обновляется через тот же механизм, что и другие компоненты (Claude/Codex/Gemini/core);
   - конфигурация гейтов качества становится частью “контракта” репозитория.

---

## 3. Архитектура Quality_Gate_Manager

Предлагаемая архитектура модуля:

### 3.1. Ядро (core)

Отдельный пакет, например `@codeai-hub/quality-gate-manager`, содержащий:

- CLI:
  - `npx quality-gate init` — первичная настройка гейтов;
  - `npx quality-gate doctor` — диагностика текущей конфигурации;
  - `npx quality-gate report` — сводный отчёт по состоянию качества (для CI/агентов).
- Конфигурацию:
  - `quality-gate.config.json` (или `.quality-gate/` как каталог):
    - список включённых инструментов и языков;
    - ignore‑паттерны для каждого инструмента;
    - схемы Git‑хуков (pre-commit, pre-push, release).

### 3.2. Адаптеры инструментов

Модуль должен иметь адаптеры для разных инструментов:

- **UltraciteAdapter**:
  - управляет `biome.jsonc`;
  - умеет:
    - запускать `npx ultracite init` с нужными параметрами;
    - обновлять `biome.jsonc` (extends, files.includes / excludes);
    - синхронизировать правила для агентов (Claude/AGENTS/GEMINI).
- **ArchitectureCheckAdapter**:
  - управляет `scripts/check-architecture.sh` и, возможно, выносит сигнатуру проверок в отдельный конфиг;
  - умеет добавлять пути, которые нужно игнорировать (например, `src/**/generated/**`, `src/**/vendor/**`).
- **DuplicationAdapter (jscpd)**:
  - управляет запуском jscpd и списком путей/исключений;
  - может разделять быстрый (pre-commit) и полный (pre-push/CI) режимы.
- **DocsQualityAdapter**:
  - markdown‑линтеры;
  - markdown‑link‑check (список директорий, допустимые схемы ссылок).
- **Language‑specific adapters**:
  - **TypeScript/JavaScript**:
    - Ultracite + ts-prune;
  - **C#**:
    - интеграция с `dotnet format`, Roslyn analyzers, возможно `editorconfig`‑правила;
  - **C++ (наш CEF Launcher)**:
    - интеграция с:
      - `clang-format` (стиль),
      - `clang-tidy`/`cppcheck` (линт),
      - CMake preset’ами;
    - настройка ignore‑паттернов для внешних библиотек/генерируемых файлов.

Каждый адаптер знает:

- какие файлы/папки он обслуживает;
- какие правила/kонфиги нужно обновлять;
- как запускать проверки в разных режимах (fast/full).

## 4. Интеграция с VS Code расширением (CodeAI Hub)

### 4.1. Первый запуск расширения

При первом запуске CodeAI Hub в новом workspace:

1. Расширение проверяет маркер (например, `doc/tmp/quality-gate-init.json` или запись в `.agent/state.json`).
2. Если гейты качества ещё не настроены:
   - запускается wizard:
     - либо как CLI (`npx quality-gate init`) и отображение логов в Output;
     - либо как Webview‑UI, который управляет тем же CLI через IPC.

### 4.2. Шаги визарда внутри расширения

Wizard должен провести пользователя/агента через несколько прозрачных шагов:

1. **Обнаружение стеков и языков**:
   - по `package.json`, `tsconfig*.json`, `.csproj`, `CMakeLists.txt`, структуре `src/`;
   - предлагает включить:
     - TS/JS (Ultracite),
     - C# (если есть .NET‑проекты),
     - C++ (если есть `packages/cef-launcher` или похожие каталоги),
     - проверки документации.
2. **Скан больших/сгенерированных файлов**:
   - показывает список кандидатов:
     - большие файлы (>N строк);
     - типичные build/dist директории;
     - бандлы (`*.min.js`, `media/**/dist` и т.п.).
   - для каждого файла/пути предлагает:
     - игнорировать в Ultracite/Biome;
     - игнорировать в архитектурном чеке;
     - оставить как есть.
3. **Настройка Git‑хуков**:
   - предлагает схему:
     - pre-commit: быстрые проверки (архитектура, Ultracite fix, ts-prune, возможно быстрый jscpd);
     - pre-push: тяжёлые проверки (полный jscpd, markdown‑links);
   - физически генерирует `.husky/pre-commit` и `.husky/pre-push`, используя конфиг Quality_Gate_Manager.
4. **Интеграция с агентами (Claude/Codex/Gemini)**:
   - синхронизирует:
     - `AGENTS.md`;
     - `.claude/CLAUDE.md`;
     - `GEMINI.md` и др.;
   - гарантирует, что правила гейтов качества отражены в инструкциях агентов (чтобы агенты не только ловили ошибки post‑factum, но и генерировали код сразу по стандартам).

5. **Финальное подтверждение**:
   - wizard показывает сводку:
     - какие инструменты включены;
     - какие пути игнорируются;
     - какие хуки реализованы;
   - сохраняет конфигурацию в `quality-gate.config.json` и, возможно, в `.agent/rules`.

---

## 5. Поддержка языков, не покрытых Ultracite (C#, C++)

### 5.1. C#

Для C# модуль должен уметь:

- обнаруживать C#‑проекты (по `.csproj`, `Directory.Build.props`, `*.sln`);
- предлагать подключить:
  - `dotnet format` (стиль кода);
  - Roslyn analyzers (CA‑правила, собственные правила);
  - интеграцию с `editorconfig` (общие правила форматирования);
- добавлять соответствующие шаги в:
  - pre-commit (например, `dotnet format --verify-no-changes`);
  - pre-push/CI (полный анализатор).

### 5.2. C++ (CEF Launcher)

Для C++ (особенно нашего модуля `packages/cef-launcher`) модуль должен:

- обнаруживать C++‑код и CMake‑файлы;
- предложить подключить:
  - `clang-format` — как минимум форматирование (pre-commit для C++ файлов);
  - `clang-tidy` / `cppcheck` — линт и статический анализ (pre-push/CI);
  - настройки для CMake (минимальный набор флагов, режимы Debug/Release);
- добавить гейты:
  - pre-commit: `clang-format` по изменённым `.cc/.hh/.cpp/.hpp` файлам;
  - pre-push/CI: `clang-tidy` по целевым каталогам, сборка launcher через CMake/Ninja.

Также Quality_Gate_Manager должен:

- исключать внешние библиотеки и third‑party код из C++‑гейтов;
- уважать существующий пайплайн `scripts/build-cef-launcher.sh` (не ломая его, а дополняя).

---

## 6. Связь с .agent/AGENTS/CLAUDE.md

Quality_Gate_Manager должен быть “зеркалом” для инструкций агентов:

- при изменении гейтов качества:
  - обновлять `AGENTS.md` (Codex);
  - дополнять `.claude/CLAUDE.md` (Claude Code);
  - при необходимости обновлять `GEMINI.md` и другие `AGENT`‑файлы.
- при запуске wizard’а:
  - явно сообщать агентам, какие проверки считаются обязательными (blocking gates),
  - какие проверки advisory (предупреждения).

Таким образом, агент при генерации кода:

- знает архитектурные правила (микро‑классы, фасады, лимит 300 строк);
- понимает, какие инструменты будут запускаться автоматически;
- может **избегать создания кода**, который гарантированно провалится на гейтах.

## 7. Расширяемость и Roadmap

Ниже — расширенное видение развития Quality_Gate_Manager с учётом языков и фреймворков, которые **Ultracite сам по себе не покрывает** (C#, C++, другие стеки), и наличия отдельного C++‑модуля (CEF‑launcher) в нашем проекте.

### 7.1. Анализ текущего “ландшафта” инструментов

Важно чётко понимать, **где заканчиваются возможности Ultracite**, а где должны включаться другие инструменты:

- Ultracite/Biome:
  - покрывает JS/TS‑мир (включая React, Next, Vue, Svelte, Qwik, Angular, Astro, Remix и т.д.);
  - не умеет C#, C++, Go, Rust, Python и др.
- Для C#/C++ и других языков уже существуют “строительные блоки”, но нет единого `npx <что‑то> init`, аналогичного `npx ultracite init`:
  - C#:
    - `dotnet format` (форматирование + часть стиля);
    - Roslyn analyzers (StyleCop, CA‑правила и т.д.);
    - `editorconfig` как общий слой форматирования.
  - C++ (в т.ч. для нашего CEF‑launcher):
    - `clang-format` (форматирование);
    - `clang-tidy` / `cppcheck` (статический анализ);
    - CMake-проекты и скрипты сборки (как `build-cef-launcher.sh`).
  - Многоязыковые hook‑раннеры:
    - `pre-commit` (YAML‑конфиг, десятки готовых хуков, поддержка `clang-format`, `dotnet format`, `black`, `ruff`, `eslint`, `biome` и т.д.);
    - Husky (который мы уже используем) — более “низкоуровневый” оркестратор Git‑хуков, к которому можно привязать любые команды.

Сейчас Ultracite решает задачу **локально для JS/TS**, а всё остальное — на совести разработчика. Quality_Gate_Manager должен стать верхним слоем, который:

- использует Ultracite как один из адаптеров (для TS/JS);
- добавляет адаптеры для C#, C++, Python и других языков;
- управляет Git‑хуками и пайплайнами так, чтобы все эти инструменты работали согласованно.

### 7.2. Целевой сценарий для “многоязыкового” wizard’а

При первом запуске `quality-gate init` (или при запуске wizard’а из расширения) модуль должен:

1. **Просканировать репозиторий**:
   - найти `package.json`, `tsconfig*.json` → включить TS/JS проверку через Ultracite/Biome;
   - найти `.csproj`, `.sln` → предложить включить C#‑гейты (dotnet format + analyzers);
   - найти `CMakeLists.txt`, `.cc/.hh/.cpp/.hpp` (как в `packages/cef-launcher`) → предложить включить C++‑гейты (clang‑семейство).
2. **Определить большие и сгенерированные файлы**:
   - собрать список файлов по порогу (например, > N строк или > M KB), в том числе:
     - `media/**` (бандлы, dist‑директории),
     - `dist/`, `build/`, `out/`, `coverage/`, временные каталоги;
   - предложить:
     - игнорировать их в Ultracite/Biome (через `files.includes` и `!!`‑паттерны);
     - игнорировать в архитектурном чеке, если это автоген в `src/**/generated`/`vendor`.
3. **Сконфигурировать языковые адаптеры**:
   - TS/JS:
     - `biome.jsonc` (extends `ultracite/*`, корректные includes/!!);
     - привязать `npx ultracite check/fix` к pre-commit/pre-push/CI.
   - C#:
     - добавить шаги:
       - pre-commit: `dotnet format --verify-no-changes`;
       - pre-push/CI: `dotnet build` + запуск анализаторов;
     - опционально — предложить scaffold `.editorconfig`.
   - C++ (CEF‑launcher):
     - сгенерировать/подложить `.clang-format` и `.clang-tidy` в `packages/cef-launcher`;
     - pre-commit: `clang-format` по изменённым `.cc/.hh/.cpp/.hpp`;
     - pre-push/CI: `clang-tidy` по целевым каталогам + `cmake --build` (используя `build-cef-launcher.sh` как часть пайплайна).
4. **Настроить Git‑хуки**:
   - на уровне Quality_Gate_Manager видео выглядит как:
     - pre-commit:
       - быстрые гейты: архитектура, TS/JS через Ultracite, C# формат/проверка, C++ формат, ts-prune;
       - фильтрация по изменённым файлам (где это оправдано).
     - pre-push:
       - тяжёлые гейты: jscpd по всем целевым языкам, markdown‑links, полные анализаторы C#/C++, возможно `npm run test`/`dotnet test`.
   - физически это может быть Husky (как сейчас) или `pre-commit`; Quality_Gate_Manager выступает как слой генерации конфигурации.

### 7.3. Roadmap версий

Возможные шаги развития Quality_Gate_Manager:

1. **v2.0 (MVP)**:
   - CLI `quality-gate init/doctor`;
   - интеграция с Ultracite/Biome + Husky;
   - wizard для ignore‑паттернов и Git‑хуков (включая анализ больших/сгенерированных файлов и автоматическое предложение `!!`‑паттернов для Biome);
   - базовый репорт по TS/JS/Docs.
2. **v2.1**:
   - адаптеры для C# и C++:
     - C# — `dotnet format` + Roslyn analyzers;
     - C++ — `clang-format` + `clang-tidy`/`cppcheck` в связке с уже существующим `build-cef-launcher.sh`;
   - расширение архитектурного чека на другие языки (если структура каталогов позволяет — например, обнаружение C++ файлов > N строк по отдельным правилам).
3. **v2.2+**:
   - глубокая интеграция с CI (GitHub Actions, Azure DevOps, GitLab CI):
     - генерация готовых workflow для GitHub Actions с запуском тех же гейтов, что и локально;
     - возможность “quality gates per PR”.
   - генерация machine‑readable отчётов (JSON) для агентов и дашбордов:
     - чтобы CodeAI Hub и внешние агенты могли анализировать состояние качества и подсказывать приоритизацию refactor/cleanup задач.
   - поддержка “quality profiles”:
     - жёсткий/мягкий режим (например, в feature‑ветках можно ослаблять некоторые гейты);
     - профили по модулям (строже для core/launcher, мягче для экспериментальных пакетов).

Важный принцип: **Quality_Gate_Manager не должен быть жёстко привязан только к одному стеку** (TS/JS). Он должен стать надстройкой, которая управляет несколькими инструментами и языками (TS/JS, C#, C++, и далее по мере необходимости), но остаётся прозрачной и предсказуемой как для людей, так и для AI‑агентов.
