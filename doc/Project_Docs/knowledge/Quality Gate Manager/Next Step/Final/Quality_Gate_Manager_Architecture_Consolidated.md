# Quality Gate Manager — Консолидированная архитектура (RU)

**Статус:** Черновик / Концепция  
**Источник:** Консолидация документов Claude / Codex / Kimi

---

## 1. Визия и ключевая идея

- Цель: превратить контроль качества из редкой Git-проверки в **непрерывный, автономный сервис** вокруг репозитория.
- Процесс написания кода (люди + Writer‑агенты) и процесс контроля качества (Quality‑подсистема + Quality‑агент) **независимы** и идут **параллельно**.
- Простые проблемы фиксируются **автоматически**; сложные — превращаются в явные задачи (QualityTask) с приоритетом и планом.
- Все агенты и инструменты видят **общее состояние качества** (Quality State) и обязаны его учитывать.

---

## 2. Высокоуровневая архитектура

### 2.1. Основные компоненты

- **Quality Gate Manager Core**  
  Центральный сервис, который:
  - хранит конфигурацию `quality-gate.config.json` (события → гейты, blocking/advisory проверки),
  - предоставляет API: `runChecks`, `getQualityState`, `registerCheck`, `registerAgent`,
  - агрегирует результаты и публикует их в хранилище состояния и UI.

- **Слой событий (Event Bus + File Watcher)**  
  Отделяет источники событий от обработчиков:
  - источники: редактор (onSave/onChange), патчи от агентов, Git‑хуки (pre-commit/pre-push), фоновые таймеры,
  - нормализует события в `FileEvent / PatchEvent / WorkspaceEvent`,
  - дебаунсит и отправляет в Trigger Engine.

- **Trigger Engine**  
  Решает, какие проверки запускать на каждом событии:
  - по конфигу выбирает набор гейтов для `onSave`, `onPatch`, `pre-commit`, `background-scan`,
  - формирует `CheckPlan` (инструменты + scope + приоритет),
  - передаёт планы в пул исполнителей.

- **Check Runners**  
  Адаптеры ко всем инструментам качества:
  - Ultracite/Biome, архитектурный чек, `ts-prune`, `jscpd`, link‑check, языковые линтеры и др.,
  - приводят вывод инструментов к общему формату `QualityIssue`.

- **Quality State Store**  
  Устойчивое хранилище качества:
  - проблемы по файлам и модулям, история проверок,
  - агрегированные метрики (количество файлов с проблемами, авто‑фиксы, тренды),
  - очередь задач и фиксов для Quality‑агента.

- **Quality AI Agent**  
  Специализированный агент, чья единственная задача — **контроль качества**:
  - не пишет фичи и не меняет архитектуру,
  - применяет безопасные auto‑фиксы,
  - оформляет сложные проблемы в структурированные `QualityTask`.

- **Слой интеграции с Writer‑агентами и IDE**  
  Обеспечивает доступ ко всем данным качества:
  - IDE показывает diagnostics и дашборд качества,
  - Writer‑агенты получают «quality context» по файлам и не имеют права его игнорировать,
  - любые автоматические патчи проходят через Quality Gate Manager.

## 3. Основные режимы работы

### 3.1. On Save / On Change (быстрый контур)

- **Триггер:** сохранение или изменение файла в редакторе.
- **Действия:**
  1. Event Bus создаёт `FileEvent(filePath, "saved" | "changed")`.
  2. Trigger Engine включает быстрые гейты: Ultracite/линт + лёгкие архитектурные правила для одного файла.
  3. Check Runners возвращают локальные `QualityIssue`; Quality State Store обновляется.
  4. IDE показывает diagnostics; Quality‑агент может применить безопасный auto‑fix (форматирование, импорты и т.п.).
- **Характер:** неблокирующий, латентность ~10–300 мс; цель — мгновенная обратная связь.

### 3.2. On Agent Patch (вратарь для автоматических изменений)

- **Триггер:** Writer‑агент предлагает diff для одного или нескольких файлов.
- **Действия:**
  1. Core перед применением патча отправляет `PatchEvent` в Quality Gate Manager.
  2. Trigger Engine строит `CheckPlan` для затронутого scope.
  3. Check Runners проверяют патч на нарушение правил качества.
  4. Если нарушены blocking‑правила:
     - Quality‑агент пытается переписать патч так, чтобы пройти гейты,
     - если не удаётся — создаётся `QualityTask`, патч возвращается агенту/пользователю на доработку.
- **Характер:** может блокировать автоматические изменения, но не вмешивается в осознанные действия пользователя.

### 3.3. Pre-Commit / Pre-Push (широкий контур)

- **Триггер:** Git‑хуки pre-commit и pre-push.
- **Действия:**
  1. Event Bus получает `GateRequiredEvent`.
  2. Trigger Engine планирует более тяжёлые проверки: `jscpd`, `ts-prune`, link‑check, архитектурный sweep по модулям или всему workspace.
  3. Quality‑агент может автоматически исправить часть проблем и оформить оставшиеся в `QualityTask`.
  4. При критических нарушениях Git‑операция блокируется (или требует явного override от пользователя).
- **Характер:** последняя линия обороны перед фиксацией/публикацией изменений.

### 3.4. Background Scan (фоновый контур)

- **Триггер:** таймер (например, каждые 5–30 минут) или ручной запуск.
- **Действия:**
  - пересканировать часто изменяемые или «красные» модули,
  - обновить агрегаты и тренды качества,
  - сформировать отчёты и/или задачи для сложных проблем.
- **Характер:** низкий приоритет, отдельный пул; не мешает активному редактированию.

## 4. Поведение Quality AI Agent (суть)

Quality‑агент — «сторож качества» с очень узкой миссией.

### 4.1. Основной цикл работы

- Работает **постоянно** в отдельном цикле:
  1. получает из Quality State список файлов и проблем с приоритетом,
  2. читает код и минимальный контекст (правила, метрики, историю изменений),
  3. решает, возможно ли безопасное auto‑исправление,
  4. либо применяет фикс, либо формирует отчёт/задачу.

### 4.2. Типы действий

- **Авто‑исправление (safe auto‑fix):**
  - форматирование кода (через Ultracite),
  - сортировка и очистка импортов,
  - var → const/let,
  - устранение простых lint‑замечаний,
  - применяется только при высокой уверенности и отсутствии конфликтов (файл не занят, нет merge‑конфликтов и т.п.).

- **Отчёт и задачи (QualityTask):**
  - для архитектурных, сложных или рискованных проблем,
  - содержит: список связанных `QualityIssue`, приоритет, примерный объём работы, предложенный план и рекомендованное commit‑сообщение,
  - может автоматически попадать в `todo-plan.md` или внутренний трекер.

### 4.3. Ограничения и безопасность

- Quality‑агент **не имеет права**:
  - добавлять новые фичи или менять архитектуру,
  - трогать файлы, над которыми прямо сейчас работает пользователь или другой агент (используются блокировки/lock‑manager),
  - ухудшать существующие метрики качества.

## 5. Ключевые сущности данных

### 5.1. QualityIssue

Минимальный универсальный формат проблемы качества:
- `id` — уникальный идентификатор;
- `ruleId` — правило/гейт, который сработал;
- `severity` — уровень (info, warning, error, blocker);
- `location` — файл и диапазон/символ;
- `message` — человекочитаемое описание;
- `autoFixable` — можно ли безопасно авто‑исправить;
- `source` — инструмент или AI‑проверка;
- `status` — open/fixed/muted;
- временные метки (`createdAt`, `updatedAt`).

### 5.2. QualityTask

Задача на исправление, когда auto‑fix недостаточен:
- `id` — уникальный идентификатор;
- `issues` — список связанных `QualityIssue`;
- `scope` — файлы и/или модули;
- `assignee` — пользователь или агент;
- `priority` — относительная важность;
- `suggestedPlan` — краткий план действий;
- `recommendedCommitMessage` — предложенное сообщение для коммита;
- `status` — open / in_progress / done.

### 5.3. QualityState

Сводное состояние качества репозитория:
- карта `file → {issues, score, lastChecked, trend}`;
- агрегированные показатели (количество файлов с проблемами, средний score, объём авто‑фиксов, оценка общего усилия);
- очереди: `pendingFixes`, `pendingReports` для Quality‑агента.

## 6. Мульти‑провайдерность и стоимость моделей

- Использовать **быстрые/дешёвые модели** для:
  - локальных фиксов в одном файле,
  - часто встречающихся стилевых проблем,
  - коротких отчётов и подсказок.

- Использовать **более мощные модели** для:
  - кросс‑файловых и модульных рефакторингов,
  - анализа архитектурных нарушений,
  - сложных и неоднозначных ситуаций.

- Стратегия роутинга:
  - классифицировать задачи по сложности/риску,
  - выбирать профиль провайдера (модель, лимиты, стоимость) в конфигурации Quality Gate Manager,
  - логировать решения для последующей настройки и оптимизации затрат.

## 7. Минимальный MVP (одна дорожная карта)

Сконцентрированная выжимка из трёх исходных документов:

1. **Quality Gate Manager Core (MVP)**
   - простейший in‑memory Event Bus,
   - минимальный Trigger Engine для `onSave` и `pre-commit`,
   - адаптеры к Ultracite и архитектурному скрипту,
   - JSON‑хранилище QualityState под `~/.codeai-hub/quality/`.

2. **Быстрый контур onSave**
   - интеграция с VS Code extension,
   - запуск Ultracite + лёгких правил для одного файла,
   - показ diagnostics без блокировки сохранения.

3. **Quality AI Agent (v0)**
   - один профиль с дешёвой моделью,
   - только безопасные авто‑фиксы форматирования/импортов,
   - работа строго по списку файлов из QualityState.

4. **Pre-Commit Gate**
   - Git‑хук, вызывающий Quality Gate Manager,
   - блокировка коммита при критических нарушениях,
   - понятный отчёт для пользователя/агентов.

5. **Базовый Quality Dashboard**
   - простая панель в UI / Project Manager,
   - агрегаты: количество файлов с проблемами, топ‑N проблемных файлов, объём авто‑фиксов за день, общий рейтинг качества.

Всё остальное (многоуровневый анализ, сложные авто‑фиксы, расширенные дашборды, поддержка C#/C++ и т.д.) может добавляться поэтапно поверх этого базового контура.
